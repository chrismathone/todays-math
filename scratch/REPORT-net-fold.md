## 0. 착수 전 보고 — `_net_cuboid` 의 어느 선이 접는 선인가 (브리프 §6)

`w=7·d=4·h=5` 를 렌더해 **그림을 열어 보고** 좌표로 짚었다. 여섯 면은 십자로 놓인다
(`u=8.444` · `ww=59.11` `dd=33.78` `hh=42.22` · `ox=65.78` `oy=16`).

```
        x=32      65.78          124.89   158.67
 y=16              ┌───[top]────┐              top   (65.78, 16   , 59.11×33.78)
 y=49.78  ┌──[L]───┼──[front]───┼──[R]──┐      L     (32   , 49.78, 33.78×42.22)
                                               front (65.78, 49.78, 59.11×42.22)
 y=92     └────────┼───[bot]────┼───────┘      R     (124.89,49.78, 33.78×42.22)
 y=125.78          ├───[back]───┤              bot   (65.78, 92   , 59.11×33.78)
 y=168             └────────────┘              back  (65.78,125.78, 59.11×42.22)
```

**접는 선은 다섯이다** — 면 여섯 장이 이루는 신장나무(6−1):

| # | 맞닿는 두 면 | 좌표 |
|---|---|---|
| 1 | top ↔ front | y=49.78, x 65.78→124.89 |
| 2 | L ↔ front | x=65.78, y 49.78→92 |
| 3 | front ↔ R | x=124.89, y 49.78→92 |
| 4 | front ↔ bot | y=92, x 65.78→124.89 |
| 5 | bot ↔ back | y=125.78, x 65.78→124.89 |

나머지는 전부 **바깥 윤곽(자르는 선)** 이다.

⚠️ **좌표만 보면 헷갈리는 자리가 실제로 있었다.** `x=65.78` 은 접는 선이기도 하고
윤곽이기도 하다 — `y` 49.78~92 구간은 L↔front 접는 선이지만, 그 **아래** 92~168
구간(bot·back 의 왼쪽 변)은 윤곽이다. 그래서 판정을 「선」이 아니라 **「선분」**
단위로 해야 한다. 눈으로 안 봤으면 `x=65.78` 을 통째로 점선으로 만들었을 것이다.

## 1. 무엇을 고쳤나

`scripts/figure/elem_advanced.py` 에 **`_net_body` 한 곳**을 두고 두 전개도가 같이 탄다.
kind 는 「면이 어디 있나」만 말하고, **「어느 변이 접는 선인가」는 공유 여부가 정한다** —
좌표로 짚지 않으므로 `w·d·h`·`sides` 가 바뀌어도 어긋날 자리가 없다 (D-61).

| 함수 | 접는 선 | 상태 |
|---|---|---|
| `_net_cuboid` | 면 6장 → **5개** | ✅ 고침 |
| `_net_prism(sides)` | 옆면 사이 n−1 + 밑면 2 = **n+1개** | ✅ 고침 |
| `_net_cylinder` | **없다** (아래 §3) | 그대로 — 결함이 아니다 |
| `_net_cone` | **없다** (아래 §3) | 그대로 — 결함이 아니다 |

- 면은 **칠만** 한다(획 없음). 윤곽은 **한 폴리라인**으로 잇는다(변마다 그으면
  butt 마개 때문에 모서리마다 톱니가 남는다). 한 고리로 안 이어지면 **던진다.**
- 접는 선 지문은 **`#111111` `5 4`** (겨냥도 숨은 모서리와 같은 지문).

### 🔴 브리프 §3 의 함정 — 확인했다

치수 지문(`#000` 1.4 `6 4`)을 **안 썼다.** 고친 뒤 실측:

```
python scripts/qa/probe-dim-outside.py --specs scratch/specs.json
  → 잰 그림 111 · 치수 점선이 안쪽인 것 0        (요구값 그대로, exit 0)
```

⚠️ **한 번 111 → 129 로 움직였다가 되돌렸다.** 처음엔 면을 `<polygon>` 으로 그렸는데,
`probe-dim-outside.py` 는 「가장 큰 `<polygon>`」을 도형 윤곽으로 삼는다 — 전개도 면을
polygon 으로 바꾸는 순간 그 판정기가 **면 한 장을 도형으로 읽기 시작**해 분모가 18
늘었다(안쪽은 계속 0이라 거짓 결함은 없었다). 그리는 것은 같으므로 **축에 나란한 면은
`<rect>` 로 남겨** 그쪽 분모를 안 흔드는 표현을 골랐다. `probe-dim-outside.py` 는
**한 줄도 안 고쳤다.**

### 곁가지 — 맞닿는 면이 **0.01px 어긋나 있었다**

`<rect>` 는 `x` 와 `width` 를 **따로** 찍고 둘 다 소수 둘째에서 반올림된다. 원래 값에서
폭을 재면 둘이 같이 올림되어 `x + width` 가 이웃 면의 `x` 보다 0.01 커진다. 그러면 그
변이 「공유하는 변」으로 안 읽혀 **접는 선이 조용히 윤곽이 된다.**

실측 — 전개도 44장 중 **4장**(`10/6/2` · `12/7/2` · `10/2/4` · `6/7/4`)에서 변 12개.
**고치기 전부터 있던 것**이고(옛 엔진을 git 에서 꺼내 돌려 확인), 폭을 **반올림한
꼭짓점에서** 빼서 없앴다.

## 2. 판정기 — `scripts/qa/probe-elem-net-fold.py` (브리프 §4)

**고치기 전에 먼저 돌려 양성이 잡히는 것을 확인했다:**

옛 엔진은 `git` 에서 꺼내 **같은 판정기**로 돌렸다(분모를 추론하지 않는다):

```
(고치기 전) 잰 전개도 44 · 접는 선 224개 · 결함 그림 44   exit 1
            F1 224건(접는 선이 전부 실선) + F4 12건(맞닿는 면이 어긋남)
(고친 뒤)   잰 전개도 44 · 접는 선 236개 · 결함 그림  0   exit 0
```

⚠️ 접는 선이 224 → 236 으로 **늘어난** 것은 F4 때문이다 — 어긋난 변은 「공유하는
변」으로 안 읽혀 옛 엔진에서는 접는 선으로 세어지지도 않았다.

### 열쇠가 **둘** 필요했다 — 브리프의 열쇠만으로는 못 쓴다

브리프는 「같은 좌표를 두 면이 공유하는 변인가」를 열쇠로 제시했다. 그것만 쓰면
**거짓 경보가 쏟아진다.** 말뭉치 935장 실측:

```
구조 열쇠만  → 잰 것 400 · 결함 400
   표의 칸 83 · 쌓기나무 104 · 겨냥도(cuboid) 81 · 띠그래프 28 · symmetry 16 …
   전부 「변을 공유하는 두 면」이다. 진짜는 45건뿐이다.
```

늘 우는 가드는 꺼진다(CLAUDE.md 2026-08-20). 그래서 **⑴ 어느 그림이 전개도인가**를
**엔진의 배선표에서** 뽑는 열쇠를 하나 더 두었다 — `_RENDER[kind]` 가 가리키는 함수
이름이 `_net_` 으로 시작하거나 `net` 이 켜졌으면 전개도. **손 목록이 아니라서 새
`_net_…` 함수를 만들면 저절로 걸린다.**

### 결함 넷을 가른다

| | 무엇 |
|---|---|
| **F1** | 접는 선이 실선이다 / 아예 안 그려졌다 ← 원장님이 짚으신 것 |
| **F2** | 바깥 윤곽이 점선뿐이다 ← **반대로 틀리는 것** |
| **F3** | 접는 선이 **치수 지문**(`#000` 1.4)이다 ← dim 판정기를 오염시킨다 |
| **F4** | 맞닿아야 할 두 면이 어긋났다 |

### 눈금 — 양성 6 · 음성 5 (`--selftest`)

음성에 브리프가 요구한 **「바깥 윤곽은 실선이어야 한다」**(F2 양성으로 잡는지)와,
「면이 하나뿐」·「원기둥처럼 점에서만 닿음」·「치수 점선이 윤곽과 나란히 지나감」·
「겨냥도 숨은 모서리」를 넣었다. 양성만 대면 재현율만 재고 지어냄은 구조적으로 0이 된다.
양성·음성 한쪽이 0이면 **판정 자체를 거부**한다(수를 손으로 안 적고 센다).

## 3. ⚠️ `netCylinder`·`netCone` 은 **고치지 않았다** — 결함이 아니기 때문이다

브리프 §2 는 넷을 다 고치라고 했다. 둘은 고치지 않았고, 그 근거를 적는다.

**전개도에서 실선은 「가위로 자르는 선」이다.** 원기둥 전개도는 옆면 직사각형에 밑면
원 둘이 **한 점에서 접해** 있다 — 종이에서 오려 내는 윤곽이 곧 그 전체 모양이고,
**도형 안쪽에 그어진 선이 하나도 없다.** 원뿔(부채꼴+접하는 원)도 같다. 접는 자리는
「원 둘레 전체 ↔ 직사각형 긴 변 전체」인데 그것은 평면 그림에서 **선분으로 나타나지
않는다**(그래서 교과서도 전부 실선으로 그린다).

억지로 긴 변과 원 둘레를 점선으로 만들면 **실선이 짧은 변 둘만 남아** 「이 두 변만
자른다」로 읽힌다 — 이번엔 반대로 틀린다(그것이 판정기의 F2 다).

🔴 **그래서 판정기는 이 둘에 대해 「깨끗」이 아니라 「관할 밖」이라고 말한다.**
`--census` 가 그 칸을 따로 찍는다 — 「결함 0」이 «깨끗»인지 «이 축이 구조적으로
침묵»인지 가르기 위해서다.

```
  kind                 잰 것  관할밖  결함
  netCone                  0      3      0     ← 관할 밖
  netCuboid               34      0      0
  netCylinder              0     24      0     ← 관할 밖
  prism(net)              10      0      0
```

**원장님께 여쭐 것:** 원기둥·원뿔 전개도에서 「밑면이 붙는 자리」를 굳이 표시하길
원하시면 방법은 있다(접점에 짧은 표시). 다만 교과서 관행과 다르므로 확정 없이는
안 넣었다.

## 4. ⚠️ **원장님이 실제로 보신 그 그림은 이 수리에 안 들어간다**

`J10504-A05-005` 의 삼각뿔 전개도는 **`src/lib/middle/m1Geo1.ts` 의
`FIGURE_TETRA_NET`** 이 그린다. 브리프 §0 이 「mid-types-c 워크트리가 쓰고 있으니
건드리지 마라」고 못박아 **손대지 않았다.**

그리고 **초등 엔진에는 각뿔 전개도 kind 가 아예 없다**(`pyramid` 의 허용 키는
`sides`·`h` 뿐, `net` 없음 — 실측). 즉 이 수리로는 삼각뿔 전개도가 안 고쳐진다.

**mid-types-c 에 넘길 것 — 방법은 확인해 두었다.** FigureSpec v2 의 `segments` 는
`dash` 키를 받는다(`figure_scene.py:2506`). `FIGURE_TETRA_NET` 에서 원장님이 짚으신
안쪽 세 변만 바꾸면 된다:

```js
AB: { points: ["A", "B"], dash: "5 4" },
BC: { points: ["B", "C"], dash: "5 4" },
CA: { points: ["C", "A"], dash: "5 4" },
// AD·BD·BE·CE·CF·AF (바깥 윤곽) 은 그대로 실선
```

실제로 렌더해 확인했다 — `stroke-dasharray` 3개가 나오고 바깥 마름모는 실선이다.
`m1Extra.ts`·`m1Solid.ts` 에도 전개도가 있어 **같이 훑어야 한다.**

**거기에 안 걸려 관문 밖에 남는다.** 브리프가 판정기를 시킨 까닭이
「없으면 이 결함은 다시 들어온다」이므로, 이름보다 그 뜻을 택했다.
바꾼 뒤 쓸기가 19개 → **20개**가 됐다.

(⚠️ `.py` 판정기의 `--selftest` 눈금은 관문이 자동으로 부르지 않는다 —
`elemProbeGauges.test.ts` 의 `GAUGED` 표는 `.ts` 만 훑는다. 기존 `.py` 판정기
둘도 같은 처지다. 눈금은 변이 하네스가 회차마다 부른다.)

**공유 DB 는 한 줄도 안 건드렸다.** `src/lib/middle/*` 도 안 건드렸다.
적재된 전개도 그림 359건은 브리프대로 **다시 그리는 쪽이 따로 해야 한다** — 이
수리는 엔진만 고쳤으므로 이미 `figureSvg` 에 굳어 있는 그림은 안 바뀐다.
