# Ontology operation persistence — draft, unapplied to the shared database

This draft adds 14 server-only tables for proposals, approvals, receipts, atomic audit/outbox, descriptive feedback, evidence snapshots, relation review/history, source import authority, compile jobs/chunks, immutable releases and an active generation pointer. It changes no existing table, role assignment, StudentSrsState JSON, FSRS, direct teacher-plan endpoint or reader floor. The native ids are frozen audit context, not authorization edges. New server code rechecks current ownership, branch, enrollment, capability and managed-account leases inside its transaction.

`draft.sql` is generated from baseline `34742b2f02456930d911e60a69ee020ccee56d64` plus explicit checks, immutable-record triggers, RLS and browser-role revocation. SQL/Prisma consistency checks must retain these deliberate native SQL protections. Browser roles get no direct policies or privileges; these tables are used through authenticated server handlers only. The proposed table-owner service connection must be verified in the actual environment before activation.

Before shared application, the lead must obtain: exact schema/catalog comparison, expected new-table count (14), table/row/index size projection, dry-run SQL results, role and RLS comparison, backup/export location, and concrete operational approval. No shared DB inspection, migration application or deployment was performed by this worker.

Rollout: ship readers/schema-aware server modules while no new write routes are enabled; apply the reviewed additive SQL before enabling those modules at runtime; verify database client generation, RLS and old student/API readers; then enable authorized writers. Feature-off operation must return unavailable without touching the new tables. Existing student-record reader floors remain binding. This additive storage creates no student JSON floor and must not justify downgrading any established reader floor.

The concrete writer flag is `MATH_ONTOLOGY_OPERATIONS=on`; unset/other values remain off. This work did not change any environment value. `preflight.sql` is read-only. The application is atomic (`BEGIN`/`COMMIT`, 3s lock timeout, 60s statement timeout, advisory transaction lock) and rejects an existing ontology namespace instead of concealing partial state. It is deliberately fail-closed on replay, not a migration runner that silently treats mismatched existing objects as success.

Measured on the synthetic PostgreSQL 18.1 cluster: 14 tables, 139 columns, 30 indexes, 7 foreign keys, 11 CHECK constraints, 3 functions and 9 triggers; empty total size 344,064 bytes (indexes 245,760 bytes). Existing column/type/default catalog stayed identical. Actual replay rejection, empty rollback to zero new tables and reapplication all passed. These are empty local measurements, not production 17.6 capacity estimates. Post-fixture row counts/sizes and PID/version/stop receipts are external `operations/postgres-run-*.json` evidence.

Execution consumes approval, applies the existing CAS transition, and inserts one unique durable receipt, mandatory audit and outbox in one actual database transaction. A no-op preserves student revision/configuredAt/journey and still records its result. The outbox is at-least-once with stable event identity; no exactly-once claim for external effects. Expired worker leases cannot acknowledge later generations.

`rollback.sql` only drops empty new storage, in reverse dependency order, and fails closed once proposal/review/job/import/history data exists. After real use, disable writes and preserve/export evidence; a rollback that destroys review or execution history needs a separate concrete recovery decision. PostgreSQL receipts/chunks may contain private scope ids and minimal derived observations, so retention/export follows the existing ownership boundaries; they must never be published as raw browser-readable files.

Local reproducibility: `node scripts/qa/ontology-full-operations/run-postgres.mjs /absolute/external/evidence/directory` starts only a synthetic temporary PostgreSQL cluster on loopback/random port, applies baseline schema and this exact draft, uses concurrent actual Prisma connections, and stops/verifies process exit in finally. The launcher requires an independently installed `embedded-postgres@18.1.0-beta.15`; its Darwin arm64 binary package was `18.1.0-beta.16` (PostgreSQL 18.1). This is not Supabase or a production dry run. It never loads a `.env` file or uses a shared database URL.
