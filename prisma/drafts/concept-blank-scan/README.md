# 개념 백지 사진 채점 — 미적용 DB 초안

2026-11-25. `draft.sql`은 검토 자료다. 실행·마이그레이션 생성·`schema.prisma` 수정·버킷 생성은 하지 않았다.
계약은 `src/contracts/conceptBlankScan.contract.ts` v1. 인쇄 스냅숏은 불변이며 새 인쇄는 새 id를 받는다.
지면 코드는 선택/은행 내용의 표지라 발행 id도, 학생 id도 아니다. 같은 코드의 발행을 허용한다.
정확한 선택(`pick`) 및 기존 60기호 인쇄 정원을 넘는 지면에는 코드가 없어 NULL로 남긴다. 후속 식별 방식을 정하기 전 코드로 복구하지 않는다.

## 표와 소유 범위

- `printed_sheet`: 스냅숏 JSON, 코드, 만든 교사, 소유 교사 `user_id`, 당시 `branch_id`.
- `submission`: 지면, 학생, 촬영자(학생/교사 중 정확히 하나), 상태와 CAS revision.
- `photo`: 쪽/재촬영 판, 비공개 버킷 객체 키, 해시, 기한, 삭제 요청/완료. signed URL은 저장하지 않는다.
- `read` / `correction`: 사진 판에 묶인 원래 읽기와 추가 이력. 고침은 원문을 덮지 않으며 직접 입력·행위자를 남긴다.
- `grade`: 판정 대상별 이력. B ○×는 두 읽기 칸을 함께 참조한다. 읽기/고침의 정확한 판을 evidence에 동결하고 교사 수정은 추가 행으로 남긴다.
- `usage_month` / `usage_call`: 서비스 Claude 키 하나의 월 합계·진행 호출·미확인 사용량과 호출 원장. 답안/사진/키를 넣지 않는다.

교사 목록은 `ownedRowsWhere(session)`을 **지면에** 적용하고, 상세/수정은 `withinOwnerScope`를 따른다.
관리자는 자기 지점, 서비스 관리자는 기존 헬퍼의 범위, 일반 교사는 자기 소유만이다. NULL 지점은 개인 소유이지 전체가 아니다.
학생은 인증 세션에서 얻은 studentId만 사용한다. 촬영 이름이나 요청의 studentId/actor/branchId를 권한으로 쓰지 않는다.
교사는 선택한 학생도 `ownedStudentsWhere`로 검증한다. 제출·사진·판정은 부모를 따라 같은 범위를 적용한다.

학생과 지면의 범위 일치는 **추후 쓰기 트랜잭션**에서 학생→반과 지면을 함께 읽고 현재 권한으로 검사해야 한다.
단순 student FK는 같은 지점을 보증하지 않는다. 학생 전반/교사 지점 이동, NULL 개인 범위, 지면 공유 규칙을 확정한 뒤
리드가 복합 FK/트리거를 결정해야 하므로 이 초안을 독립적인 운영 권한 방어로 간주하지 않는다.
사진/읽기/고침의 복합 FK에는 NULL인 branchId를 사용하지 않았다. JSON CHECK는 `IS TRUE`로 결측 NULL 통과를 막고,
전체 JSON, 유효 쪽 수, snapshot의 slot/target과 evidence id 대응은 Zod + 쓰기 트랜잭션의 책임이다.

## DB 저장소를 만들 때의 원자성

1. UTC 시작 월 행을 만들고 잠근다. 미확인 사용량·진행 호출이 있으면 거절, 합계 >= cap이면 거절한다.
2. 호출 id를 만들고 같은 트랜잭션에서 running/active_call_id를 기록한다. 커밋 후 Claude를 한 번 호출한다.
3. 응답 실제 입력/cache read/cache create/출력 토큰과 고정 단가로 정산한다. 잘린 출력도 비용을 더한다.
   같은 lease의 중복 정산은 금지한다. API 응답은 성공했지만 결과 JSON이 깨져도 비용은 같다.
4. 비용 증거가 없으면 unresolved로 닫는다. 작업이 끊겼다고 TTL만으로 running을 풀지 않는다.
   운영 복구는 호출 원장/제공자 증거를 확인한 뒤 한다. 메모리 구현에는 자동 해제나 복구 API가 없다.

현재 로직은 월 합계에 도달한 **다음 호출부터 중지**한다. 단일 진행 호출은 잔액보다 커질 수 있지만,
동시 호출들이 같은 잔액으로 시작하지는 못한다. 한 건도 $100을 넘지 않는 선예약 방식이 필요하면 최대 토큰 예산과
예약액 정책을 따로 확정해야 한다. 메모리 저장소는 시험용이며 운영 서버리스/다중 프로세스에서는 사용할 수 없다.

## 사진 보존 — 두 안, 아직 선택하지 않음

두 안 모두 앱 Supabase의 **비공개 전용 버킷**(이름 미정), 서버 키만 쓰기, 서버가 소유를 확인한 뒤 짧은 signed URL,
객체 키에 학생 이름/학번 없음, 만료 뒤 새 열람 URL 발급 거절을 전제로 한다.
비공개 버킷과 유효기간 URL은 [Supabase Storage 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals)에 따른다.

| 안 | 원본 보존 제안 | 이점 | 남는 제한 |
|---|---|---|---|
| 가 | 업로드부터 7일 | 원본 노출·보관량을 줄임 | 뒤늦은 교사 재검토는 글/판정 이력만 가능 |
| 나 | 업로드부터 30일 | 월 단위 교사 재검토 가능 | 사진을 더 오래 보관 |

주기 작업은 만료/명시적 삭제 요청 → Storage API 삭제 → 성공 시 deleted_at 기록 순으로 멱등 재시도한다.
메타데이터 SQL 삭제만으로 객체가 지워지지 않는다([공식 삭제 안내](https://supabase.com/docs/guides/storage/management/delete-objects)).
학생/제출 삭제도 먼저 객체 삭제 작업을 만들고, 완료 후 연결을 정리한다. CASCADE만으로 사진까지 지워졌다고 하지 않는다.
보존 기간, 실패 사진 기한, 읽은 글/판정 이력의 별도 보존 기간, 재촬영 시 이전 사진 삭제 시점은 보고서의 물음에 남겼다.
