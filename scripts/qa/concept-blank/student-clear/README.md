# 현재 질문과 검토 증거의 대조

이 도구는 편집 초안을 읽는다. 질문·답·기준의 형식 검사, Codex가 실제 읽고 기록한 개별 판단, Claude의 답을 가린 검토와 원문·답을 공개한 검토를 구분한다. 모델의 통과 판정은 실제 학생의 학습 효과를 입증하지 않는다. 운영 은행을 변경하거나 학생 기록을 쓰지 않는다.

`inventory.ts`에 다음 경로를 지정한다. 작업 폴더 이름이나 사용자 이름은 코드에 고정하지 않는다.

```powershell
node node_modules/tsx/dist/cli.mjs scripts/qa/concept-blank/student-clear/inventory.ts `
  --baseline <원래_BANK_PARTS를_담은_baseline.json> `
  --e3e4 <초3·4_보고서_폴더> `
  --e5e6 <초5·6_보고서_폴더> `
  --middle <중학교_보고서_폴더> `
  --reviews <독립_검토_코호트_폴더> `
  --out <대조_결과.json>
```

원문은 `{ sourceCommit, parts }`이며 원래 객체의 필드 순서까지 보존한다. 초3·4와 초5·6의 현재 입력은 `audit.json`이다. 중학교는 완성된 `audit.json`을 우선하고 아직 없으면 `proposal-cohorts.json`을 읽는다. `partial-audit.json` 같은 과거 중간 초안을 최종 입력으로 사용하지 않는다.

`proposals.ts`는 독립 검토와 향후 적용이 함께 쓰는 하나의 변환이다. assembled `bQuestion`·`clozeQuestion`을 우선한다. 초기 초안의 C `{anyOf}`와 빈칸별 동치 표현을 실제 `string[][]`로 옮기며, 기록하지 않은 동의어를 생성하지 않는다. 일반 설명 `coreAfter`와 C 문장은 분리한다. 제외 결정이 없는데 질문이 null인 경우, 인정 답과 지문 키가 맞지 않는 경우, 잘못된 일반 설명은 거절한다. 미완 저작을 유지 또는 승인으로 보충하지 않는다.

`editorial.ts`는 세 작업자의 문서화된 지문 함수를 각각 재계산한다. 장부에 현재 질문·답·기준·일반 설명의 지문이 있고 학습 역할도 일치해야 직접 읽기 후보로 센다. B의 raw 질문과 assembled 질문, C의 실제 문장·인정 답도 대조한다. 최종 장부의 `needs-revision`이나 수정 후 낡은 지문을 채택으로 세지 않는다. 이 기록 자체는 독립 검토 승인이 아니다.

`independent.ts`는 입력 묶음·행별 지문과 두 단계의 입력/원응답/실제 모델 출처를 확인한다. 모든 ID와 실제 노출 형식의 답이 정확히 한 번씩 있어야 하며, 직접 답이 비거나 검토 지적이 남으면 통과 후보가 아니다. 원응답과 정리한 판정은 보존하고 캐시의 `approvedIds`를 신뢰하지 않는다. 다른 버전의 성공 검토는 현재 내용에 적용하지 않는다. 실패한 묶음은 부분 성공도 승인 증거로 사용하지 않는다.

결과에는 현재 지문으로 맞는 독립 검토 후보 수, 직접 읽기 후보 수, 두 검토가 모두 맞는 후보 수를 따로 쓴다. 저작 초안 수나 중복 재검토 횟수와 구별한다. 표기 결함과 C 학생 문장 충돌도 후보 전체에서 검사한다. `releaseReady`는 이 진행 도구에서 항상 false다. 운영 적용에는 전체 내용 채택, 일반 설명의 복습·교재 연동과 실제 인쇄 검증을 별도로 완료해야 한다.

`compile.ts`는 같은 입력 경로와 `--baseline-hash <보존한 원래 BANK_PARTS SHA256>`를 받아 내용 적용 계획을 만든다. 현재 실행 은행이 원래 기준과 같아야 하며, 모든 ID의 현재 직접 읽기와 독립 검토, 학습 역할, 수정 이유, 표기와 C 문장 충돌 검사를 통과해야 출력 파일을 쓴다. 진행 집계 파일의 승인 수나 불리언을 신뢰하지 않고 원본 보고서와 두 단계 검토 파일을 다시 읽는다. 원천 ID·순서, OX·적용·그림은 보존하고 B/C 질문 표와 별도의 일반 설명 변경 목록을 만든다. 다른 세션이 원천 은행을 바꿨다면 덮어쓰지 않고 멈춘다.

계획 상태는 `content-reviewed-plan; print-and-memory-activation-pending`이다. 계획 출력 자체로 운영 은행이나 학생 기록을 바꾸지 않는다. 계획에 기록한 실제 후보 은행의 지문을 기준으로 인쇄·교재·복습 연동을 검증하고, 최신 열린 평가의 지문 호환성을 확인한 다음 별도 적용한다. `definition-source.ts`는 승인된 ID의 일반 설명 문자열만 고치는 코드 위치를 찾으며, 보강 문항의 비어 있는 번호와 수식의 raw 문자열을 보존한다.

`manuscript.ts`는 그 일반 설명 변경 ID가 출처인 대본 턴만 동기화할 계획을 만든다. 다른 세션이 편집한 도입·예제·나머지 대화는 현재 대본 그대로 남긴다. 출처나 배치가 이동하거나 이전 교정 원장의 마지막 문장이 현재 대본과 다르면 교정을 거절한다. 기존 교정의 맨 처음 문장은 보존하여 최초 대본 지문 검사가 계속 가능하다. 오프라인 `materializeGrade`에 후보 은행을 직접 전달해 실제 운영 파일을 먼저 바꾸지 않고 새 대본을 비교할 수 있다.

`source-plan.ts`는 새로 검증한 내용 계획·실제 기준 은행·현재 코드의 대응을 확인하고14개 코드와 별도 질문 표의 파일 내용을 준비한다. 파일은 쓰지 않는다. 실제 적용자는 준비된 모든 `before` 값과 현재 파일을 다시 대조하고, 기존 질문 표가 뜻밖에 존재하면 덮어쓰지 않는다.

원천 사례의 수식 뒤 조사만 틀린 경우 `compile.ts`의 선택 옵션 `--example-corrections <교정 배열.json>`을 쓸 수 있다. 기존 필수 옵션은 그대로다. 배열 각 행은 정확히 `{ part, id, before, after, reason }`이며 `before`는 불변 기준의 `example.prompt` 전체 문자열이다. ID 중복, 다른 part·이전 prompt, 빈 이유, 추가 필드(답·일반 설명 등), 수식이나 다른 문구 변경은 거절한다. 원래 prompt에 `josaFaults` 결함이 정확히 하나 있고, 그 수식 뒤 조사 하나를 올바른 짝으로 바꾼 뒤 결함이 없어야 한다. 답은 원래 그대로다. 교정 파일도 `capturedSources`에 SHA256을 남긴다.

이 경로는 `normalizeProposal`이나 B/C 검토 지문을 바꾸지 않는다. 후보에만 교정을 적용한 뒤 전체 표기 검사와 `candidateBankHash`를 계산하고, 별도 `examplePromptChanges`를 계획에 싣는다. 교정이 없으면 이 필드가 없어서 기존 계획 모양을 보존한다. `source-plan.ts`도 같은 검증과 교정을 해 후보 지문을 대조한다. `example-source.ts`는 `definitionLiterals`의 ID 결합 위치로 사례 prompt를 찾는다(plusSection 개념 튜플은 일반 설명이 요소 3, `[prompt, answer]`가 요소 4). 해당 prompt 리터럴만 고치며 답·다른 ID·순서·helper·OX·적용·그림은 그대로 남긴다. 원천 코드의 prompt나 답이 이동·변경되면 거절하고, 파일 쓰기는 계속 호출자 소유다. 교정 목록은 전체 독립 검토나 인쇄·복습 활성화를 대신하지 않는다.

`opening-source.ts`는 기존 도입부의 핵심 원천 ID·순서·학습 내용 지문을 먼저 확인하고, 교정 일반 설명에 해당하는 소단원·대단원의 출처 지문만 갱신할 계획을 만든다. 도입 질문·설명·목표·기존 검토자와 날짜는 바꾸지 않는다. 바뀐 일반 설명과 기존 목표를 실제로 다시 읽은 기록이 있어야 적용한다. 학습 내용 지문에서 `questionRevision`, `bQuestion`, `clozeQuestion`, `questionExclusions`를 제외하여 평가 물음만 바뀐 경우 원래 목표의 출처를 바꾸지 않는다. 학생 질문의 정확한 동결 대응은 별도의 전체 payload 검사로 유지한다.
