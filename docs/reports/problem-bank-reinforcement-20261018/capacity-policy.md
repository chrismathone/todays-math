# 수학 재고 충분성 — 제품 규칙과 판단 분모

기준 소스: `2ae266866` (2026-10-18). **총 문항 수 대신, 선택 범위·출제 자격·문항류·난이도·형식·최근 제외를 적용한 공급량을 요청 수와 비교해야 한다.** 모든 차시에 20문항이나 여섯 난이도를 요구하는 제품 규칙은 없다.

이 분담은 정적 소스 검토와 메모리 검증만 했다. DB 접속·환경값 출력·제품/인쇄 변경·DB 쓰기·push·배포는 없었다. 실제 DB 재고, 내용 중복과 반복출제 시뮬레이션은 root 담당이며, 기존 감사 보고서의 재고를 이번 실측값으로 옮기지 않았다. 이동 가능한 수치·근거 지문은 [capacity-policy.json](capacity-policy.json), 먼저 작성한 로컬 전달 파일은 `.qa-artifacts/capacity-policy-brief.json`이다.

## 3. root 집계에 적용할 공급 단위

1. **출제 가능한 행**: 공용 풀 `shared`, `reviewStatus=approved`, `directUseAllowed=true`, `answer != MISSING_ANSWER`인 행에 실제 범위·출처·책·검색·난이도·형식 조건을 적용한다. 승인 수나 목록 보유 수만 쓰지 않는다. 빈 답/해설/그림의 내용 품질은 별도 검사 축이며, 임의로 자격 SQL을 넓혀 제품 가용량과 섞지 않는다. 근거: [자격:32](../../../src/lib/problemEligibility.ts#L32), [풀:14](../../../src/lib/problemPool.ts#L14), [자동출제 조회:66](../../../src/lib/findEligibleProblems.ts#L66), [구성 재검증:255](../../../src/lib/unifiedBankSelection.ts#L255).
2. **한 시험지의 문항류 수**: `familyIdOf`가 정본이다. `familyKey.trim()`이 있으면 **unitId와 함께** 식별하고, null/빈 문자열/공백은 `solo:<problemId>`로 각각 센다. 다른 단원의 같은 키를 합치거나 null 전부를 하나로 접지 않는다. `problemType`은 구성/배치의 유형이며 문항류 정체가 아니다. 근거: [문항류:46](../../../src/lib/generator/familyKey.ts#L46), [세기:60](../../../src/lib/generator/familyKey.ts#L60), [선택 중 중복 방지:194](../../../src/lib/generator/balanceDifficulty.ts#L194).
3. **내용이 다른 문항 수**: 위 문항류·행 수와 따로 센다. 한 문항류의 객관/단답 형제나 서로 다른 ID의 같은 발문은 새 내용 재고를 부풀릴 수 있다. 제품의 문항류 규칙은 같은 내용의 모든 행을 자동 합치는 규칙이 아니다. 반복 시나리오는 `ID 재사용 없음`과 `내용 반복 없음`을 각각 표시한다.
4. **난이도 × 형식 × 차시의 결합**: 난이도별 문항류 수를 더하면 여러 칸에 걸친 같은 문항류를 중복 계산할 수 있다. 형식별 수도 같은 문제가 있다. 시험지 만들기는 난이도 배정 뒤 문항류를 뽑고, **이미 뽑힌 문항류의 같은 차시·같은 난이도 형제** 안에서 형식을 배정한다. 전체 풀에 형식 재고가 있어도 실제 무작위 구성에서는 미달할 수 있다. 주변 합계만으로 성공을 보장하지 않는다. 근거: [난이도 배정:479](../../../src/lib/unifiedBankSelection.ts#L479), [문항류를 사용하며 선택:487](../../../src/lib/unifiedBankSelection.ts#L487), [형식 후속 배정:294](../../../src/lib/unifiedBankSelection.ts#L294), [형식의 형제 범위:405](../../../src/lib/unifiedBankSelection.ts#L405).
5. **표시 형식과 구성 형식**: 목록/필터는 본문·정답을 보는 기존 `classifyFormat`을 사용하고, 구성의 형식 의도는 후보의 원시 `questionType`을 사용한다. 따라서 DB의 원시 형식과 파싱 분류는 별도 열로 보존한다. 미분류는 즉시 출제 불가라는 뜻이 아니다. 형식 필터가 있을 때 가용량 API가 `facets:null`을 내는 경우도 있어, 그 응답의 행 수를 문항류 수로 대체하면 안 된다. 근거: [형식 판정:247](../../../src/lib/problem/provenance.ts#L247), [형식 조회:15](../../../src/lib/problem/formatQuery.ts#L15), [원시 형식 배정:431](../../../src/lib/unifiedBankSelection.ts#L431), [가용량 제한:146](../../../src/lib/bankSourceAvailability.ts#L146).

## 4. 최근 14일과 반복 횟수의 차이

실제 조회 구간은 **`[기준일-14일, 기준일]` 양끝 포함**이며 `testDate` 기준이다. 일일/확인테스트는 반 소유자의 계정, 시험지 만들기는 로그인 계정의 **모든 `test`**가 대상이다. 반·학생·시험 종류·상태 조건이 없으므로 초안도 조회 대상이며, 여러 반이 같은 차시를 쓰면 함께 재고를 소비한다. 다른 계정의 사용 이력은 합산하지 않는다. 근거: [날짜 상수:2](../../../src/lib/tests/constants.ts#L2), [전체 조회 조건:19](../../../src/lib/tests/recentProblemIds.ts#L19), [반 소유자 사용:148](../../../src/lib/tests/generateDraftTest.ts#L148), [시험지 계정/서울 날짜:7](../../../src/lib/bankQueryContext.ts#L7).

제외하는 것은 **사용한 problemId**다. 같은 문항류의 다른 ID는 남는다. 문항류의 모든 행이 빠져야 그 문항류가 사라진다. 한 시험지 안의 문항류 제한과 시험지 사이의 ID 제외를 구분한다. 근거: [ID 필터:120](../../../src/lib/generator/selectProblems.ts#L120), [은행 ID 제외:138](../../../src/lib/unifiedPreview.ts#L138), [현재 용량 함수:33](../../../src/lib/tests/draftCapacity.ts#L33).

따라서 14일을 “14회 출제”로 바꿔 계산하지 않는다. 하루 1회라도 날짜 폐구간에는 **15개 날짜**가 들어갈 수 있고, 같은 날 여러 시험을 만들 수도 있다. 반대로 진도가 다른 차시로 이동하면 한 차시를 14번 연속 쓰지 않는다. 실제 이력 기반 잔여 용량과, 같은 차시를 계속 쓴다는 스트레스 가정을 분리해야 한다.

오답 복습의 `planRetry`는 의도적으로 14일 제외를 적용하지 않고 명시적 `excludeIds`를 받는 별도 경로다. 아래 반복 공급 시나리오는 새 일일/확인/구성 시험지를 반복 만드는 경우다. 학생 SRS의 일일 학습량이나 교과서 원문별 지정 복습 슬롯을 여기에 합치지 않는다. 근거: [오답 복습의 경계:16](../../../src/lib/generator/planRetry.ts#L16).

## 5. 수량 시나리오 — 가정으로 표시할 비교표

**한 시험지에 8/10/20문항, 같은 풀에서 총 3/5/10/14회**를 비교한다. 8은 일반 출제의 공장 기본 수다. 10과 20 및 반복 네 값은 이번 감사의 가정이고 모든 차시의 필수 재고 기준이 아니다. 아래 회수에는 첫 시험지가 포함되며, 기존 제외 이력이 없고 모두 같은 제외 창 안에 있다고 가정한다.

| 회당 문항 | 3회 | 5회 | 10회 | 14회 |
| --------- | --: | --: | ---: | ---: |
| **8**     |  24 |  40 |   80 |  112 |
| **10**    |  30 |  50 |  100 |  140 |
| **20**    |  60 | 100 |  200 |  280 |

표의 숫자는 **ID를 재사용하지 않을 때 필요한 총 선택 수 `q × r`**다. 그만큼의 서로 다른 문항류가 필요하다는 뜻은 아니다. 동일한 문항류는 시험지 사이에 다시 나올 수 있다.

- **한 번의 수량 충족**: 출제 자격·현재 필터·최근 ID 제외 후 `F = countFamilies(남은 행)`. 문항류 제한이 켜져 있으면 `F >= q`여야 한다. 제한을 끈 시험지 구성의 행 용량도 별도 표시한다. 일반 자동출제는 올바른 합의 배분으로 실제 `selectProblems`를 호출해 수량·대체 수를 함께 기록한다.
- **반복 공급의 낙관적 상한**: 남은 문항류별 행 수를 `n_f`, 반복 수를 `r`라 하면 `C_r = Σ min(n_f, r)`. 한 문항류는 한 장에 하나만 들어가므로 `C_r < q × r`이면 ID 재사용 없는 r회는 불가능하다. 이 식은 **동일 풀·기간 내 소모·난이도/형식 자유**라는 완화 조건의 용량 검사다. 실제 선택 순서와 필터 결합의 성공을 대신하지 않는다.
- **내용 반복 없는 공급**: 같은 내용의 서로 다른 ID를 모두 새 재고로 세지 않는 별도 조건을 적용해야 한다. 위 `C_r` 통과를 “새 내용 r회 보장”으로 보고하지 않는다.
- **실제 반복 재현**: 기존 제품 선택 함수를 재사용하고 매 회 선택 ID를 누적 제외한다. 최초 미달 회차, 선택 수, 서로 다른 문항류 수, 난이도 대체 수를 남긴다. 시험지 구성은 무작위이므로 시드/난수 고정 방법과 시행 수를 적는다. 날짜가 창 밖으로 나가거나 다른 계정이면 같은 시나리오가 아니다.

예를 들어 **100행·4문항류**인 풀은 기본 8문항을 한 번도 못 채운다. **8문항류·각 14행**인 풀은 완화된 ID 공급으로 8문항×14회 용량을 갖지만, **107행·107문항류**인 풀은 112번의 선택을 채우지 못한다. 이것은 식을 설명하기 위한 가상 예이며 실제 DB 관측이 아니다. 같은 발문 두 형식의 형제만 많으면 내용 반복 용량은 더 작을 수 있다.

root 보고서는 조건별로 `지원 범위 / 요청(q,r) / 자격 행 / 남은 문항류 / 내용 중복 제외 재고 / C_r / 실제 최초 미달 / 난이도·형식 미달`을 함께 제시하면 된다. **기본 8문항도 미달**, **8은 가능하나 10/20 또는 반복 시나리오 미달**, **총수는 가능하나 선택한 난이도/형식 미달**, **일반 지원 범위 밖의 확장 준비 공백**을 나누어 쓰면 보강 대상과 기준이 분명해진다. 이 문서는 어느 차시가 실제로 해당하는지 판정하지 않는다.
