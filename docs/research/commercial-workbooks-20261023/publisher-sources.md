팩 ID는 `visang-5761-2026-ch1-v1`이다. JSON 최상위는 `id`, `label`, `coverage`(문자열), `metadata`, `provenance`, `exercises`이다. 처음 세 필드는 카탈로그용이며, 정식 요청 스키마는 strict이므로 팩 전체를 요청에 펼치지 않는다.

```ts
import pack from "../../data/commercial-workbooks/visang-5761-2026-ch1-v1.json";

const input = workbookCreateEditionSchema.parse({
  requestId, // 호출자가 생성하는 요청 ID
  metadata: pack.metadata,
  provenance: pack.provenance,
  exercises: pack.exercises,
});
// 실제 등록을 수행하는 호출자에서 source.createEdition(input)를 사용한다.
```

`metadata.edition`은 필수이며 `2026년 학습 · 2022개정`으로 고정했다. `provenance.kind`는 `publisher`이고 `reference`에는 공식 교재 URL과 PDF URL이 함께 들어간다. 임의 교재 ID나 서버의 exercise UUID는 이 팩에서 생성하지 않는다.

TSV 머리글은 다음 순서이다.

```text
volume	section	page	number	subpart	answerText	keyStatus	sourcePage
```

`parseWorkbookImport(tsv)`가 정식 스키마로 파싱한 JSON `exercises`와 동일한 결과를 낸다. 빈 키 행에서는 `answerText`, `keyStatus`, `sourcePage`를 모두 비운다. 마지막 빈 필드는 `""`로 직렬화해 여덟 열을 유지하며, 파서는 이를 빈 문자열로 읽는다. 정식 가져오기 파서는 정답 없는 행에 상태·출처 쪽을 지정하면 거부하므로, 그 행의 출처와 검토 근거는 별도 장부의 `nullKeyLedger`에 보존한다.

## 주소와 수록 범위

문항 한 행은 교재의 **큰 문항 번호 하나**이다. 모든 행의 `volume`은 `개념책`, `section`은 `1. 자연수의 혼합 계산`, `subpart`는 빈 문자열이다. 같은 번호 안의 ⑴·⑵ 또는 ❶·❷ 답은 `answerText` 안에 순서와 표식을 보존한다. 소문항을 별개의 과제 문항으로 세지 않는다.

`page`는 교재의 표제 쪽이다. `sourcePage`는 **PDF 파일을 처음부터 1로 센 쪽**이며, 정답 상자가 놓인 쪽을 가리킨다. PDF 6쪽은 24~26쪽 풀이와 경계를 확인한 보조 근거이고, 해당 정답 상자는 PDF 5쪽에 있다.

## 정답 미수록 장부

아래 여섯 주소는 삭제한 문항이 아니라 `key: null`인 등록 문항이다. 미수록 답을 검토 완료 정답 수에 세지 않는다.

| 교재 쪽 | 번호 | PDF 쪽 | 사유 |
| --- | --- | --- | --- |
| 20~21 | 2 | 4 | 선 잇기 그림. 연결 관계를 텍스트 답으로 추측하지 않음 |
| 20~21 | 6 | 4 | 풀이 참조. 설명이 필요한 답을 일부 계산값으로 대체하지 않음 |
| 22~23 | 7 | 5 | ❶의 서술 어휘와 ❷의 수치 배열로 이루어진 복합 답. 수치 부분만 전체 키로 등록하지 않음 |
| 24~26 | 5 | 5, 보조 6 | 인물 선택과 계산 결과의 복합 답. 숫자만 전체 키로 등록하지 않음 |

24~26쪽 19·20번은 정답 상자에 명시된 `7개`, `3개`만 수록했다. 두 문항은 서술형이므로 `limitedAnswerReferences`에 최종 수치만 있다는 제한을 별도로 기록했다. 이 키는 풀이 적절성이나 부분 점수를 판정하는 기준이 아니다.

## 시각 대조와 표기

PDF 2~6쪽을 각 페이지 이미지로 다시 읽고 `pdftotext -layout`의 대응 구역과 비교했다. PDF 2쪽의 양쪽 열과 PDF 4~5쪽의 이어지는 정답·풀이 구역을 구분했다. 이미지 파일별 SHA-256은 검토 장부에 들어 있다.

- PDF 4쪽의 18~19쪽 정답 표에서 텍스트가 번호·답을 `43`, `54`처럼 붙인 부분은 이미지로 확인해 **4번=3, 5번=4**로 분리했다. 이 표의 28개 답 전체를 독립 fixture로 검사한다.
- PDF 2~4쪽과 5쪽의 계산 순서 화살표는 식 뒤 `[① 연산, ② 연산, …]`으로 적었다. 식과 단계는 이미지의 파란 표시를 대조했다. 15쪽 1번 ⑴의 순서는 `÷, −, +`, 17쪽 1번 ⑵의 순서는 `+, ÷, ×, −`이다.
- 곱셈·나눗셈·뺄셈은 `×`, `÷`, `−`로 표준화했다. 추출기에 생기는 역슬래시나 제어 문자를 그대로 정답으로 넣지 않았다.
- 결과가 다름을 나타내는 짧은 답은 `≠`로 표시했다. 선택 칸의 동그라미와 빈 칸은 `(○)`, `( )`로 보존했다.
- ⑴~⑷와 응용유형의 원형 단계 ❶~❷를 구별했다. 선택 기호 ㉠·㉡·㉢, 선택지 ④, 수량 단위, 괄호와 식의 대안은 유지했다. 원문 배열을 정렬하지 않았다.

`reviewed`는 이 범위의 수치·기호 정답 참조를 원문과 대조했다는 뜻이다. 자동 수학 채점, 출판사의 별도 승인, 전권 완전성 또는 서술형 해설의 검토 완료를 뜻하지 않는다.

## 검증과 전달

정식 `commercialWorkbook.contract.ts`와 `commercialWorkbooks/import.ts`를 사용하는 단위 검사가 판본 필수성, TSV/JSON 동등성, 100개 주소의 전체 목록과 유일성, PDF 출처 쪽별 개수, 28개 연산 답 fixture, 순서·괄호·단위·부분 표식, 빈 키 장부의 완전성, 범위 밖 제외를 검사한다. 실행 명령은 다음과 같다.

```sh
npx vitest run src/__tests__/unit/commercialWorkbookPublisherPack.test.ts
```

2026-10-23 실행 결과: **8개 검사 통과**. 해당 검사 파일의 ESLint와 변경 파일의 공백 검사도 통과했다.

이 분리된 소스 작업트리에서는 서버 작업트리의 계약·가져오기·오류 모듈을 검사 목적으로만 복사했다. 해당 서버 파일과 `node_modules` 연결은 이 변경에 커밋하지 않는다. 서버·UI 변경, 운영 데이터 등록, push는 이 작업에서 수행하지 않는다. 후속 작업은 카탈로그에서 이 팩을 선택하고 기존 `createEdition` 경로로 등록하는 연결이며, 범위를 넓히려면 별도 페이지 대조와 새 커버리지 장부가 필요하다.
