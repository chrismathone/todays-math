# 관리 콘솔·지점 관리 고도화

상태: 2026-10-03 Codex·Claude·Grok 3자 합의 후 구현·통합 검증 완료. [검토·합의 기록](tracks/reports/admin-branch-consensus-20261003.md), [통합·운영 반영 기록](tracks/reports/admin-branch-integration-20261003.md).

2026-10-04 사용성 점검 후속: [37개 항목의 계획 보강·수정 실행](admin-usability-remediation-20261004.md). 기존 완료 범위와 후속 점검을 구분하여 추적한다.

## 사용자 확정 요구

- 관리 콘솔의 계정 관리를 각 지점 안으로 이동한다.
- 지점에서 계정 목록을 보고 기존 계정 수정·승인·정지·복구·비밀번호 재발급 등을 이어서 수행한다.
- 지점마다 수학·영어 메뉴를 켜고 끈다. 원장도 지점 체크리스트를 따른다.
- 기존 웹앱의 디자인과 컴포넌트를 이어 쓴다.
- Codex·Claude·Grok의 3자 합의를 도출한 뒤 계획을 실행한다. 이 요청에 따라 화면 배치도 기존 디자인 범위에서 함께 검토·선택한다.

## 현재 코드에서 확인한 문제

- Branch는 이름·생성일만 갖고 있어 지점 메뉴 설정을 저장할 수 없다.
- auth.ts, accountRouteAccess.ts, adminAccounts.ts, AccountReview.tsx가 isAdmin에 전체 메뉴를 자동 부여한다. 영어의 일부 API 도우미에도 같은 예외가 있다.
- /admin의 계정 목록과 집계가 전 지점 공통이다. 지점 카드의 원장 링크도 전역 계정 상세로 이동한다.
- 개인 메뉴만 저장된 구조에 지점 제한을 덮어쓰면 지점 메뉴를 다시 켰을 때 원래 개인 설정이 복구되지 않는다.
- 지점 관리 권한과 업무 메뉴 이용권은 별개여야 한다. 메뉴가 모두 꺼져도 관리·내 정보·로그아웃 경로는 유지한다.

## 제안하는 사용 흐름

1. /admin은 /admin/branches로 이동한다. 관리 콘솔 상단은 지점 관리·eywa 동기화·SRS 등 기존 운영 도구를 유지하고 별도 전역 계정 관리 메뉴를 없앤다.
2. 지점 목록에 지점명, 원장, 계정 수, 사용 메뉴 수와 명시적 '지점 관리' 링크를 표시한다. '미소속 계정' 진입점은 따로 제공한다.
3. 지점 상세에는 지점명/원장 요약, '계정'과 '사용 메뉴' 영역을 둔다. 계정 검색·상태 필터·집계·페이지 이동은 전부 현재 지점 범위다.
4. 계정 상세에도 지점 이름과 목록으로 돌아가기 링크를 표시한다. 기존 URL은 현재 소속 지점 URL로 연결해 북마크를 보존한다. 계정 이동 후에는 새 소속으로 이동한다.
5. 사용 메뉴 편집은 기존 수학/영어 탭과 체크리스트를 재사용한다. 저장 전 변경 항목과 영향 범위(원장·관리자·강사 포함)를 알리고 명시적으로 저장한다. 저장 성공·실패·충돌을 구분한다.
6. 개인 메뉴에는 지점에서 차단한 항목의 사유를 표시한다. 개인 설정과 실제 허용 결과가 혼동되지 않게 설명하며, 원장 직책 때문에 체크하거나 편집을 잠그지 않는다.

### 배치 검토

Wire 후보: A 지점 목록→지점 상세의 계정/메뉴 영역, B 지점 카드 안 전체 인라인 펼침, C 전역 계정 화면에 지점 필터만 추가, D 좌측 지점 목록+우측 분할 편집. 제안은 A: URL로 지점 맥락을 보존하고 기존 계정 화면을 재사용한다.

Hi-fi 후보: H1 현재 흰 패널·절제된 파란 강조·기존 밀도, H2 큰 요약 대시보드, H3 빽빽한 스프레드시트, H4 오버레이 중심. 제안은 H1: 현재 관리 콘솔 토큰·버튼·체크박스·간격을 유지한다. 새로운 시각 정체성을 도입하지 않는다.

## 권한 정책 제안

- 일반 지점 계정(원장·관리자·강사): 실제 메뉴 = 지점 허용 ∩ 개인 허용 ∩ 기존 시범 운영 제한.
- 지점 관리자 직책은 소속 지점 계정/자료 관리 권한이며 메뉴 전체 허용권이 아니다.
- 최고관리자는 `isSuperAdmin === true`로 판별한다. 최고관리자도 업무 메뉴는 소속 지점·개인 설정을 따르며, `/admin`·운영 복구 경로 접근은 별도 권한으로 유지한다. 일반 원장에게 `/admin` 권한을 추가하지 않는다.
- 미소속 계정은 개인 메뉴 정책을 따른다. 다른 지점의 메뉴를 상속하거나 임의의 기본 지점에 배정하지 않는다.
- 지점 체크리스트는 현재 메뉴 ID를 정확히 저장한다. 과거 개인 설정의 통합 english 호환 처리는 유지하되 지점에서 영어 앞의 세 메뉴를 끈다고 듣기/은행까지 자동으로 끄지 않는다.
- 메뉴를 끄면 사이드바·직접 URL·관련 API·인쇄/내보내기 관문에 같은 정책이 적용된다. 소유권 판정에 필요한 isAdmin은 그대로 유지하고 메뉴 우회만 제거한다.
- 다음 서버 요청부터 최신 지점 정책을 다시 읽는다. 이미 생성된 결과물/기록은 삭제하지 않는다.
- 학생의 /learn 인증·과제 이용은 이번 교직원 메뉴 설정과 별도다. 학생 권한까지 확대하는 정책 변경은 이번 범위에 넣지 않는다.
- 기존 eywa 연동 계정의 소속/직책 잠금, 마지막 원장 보호, 승인·정지·삭제 처리, 세션 폐기는 보존한다.
- 지점 체크리스트 변경과 관리 콘솔 안 계정 관리는 기존과 같이 최고관리자 전용이다. 원장의 기존 `/branch` 소속 계정 관리 기능은 유지하되 지점 메뉴 상한을 변경할 수 없다.
- 개인 설정은 **차단 목록**이다. `disabledMenus=[]`는 전체 허용이다. 원장 계정의 개인 설정을 일괄 초기화하지 않는다. 적용 전 익명 집계로 기존 차단값 유무를 확인하고, 명시적으로 저장돼 있던 차단은 사용자 요구대로 존중한다.
- 현재 auth.ts의 JWT 콜백은 매 요청마다 계정을 DB에서 다시 읽는다. 여기에 branch.disabledMenus를 함께 조회하고 공통 서버 계산 함수를 호출한다. 기존 토큰의 오래된 menus를 권한의 원천으로 사용하지 않는다. 요청 사이 영구 캐시는 두지 않는다.
- 지점 메뉴를 꺼도 학생의 기존 `/learn` 과제, 시스템 동기화·배치는 이번 교직원 메뉴 관문의 영향을 받지 않는다. 원장용 대화형 기능에는 정책을 적용한다.

## 데이터와 API 제안

- Branch.disabledMenus string[] 기본 [] 및 menuRevision 정수 기본 1 추가. 기존 지점은 전 메뉴 허용으로 시작해 데이터 파괴 없이 확장한다.
- Branch 메뉴 저장은 expectedMenuRevision으로 낙관적 잠금. 충돌은 409이며 덮어쓰지 않는다. 한 트랜잭션에서 저장·revision 증가·변경 전후 감사 기록.
- 관리 계정 응답은 configuredMenus(개인 설정), branchMenus(지점 상한), menus(실제 결과)를 구분한다. 지점 제한 때문에 개인 설정을 영구 차단으로 바꾸지 않는다.
- 지점 목록/상세 GET은 메뉴와 revision을 반환한다. PATCH는 기존 이름 변경을 유지하고 메뉴 변경을 추가한다.
- 계정 목록 API는 branchId=<UUID>|unassigned 필터를 필수로 검증해 목록·총수·상태·정지/삭제 집계 모두에 적용한다. 누락·빈 값·잘못된 값은 400, 없는 지점은 404이며 전체 목록으로 돌아가지 않는다.
- 지점 안 계정 상세는 실제 소속을 서버에서 검증한다. 조작된 지점 URL로 타 지점 계정을 표시하지 않는다. 기존 최고관리자 계정 수정 API의 인증·동일 출처·충돌 보호는 유지한다.
- DB 스키마를 먼저 적용·검증하고 코드를 배포한다. 대상 migration 한 개만 적용하며 다른 미적용 migration을 함께 배포하지 않는다.

통합 시 최신 main에 별도로 추가된 `textbook` 메뉴를 확인했다. 원래 migration을 수정하지 않고 지점 CHECK에 이 메뉴를 추가하는 `20261003230000_branch_menu_textbook`을 후속 적용한다. 따라서 이번 대상은 지점 기능 원본과 이 호환 migration **두 개**이며, 다른 미적용 migration은 여전히 함께 실행하지 않는다. 교재 제작도 원장 메뉴 우회 없이 같은 지점 제한을 따른다.

### 검토 후 계약 보강

- 메뉴 PATCH의 `expectedMenuRevision` 누락은 400. `{id, menuRevision: expected}` 조건부 갱신의 영향 행이 정확히 1개일 때만 성공한다. 기존 `AccountAuditLog`에 같은 트랜잭션으로 이전/이후 메뉴·actor·branchId·revision을 기록한다. 감사 저장이 실패하면 갱신도 롤백한다.
- 이름만 변경하는 기존 PATCH는 revision을 요구하거나 증가시키지 않는다. 메뉴 요청에는 현재 ID만 허용하고 `english`·알 수 없는 ID·중복은 400으로 거부한다. 두 종류를 함께 보낼 때도 단일 트랜잭션을 사용한다.
- 계정 폼의 원본/저장은 `configuredMenus`이며 `menus`는 결과 표시용이다. 지점에서 막은 체크박스는 실제 허용 상태로는 해제하고 차단 이유 및 보존된 개인 설정을 표시한다. 차단 항목은 지점에서 다시 켤 때까지 개인 화면에서 토글하지 못하게 하되 내부 configuredMenus 값을 보존한다.
- 계정 PATCH의 기존 `expectedUpdatedAt`은 이동을 포함한 모든 계정 변경에 대한 충돌을 차단한다. 화면 소속을 나타내는 `expectedBranchId`를 추가해 현재 소속 불일치를 409로 거부한다. 비밀번호 재발급에는 현재 누락된 수정 시각·소속 비교와 트랜잭션을 추가하고 폼에서 두 값을 전송한다. 백엔드 전용 연동 해제 등 기존 변경에서도 소속 변경과의 경쟁을 검증하되 지점 관리자에게 새 권한을 부여하지 않는다.
- 읽기 전용 `branchMenus`·`configuredMenus`·`menus` 결과 필드 중 API 입력 계약에 없는 필드는 무시하지 않고 기존 strict 검증대로 거부한다. 개인 메뉴 수정의 입력 키는 기존 `menus`를 유지하되 값은 configuredMenus 원본이다.
- 지점 카드의 계정 수는 삭제되지 않은 계정이며 승인 대기 수를 함께 표시한다. 미소속 진입점에도 동일 집계를 표시해 대기 계정이 숨지 않게 한다.
- 유효하지 않은 지점 경로와 소속이 맞지 않는 지점 내 계정 경로는 404. 전역 레거시 계정 URL만 실제 소속 경로로 재이동한다. 명시적 소속 이동 성공 후에는 새 소속 경로로 이동한다.
- 메뉴가 0개면 기존 작업실의 '사용할 수 있는 메뉴가 없습니다' 화면과 내 정보·로그아웃·허용된 관리 경로를 유지한다. 꺼진 메뉴로의 재이동 반복을 만들지 않는다.
- 차단 목록 방식은 미래에 추가되는 메뉴를 기본 허용한다. 단, 듣기 등 별도 시범 운영 조건은 계속 AND로 제한한다. 새 메뉴 추가 시 계약·DB CHECK·권한 경로 검증을 함께 갱신한다.
- 기존 미적용 migration들은 이름·체크섬을 대조해 기록만 하고 이번 범위에 자동 포함하지 않는다. 새 migration의 전제 스키마가 충족되는지 검사한 후 대상 하나만 적용한다. 관련 없는 미적용 이력이 있다는 이유로 전체 적용하거나 기존 기록을 조작하지 않는다.
- 2026-10-03 운영 DB의 읽기 전용 익명 집계: 활성 원장 2명과 미소속 최고관리자 1명 모두 개인 차단값이 없다. 강사 10명 중 9명은 차단값이 있다. 따라서 원장 자동 허용을 제거해도 기존 원장 권한이 갑자기 0개가 되지 않으며, 강사 설정은 그대로 보존해야 한다.
- 같은 검사에서 `branch`·`user`는 RLS가 꺼져 있고 `anon`·`authenticated`에 DML 권한이 있었다. 새 지점 메뉴 설정이 앱 밖에서 변조되지 않도록 대상 두 테이블에 RLS를 켜고 공개 클라이언트 권한을 회수한다. 정책을 새로 열지 않는다. 기존 NextAuth+서버 Prisma 연결은 테이블 소유자/서버 역할로 계속 사용한다. 다른 테이블의 보안 개편으로 범위를 넓히지 않는다. 적용 전 서버 DB 역할의 소유/우회 여부를 확인하고 실제 로그인·메뉴 읽기·계정 변경과 anon/authenticated 접근 거부를 검증한다. 근거: [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security).

### 반드시 점검할 메뉴 우회 지점

`auth.ts`, `accountRouteAccess.ts`, `adminAccounts.ts`, `AccountReview.tsx`, `english/routeSupport.ts`, `english/bank/http.ts`, `english/bank/service.ts`, `privateDocumentActions.ts`, `math-srs/courseTeacherRoutes.ts`, `classes/[id]/math-srs/page.tsx`, 듣기 runtime의 교사 직접 조회. `ownerScope.ts`의 소유권 확대와 학생용 runtime은 변경하지 않는다. 단순 전체 isAdmin 치환은 금지한다.

### 1차 검토의 의견 차이와 Codex 조정

- Claude의 원장 개인 설정 초기화 제안은 실제 원장 2명의 차단값이 모두 비어 있고 빈 배열이 전체 허용이므로 불필요하다. 저장된 개인 정책을 지우지 않는다.
- Grok의 지점 관리자에게 콘솔의 모든 계정 수명주기 작업을 허용하자는 제안은 현재 권한보다 넓다. 이번에는 최고관리자 콘솔의 배치만 바꾸고 원장의 기존 `/branch` 권한을 그대로 둔다.
- Grok의 응답 필드를 deny list로 바꾸자는 제안 대신 기존 UI/API가 사용하는 허용 목록 계약을 유지한다. `configuredMenus`·`branchMenus`는 그 각각의 허용 목록이며 서버 계산 결과 `menus`와 구분한다. 저장 DB만 deny list다. 개인 폼 제출은 실제 결과를 되쓰지 않는다. 메뉴가 바뀌지 않은 이름/이메일 저장은 `menus` 자체를 전송하지 않아 레거시 개인 값까지 보존한다.
- 지점 차단 체크박스를 편집 가능하게 하자는 Claude 제안과 개인 체크 상태를 그대로 표시하자는 Grok 제안 대신, 사용자가 요구한 '지점 체크리스트를 따르는 실제 메뉴'를 체크 상태로 보여 준다. 개인 허용 원본은 별도 상태로 보존하고 차단 설명에 표시한다. 지점 설정을 풀면 원본대로 복구된다.
- 두 검토자의 관련 없는 미적용 migration이 있으면 무조건 중단하자는 의견 대신, 기존 저장소에서 사용 중인 대상 지정·체크섬·전제조건 가드를 유지한다. 이번 migration만 트랜잭션 적용하며 관련 없는 이력을 고치거나 같이 실행하지 않는다.

## 실행·검증 순서

1. Claude·Grok 독립 검토 → Codex가 수정안 작성 → 두 검토자에게 최종안 재검토 → 세 주체의 명시적 결론을 기록한다.
2. Orca 워크트리: 데이터/API, 권한 정책, 관리 UI를 경계가 겹치지 않게 병행한다. 공유 계약을 먼저 고정한다.
3. 의미 있는 테스트: 원장도 지점 차단 준수, 다른 지점 불변, 개인 설정 보존, 최신 세션 반영, 관리 경로 유지, 미소속, eywa 계정 메뉴 저장, 모든 집계 지점 범위, 동시 수정 충돌.
4. 실제 로컬 PostgreSQL과 브라우저로 최고관리자→지점 A 메뉴 끄기→A 원장 직접 API 차단→B 원장 허용→재켜기→개인 설정 보존을 검증한다. 계정 상세/이동/기존 URL, 모바일·키보드·실패 상태도 확인한다.
5. 타입 검사·관련 테스트·빌드·UI 검증 후 main에 병합한다. DB→코드 순서로 반영하고 완료한 깨끗한 워크트리를 정리한다.

## 이번 범위에서 보류

- 지점 삭제/대량 이동, 결제·요금제, 새 사용자 직책 체계, 사용량 분석 대시보드, 학생 메뉴 정책, 지점별 브랜딩.
- 실사용 지점 체크값은 운영자가 화면에서 선택한다. 구현 과정에서 임의로 현재 지점 메뉴를 끄지 않는다.
