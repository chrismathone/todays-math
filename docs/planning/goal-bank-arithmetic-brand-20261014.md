# 문제은행 업그레이드와 연산대장 실행 계획

작성일 2026-10-14 · 기준 main `4040b23b3` · 개정안 4
근거: [실사용 벤치마킹](benchmark-qbank-20261014.md)

검토 결과: Codex 조정, Claude·Grok 최종 **approve**. Gemini는 실행기 미설치로 미참여. [이견 조정과 합의 기록](benchmark-consensus-20261014.md)을 따른다. 아래 합의는 계획에 대한 것이며 구현 완료를 의미하지 않는다.

## 목표와 사용자 확정 사항

첫 목표는 문제은행 업그레이드다. P0에서 **사용 가능한 문항 찾기 → 정확한 수량으로 구성 → 저장·출력**을 완성하고 기존 채점 경로의 두 변형 복습을 보존한다. 제작기에서 저장한 학습지를 채점으로 연결하는 개선은 P2다. 그다음 전용 연산 엔진으로 연습지를 생성·저장·출력하는 `연산대장`을 추가한다. 제품 표시명은 `오늘 수학`, `오늘 영어`로 바꾼다.

사용자가 확정한 연산 방향은 다음과 같다.

- 연산 능력 자체를 확인하고 기르고 반복 연습하는 **전용 연산 문제**를 만든다. 계산이 들어 있는 일반 수학 문제 모음이나 기존 난이도 `연산` 필터로 대체하지 않는다.
- 목적에 맞으면 **별도 연산 엔진을 만든다**. 이번 계획은 전용 엔진 신설을 기본으로 한다. 기존 생성기의 장·문제은행 행을 원천으로 쓰지 않고, 검증한 순수 수학·표현 부품만 재사용한다.
- 출력은 **문제지와 답만 적힌 정답지**다. 풀이·해설 생성과 출력은 요구하지 않는다. 내부의 정답 검증은 필수다.
- 브랜드는 `오늘의수학/오늘의 수학 → 오늘 수학`, `오늘의영어/오늘의 영어 → 오늘 영어`다. 독립 기능명 `오늘의 기억`은 유지한다.
- 결제·주문은 하지 않는다. 외부 서비스의 문항·화면을 복제하지 않고 탐색 구조와 작업 흐름을 참고한다.

이 문서는 구현 지시와 수용 기준이다. 계획 합의가 구현·데이터 적재·배포 완료를 뜻하지 않는다. 시작 시 최신 main과 운영 화면을 다시 대조한다. 경쟁사에서 메뉴만 확인한 항목은 실제 채점·학습효과까지 검증된 것으로 해석하지 않는다.

## 문제은행 수량과 출처 계약

### 수량을 같은 의미로 비교한다

`src/lib/bankSourceCounts.ts`와 `src/contracts/bankSource.contract.ts`의 기존 계약을 보존한다.

| 수 | 정의 | 화면에서의 의미 |
| --- | --- | --- |
| 책의 `count` | 공용 풀에서 보이는 해당 책 원문 행 수 | 책 전체 보유량 |
| 책의 `open` | 위 원문 중 `problemEligibleWhere`를 만족하는 수 | 책 전체의 출제 가능 원문 수 |
| 현재 조건의 사용 가능 수 | 현재 학년·단원·난이도·출처·제외 ID 등에 동일한 출제 자격을 적용한 수 | 지금 구성에 실제 사용할 수 있는 수 |
| 원문별 두 변형 준비 수 | 지정 슬롯 중 현재 출제 자격과 원문 대응 검증을 통과한 슬롯 수 | 0/2·1/2·2/2 |
| 실제 담긴 수 | 현재 학습지에 중복 없이 담긴 문항 수 | 실제 미리보기·출력의 대상 |

기존 출처 고르기 창의 전체 보유 수는 **다른 필터와 무관한 전역 재고**다(D-161). 이를 현재 필터의 가용량으로 몰래 바꾸지 않는다. `kinds`는 보유량이며 출제 가능 수가 아니다. 기존 sources API를 우선 확장하되 기본 응답 의미와 호환성을 보존한다. 갈래/자료 종류의 eligible 수와 필터 적용 가용량은 명시적인 조회 모드·버전 계약으로 분리하며 기존 숫자 필드를 다른 형태로 바꾸지 않는다. 같은 데이터·권한·조건 F에서 범위 가용량, 목록 total, 랜덤 선택 풀이 같은 `resolveUnifiedBankQuery`/출제 자격 조건을 쓰도록 짝 시험을 둔다. 겹치는 범위를 합산할 때는 문항 ID의 합집합으로 센다.

검수 조회에서는 출제 불가 행도 `eligible=false`와 확인 가능한 상태를 보여 줄 수 있다. 고르기·구성·출력에서 자격을 강제한다. `directUseAllowed`는 법적 권리만 나타내는 칸이 아니라 그림 유실 등 여러 잠금 사유에 쓰인다. `source`, `reviewStatus`, 정답 상태로 확인되는 사실만 표시하고 원인이 저장되지 않은 잠금은 `출제 잠금(사유 미기록)`으로 표현한다. 승인된 교과서 원문 전체를 사용 금지로 취급하지 않는다.

출제 자격의 유일한 규칙은 `src/lib/problemEligibility.ts`다. 공유 풀, 승인, 직접 사용 허용, 정답 센티널 검사를 서버·화면에서 동일하게 적용한다. 30개 원문 중 현재 조건에서 24개만 사용 가능하면 원문 30과 사용 가능 24를 나란히 표시하고, 실제 24개를 담았을 때 출력 수도 24다. 조회 후 권리·검수 상태가 바뀌면 출력 직전 재검증으로 차이를 설명하고 갱신하며 낡은 24를 강제 유지하지 않는다.

현재 `ScopePicker`는 0문항 선택을 막고 `width={880}`을 사용한다. 이 동작을 신규 구현으로 보고하지 않는다. 가용량 미확인·로딩 실패를 0으로 위장하지 않고 별도 상태로 처리하며, 교사용 수학 제작기의 가용량 확인 전 적용은 막는다. 클릭·전체 선택·필터 전환·초안 복원·출력 재검증까지 같은 규칙을 적용한다. 공통 컴포넌트의 영어 사용처는 따로 회귀 확인한다.

### 출처별 탐색은 확보한 메타데이터부터 연다

차시 선택은 학년 맥락과 계층 탐색을 개선하고, 책/자료/자료 안 번호와 시험지/회차는 별도의 출처 고르기로 설계한다. 현재 `SourceMaterial`에 교과서 본문 쪽 필드가 없고 번호도 자료 안 번호이므로 **쪽별 탐색은 구현 범위에서 뺀다**. P0의 축은 `과목 → 출판사·저자/책 → 자료의 교과서 단원 번호·종류·회차 → 자료 안 번호`다. 모든 자료를 차시 735행 모달로 표현하지 않는다. 범위 팝업은 배포본과 CSS를 실측하고 공용 `PickerDialog`/`BankSourcePicker`를 재사용·확장해 중앙 배치·최대 폭·스크롤·초점 복귀를 수정한다.

실행 전에 다음 준비도 표를 실제 데이터에서 산출한다. 이번 계획 검토에서는 운영 DB를 재집계하지 않았다.

1. 교과서: 출판사·책·개정판·단원 번호·자료 종류/회차·자료 안 번호의 보유/누락 수와 원문-변형 연결률. 본문 쪽과의 대응은 향후 별도 확보 항목이다.
2. 기출: `Exam`/`ExamQuestion`, `past_exam` 원문, 그 원문에 연결된 변형의 실제 행 수와 학교·학년/과목·연도/회차·번호·사용 가능 수. 데이터가 0이면 빈 제작 입구를 만들지 않는다. 학평은 현 모델/자료가 확인되지 않아 이번 범위 밖이다.
3. 누락 필드는 `미분류` 또는 해당 탐색축 비활성으로 처리한다. 파일명·문항 내용에서 추정한 값을 확정 메타데이터로 표시하지 않는다.
4. 기존 `books/materialKinds` 필터는 `school_textbook`에 한정되고 `transformed`는 `other`에 속한다. 책에서 변형을 찾는 관계 조회는 원문 연결을 사용하며, 호환되지 않는 필터를 합쳐 빈 결과를 만들지 않는다.
5. `engine` 출처에는 엔진 표지 없는 `manual` 행도 포함된다. 이 수를 모두 생성 엔진 문항 수나 생성 가능량으로 광고하지 않는다.

기출 원문 사용 제한은 탐색 개선과 별개다. 제한된 원문은 담기·저장·인쇄·배부 관문을 통과할 수 없다. 시험지 메타데이터만 있다고 실제 출제 가능한 문항이 있다고 표시하지 않는다.

### 교과서 두 슬롯

기존 `src/lib/tests/retryCandidates.ts`, `src/lib/generator/planRetry.ts`, `src/lib/import/schoolTextbook/retryPairPlan.ts`와 저장된 복습 계약을 재사용한다. 슬롯 식별은 `tb-retry-v1:{원문 id}:1|2`에 더해 `source=transformed`, `originProblemId`, 원문과 같은 `unitId`, 출제 자격을 함께 확인한다. 화면마다 파서를 만들지 않고 공통 `textbookSlotReadiness`로 추출한다. 같은 원문·제외 조건에서 `2/2 ⇔ planRetry 부족 0`을 짝 시험으로 검증한다.

- 런타임 준비 상태는 위 `planRetry` 술어와 동일하게 계산한다. 현재 `Problem`에는 원문 fingerprint 저장 칸이 없고 복습 엔진도 이를 검사하지 않으므로, 준비 상태 화면에만 별도 fingerprint 조건을 추가하지 않는다.
- 1/2도 실제로 생길 수 있는 상태다. 두 슬롯 중 하나가 반려되거나 출제 금지이면 부족으로 보여 준다.
- 새 두 변형은 기존 쌍 검증·중복 방지·트랜잭션 적재를 유지한다. 적재했다고 곧 승인된 것으로 취급하지 않는다.
- 일반 유사문항과 지정 슬롯을 구분한다. 부족한 슬롯을 임의 유사문항으로 채워 2/2로 표시하지 않는다.
- 원문별 복습 실행은 기존 부족 차단 정책을 지킨다. 원문-변형 내용 대응은 적재·갱신 도구의 책임이다. 원문 내용이 바뀌거나 재검토로 잠기면 관련 지정 슬롯도 함께 잠그거나 대응을 다시 검증한 뒤 연다. 1A는 현재 갱신 도구가 변형까지 처리하는지 확인하고 공백이 있으면 보강한다. fingerprint 저장 칸과 런타임 비교를 신설하는 대안은 이번 범위에서 제외한다.
- 책 원문 수와 변형 수를 합쳐 같은 의미의 보유량으로 만들지 않는다.
- 원문과 지정 변형을 같은 학습지에 담는 것은 경고 후 허용한다. 경고는 `이 학습지에서 이미 연습한 변형이 복습에 다시 나올 수 있습니다`로 설명한다. 2/2는 자격 있는 슬롯 수이며 새로 보게 될 문항 수가 아니다. 사용 이력 제외 옵션을 적용하면 같은 제외 조건으로 부족을 다시 계산하고 조용히 다른 문항을 대체하지 않는다.

## 전용 연산 엔진

### 문항·유형 라벨 추가 요구 — 2026-10-14

사용자는 연산대장의 `출제율 1~10위` 표시를 보고 일반 문항과 연산 유형 모두에 다양한 라벨을 요청했다. 다음을 이번 화면·데이터 계약에 포함한다.

- 문항 라벨과 유형 라벨은 대상 ID를 구분한다. 유형의 순위를 그 유형에 속한 모든 문항의 개별 출제 순위로 표시하지 않는다.
- 특징 라벨은 확인한 메타데이터/생성 조건으로 만든다. 연산의 `덧셈`, `세로셈`, `받아올림 1회`, `나머지 없음` 등이 대상이다. `기초 다지기` 같은 목적은 검토된 카탈로그 분류로만 제공한다.
- 순위는 실제 사용 기록으로 계산한다. 예: `이 유형에서 출제 1위`, `덧셈 유형 선택 1위`. 비교 집단, 최근 30일/전체 기간, 집계 기준일, 건수를 상세 설명에서 확인할 수 있게 한다. 분모를 정의하지 않은 출제 횟수에 `출제율`이라는 이름을 붙이지 않는다.
- 같은 학습지를 다시 저장하거나 미리보기/새로고침한 것은 새 출제로 세지 않는다. 저장, 출제 확정, 인쇄는 서로 다른 사건이다. `선택 순위`와 `출제 순위`를 섞지 않는다. 연산은 원문 Problem 행을 만들지 않고 저장 문서에 포함된 유형의 사용을 집계한다.
- 첫 적용은 본인 기록을 기본 범위로 한다. 학원 단위 통계는 권한 범위의 익명 집계가 확보되면 별도 범위로 제공한다. 다른 학원의 비공개 학습지나 학생별 기록을 노출하지 않는다.
- 기록이 없거나 표본이 충분하지 않으면 순위 라벨을 숨긴다. 공동 순위는 공동이라고 표시하며 임의 타이브레이크로 유일한 1위를 만들지 않는다. `최근 인기`/`상승`은 두 비교 기간의 관측 자료가 있을 때만 사용한다.
- 후보 라벨은 `출제 TOP 10`, `많이 선택한 유형`, `최근 인기`, `새 유형`, `즐겨찾기`, 특징 라벨이다. 정답률/오답률/효과/추천 라벨은 그 뜻을 뒷받침하는 데이터·검토 없이는 생성하지 않는다.
- 선택 카드에는 대표 2~3개만 표시하고 나머지는 상세에 둔다. 같은 카드 크기와 정보 정렬을 유지한다. 라벨은 색만으로 구분하지 않고 텍스트와 접근성 설명을 제공한다. 인쇄 문제지·정답지에는 기본적으로 넣지 않는다.

위 항목은 사용자 추가 요구와 구현 규칙이며 기존 Claude·Grok 개정안 4 합의에 포함되어 있었다고 소급하지 않는다. 실제 집계 경로와 UI 연결이 끝나기 전에는 라벨 기능 완료로 보고하지 않는다.

### 첫 출시 카탈로그

연산 세부 기능을 키로 관리한다. 과정 전체나 기존 제품 난이도 `연산·기본·응용·심화`로 자동 분류하지 않는다. 첫 출시에는 아래 **7개 스킬군**을 대상으로 하되 각 하위 조건의 지원 상태를 명시한다.

| 스킬군 | 통제할 조건 |
| --- | --- |
| 한 자리 덧셈 | 받아올림 없음/있음, 피연산자 범위 |
| 한 자리 뺄셈 | 결과 0 이상, 피감수·감수 범위 |
| 두 자리 세로 덧셈 | 받아올림 횟수 0/1/2 |
| 두 자리 세로 뺄셈 | 받아내림 0/1, 음이 아닌 결과 |
| 곱셈구구 | 선택한 단과 곱하는 수 범위 |
| 두 자리 × 한 자리 | 피연산자 범위와 받아올림 조건 |
| 두 자리 ÷ 한 자리 | 0이 아닌 제수, 나머지 0인 정수 몫 |

각 스킬은 목표 기능, 선행 기능, 피연산자 범위, 표기 방식, 지원 조건, 정확한 `domainSize`, 정답 형식을 카탈로그에 명시한다. 화면에서도 생성 전에 조건별 가능 수를 보여 주고 요청이 넘으면 생성 버튼을 비활성화한다. 숫자를 바꾸더라도 목표 기능 조건이 깨지면 거절한다. 예를 들어 받아올림 연습에 받아올림이 없는 식이 들어가면 실패다. 문장제·도형 이름/추론·공식 선택·받아올림 횟수 자체를 묻는 지식 문항은 제외한다.

단일 기능 연습을 기본으로 하고 여러 기능을 섞을 때도 선택한 스킬별 배분을 보존한다. 스킬별 요청 수를 각각의 조건별 domainSize와 비교하고 하나라도 초과하면 회차 전체를 거절한다. 표기 방식은 skillId에 고정하며 한 스킬에 여러 표기를 허용하려면 동일성 키와 용량 계약도 함께 바꾼다. 동일 기능을 연습하는 목적과 다양한 식을 제공하는 목적을 구분한다. 속도 측정을 필수로 두거나 정답만으로 이해·특정 오개념을 확정하지 않는다.

분수·소수·음의 정수·혼합 계산은 이후의 **연산 범위 확장**이다. 초등/중등 한 과정씩을 억지로 채우는 첫 출시 조건을 삭제한다. 확장 시 분모·자릿수·부호·연산 순서와 답 표기를 독립 스킬로 정의한다.

### 엔진 경계와 검증

새 `src/lib/arithmetic/`에서 카탈로그 → 문항 명세 → 표기 → 독립 검산을 분리한다. `generateElementaryProblem`, 초등 장 핸들러, 중등 `def`, 문제은행 행은 연산 문항 원천으로 사용하지 않는다. 기존 초등 `연산`에는 선분 이름/각도 유형, 중등에는 문장제가 포함돼 있다.

순수 정수·유리수 연산과 세로셈 표현 부품은 적합성과 영향 범위를 확인해 재사용할 수 있다. 거대한 장 모듈을 가져오지 않는다. 전용 엔진을 만든다는 이유로 기존 학생 SRS·탐험 엔진이나 학습 기록을 변경하지 않는다.

- 생성 명세는 `engineVersion`, `catalogVersion`, `skillId`, 조건, 피연산자·연산자, 시드, 회차·순서를 가진다. 같은 버전·설정·시드로 같은 명세와 순서를 재현한다.
- `verify(spec)`는 명세의 피연산자·연산에서 정답을 다시 계산한다. 생성/렌더 함수가 낸 답을 그대로 받아 성공 처리하지 않는다. 생성 답 오염, 연산자/피연산자 변경, 경계값, 조건 위반을 검출하는 시험을 둔다.
- 학습자용 결과는 식·답란과 정답이다. `solution`을 필수화하거나 검증 로그를 해설처럼 출력하지 않는다.
- 기본 동일성 키는 스킬과 **순서 있는 피연산자**다. 3+8과 8+3은 다른 연습 문항이고, 같은 답을 갖는 다른 식도 허용한다. 동일 키는 한 회차 안에서 중복하지 않는다.
- `domainSize`는 선택 조건과 중복 정책이 반영된 정확한 유한 수다. 한 회차에서 요청 수가 가능 수를 넘으면 전체 생성을 거절하고 가능/요청 수를 알려 준다. 중복·다른 스킬·문제은행 문항으로 조용히 채우지 않는다. 무한 생성으로 표현하지 않는다.
- 회차 간 반복은 학습 목적상 허용한다. 과거 미사용 문항 제외는 후속 기능이다. 생성 탐색에는 종료 상한이 있어야 한다.
- 생성 API의 조건·수량·회차·본문 크기를 서버에서 제한한다. 최초 상한은 기존 제작기 상한 100문항 이내에서 정하고 다회차 총량도 제한한다. 실제 지면은 읽기 쉬운 크기로 여러 쪽에 나눈다.
- 학생 답 자동채점은 첫 출시 범위에 없다. 이후 정수·분수·소수·몫/나머지 답 형태와 동치 판정 계약을 별도로 검증한다.

### 저장과 출력

첫 출시는 `WorkspaceDocument`의 새 `arithmeticSheet` kind와 버전 있는 payload로 저장한다. 기존 문서 kind 열거·읽기/쓰기 API·내보내기·목록·다시 열기·소유권 검사를 함께 확장해야 하며 JSON에 태그만 붙여 완료로 보지 않는다. 서버에서 검증한 명세와 **발문·정답 스냅샷**을 함께 보존하고, 재열 때 최신 엔진으로 조용히 재생성하지 않는다.

새 kind는 `workspace_document_kind_check` 확장 마이그레이션을 동반한다. 현재 CHECK는 `draft`, `extraction`, `conceptBlank`만 허용하므로 payload 태그만으로 저장할 수 없다. kind 이름은 기존 camelCase 관례에 맞춘 `arithmeticSheet`로 통일한다. 공유 DB 적용은 해당 실행의 사용자 승인 범위를 확인한 뒤 **DB 제약 확장 → 호환 읽기 코드 배포/확인 → 새 kind 쓰기 활성화** 순서로 한다. 모르는 kind 때문에 옛 목록·읽기 코드가 실패하지 않는지 확인하고 필요한 호환 배포를 먼저 한다. 새 문서가 저장된 뒤에는 이를 읽을 수 없는 버전으로 되돌리지 않는다.

연산 문서는 `내 시험지`에 연산 자료로 표시하고 `problemCount`는 스냅샷 문항 수로 계산한다. 기본은 비공개이며 소유권·`visibility/sharedBranchId` 권한을 기존 문서와 같은 서버 관문으로 처리한다. 공유·복사·내보내기는 실제 지원한 기능만 노출하고, 문서 수량을 문제은행 재고 수에 섞지 않는다.

생성물을 기존 `Problem`/`Test` 행에 자동 삽입하지 않는다. 현재 이들에는 단원·문항 ID 연결이 필요하고, 풀이 없는 문항을 기존 `nosolution` 대기열로 보내면 요구와 충돌한다. 기존 학생 채점은 숫자 답 자동 검산 계약이 아니므로 화면만 연결해 완성됐다고 하지 않는다.

공통 인쇄의 글꼴·수식·A4 측정·페이지 나눔·미리보기 기반을 재사용한다. 연산에 맞는 간결한 배치는 별도 프리셋/표현층으로 만들 수 있다. `quickAnswerOnly`로 정답지만 만들고, 연산 메뉴에는 풀이·해설 옵션을 두지 않는다. 문제지에는 정답이 새어 나오지 않아야 한다. 문항 번호와 정답 번호는 페이지가 바뀌어도 정확히 대응한다.

`/dev/print-check`에 연산 검수 항목을 추가한다. 브라우저 미리보기·인쇄용 렌더·PDF의 잘림/수식/답란/페이지 순서를 검증하고, 종이 출력은 실제 수행한 경우에만 검수 완료라고 기록한다. HWPX는 기존 기능을 보존하고 연산 지원을 표시하려면 같은 정답 전용 지면을 별도로 검증한다.

## 브랜드와 화면 구성

사용자에게 보이는 제목·로그인·작업실·학생 화면·접근성 이름·메타데이터·인쇄 헤더부터 변경한다. 출현 문자열 전체를 일괄 치환하지 않는다. 기존 초안, API/DB 키, 패키지명·도메인, 저장소 키, JSON 스키마는 호환성 계획 없이 바꾸지 않는다. `오늘의 작업·개념·기억·시험·확인테스트`는 독립 기능명으로 유지한다. 제품명 SSOT `WORKSPACE_PRODUCTS`, 교사에게 복사되는 ChatGPT 요청문 머리, 연동 안내 문구도 표시명 감사 대상이다. 저장소 밖 서비스 설정은 위치와 적용 여부를 별도로 기록한다.

교사/관리자 UI와 새 연산 지면은 `DESIGN.md`·메뉴 맵·D-07에 따라 구체적인 Wire 4~5안 → 선택 → Hi-fi 4~5안 → 선택 순서로 준비한다. 이미 선택된 시안과 사용자 위임은 재확인하지 않는다. 이번 제품명 변경 문구는 사용자가 확정했으므로 그대로 반영하며 새 브랜드 디자인 선택을 이유로 문구 수정을 보류하지 않는다. 긴 목록은 공용 `PickerDialog`, 출처는 `BankSourcePicker`, 여러 쪽 미리보기는 `PaperStrip`을 우선 재사용·확장한다. 현재 Math workroom이 English 정렬 기준이며 `Workroom.module.css`가 활성 셸이다. 학생 앱과 인쇄 예외를 지킨다. 범위·후보·출력의 주 행동 위치, 빈 상태와 실패 상태, 키보드 탐색·초점 복귀, 1700px·1280px·좁은 화면의 스크롤을 확인한다. 연산 학생 메뉴를 자동 개방하거나 SRS를 재설계하지 않는다.

이번 사용자는 Claude·Grok·Gemini와 함께 적용 계획을 만들고 검토하라고 명시했다. 위 담당은 그 협업 계획이며 실제 실행 시 제공자 가용성을 다시 확인한다. 이 요청 밖의 일반 작업트리 실행은 AGENTS.md의 Codex 기본 원칙을 따른다.

독립 작업은 Orca 작업트리로 분리한다. 각 워커는 담당 파일만 수정하고 교차 경계를 보고한다. 코드 작성 전에 관련 로컬 Next 가이드를 읽는다. 푸시 직전 대상 원격 브랜치를 fetch·비교하고 최신 변경 통합 후 관련 검사를 다시 수행한다. 강제 푸시는 하지 않는다. 완료·병합·clean·실행 종료 조건을 모두 만족한 작업트리만 제거하고 브랜치는 보존한다.

## 출시 경계

연산 첫 입구는 기존 `시험지 만들기` 안에 둬 새 최상위 메뉴 키를 추가하지 않는다. 기존 메뉴 권한과 문서 소유권을 서버까지 적용한다. 향후 최상위 메뉴가 필요하면 `accountAccess.contract.ts`의 메뉴 열거와 사용자/지점 DB CHECK, 기본 노출 정책을 함께 변경하고 DB → 코드 순으로 배포한다.

0문항 과정은 기본 선택 목록에서 접거나 뒤로 보내되 검색에서 상태를 확인할 수 있게 한다. 이미 전달되는 `bankEntry.grade → initialGroup`을 보존하고 반/진도 맥락을 추가한다. 고등 과목 신규 개방은 기존 열린 결정의 최신 상태를 확인한 별도 범위이며 이 계획으로 자동 확대하지 않는다.

작업트리 배분 전 계획 문서를 커밋해 공유하거나 명시적인 절대 경로와 문서 버전을 제공한다. 배포 검증은 시험 지점·시험 계정으로 실행하고 실제 학생에게 자동 배부하지 않는다. 배포 단계에서는 Ready 상태와 실제 화면을 확인한다. 인쇄 변경은 `/dev/print-check`에 등록하며 기존 프로젝트의 실물 출력 완료 조건을 지킨다. 프린터 검수를 못 했으면 대기 상태를 남기고 인쇄 검수가 완결됐다고 보고하지 않는다. 현재 단계는 계획 검토이므로 배포·DB 적용을 수행하지 않는다.

## 수용 시나리오

1. **빈 범위와 미확인:** 0문항 범위는 클릭·전체 선택·필터 전환·초안 복원·출력에서 적용 불가. 가용량 로딩/오류는 0과 구분. 영어 제작의 기존 동작 보존.
2. **수량 의미:** 전역 count/open은 필터 변경으로 의미가 변하지 않음. 현재 조건 가용량은 실제 조회/선택과 동일. 원문 30/가능 24/담김 24를 구분. 권리 변경 시 출력 전 차이 안내와 재검증.
3. **메타데이터:** 책/자료/자료 안 번호 누락, 변형이 other에 있는 경우, 문항 연결 없는 시험지, 중복 원문을 포함하는 자료를 구분. 교과서 본문 쪽 탐색과 학평은 이번 범위에서 제외.
4. **두 슬롯:** 0/2·1/2·2/2, 하나 반려, 같은 변형 중복, 원문 갱신 시 적재 도구가 원문·지정 변형을 잠그거나 재검증하는지, 정답 미확인, 일반 유사 후보를 검사. 부족한 복습 쌍은 차단.
5. **연산 정의:** 7스킬군의 지원 조건/범위/용량을 명시. 문장제·도형·공식 선택·기존 연산 등급 행이 섞이지 않음. 받아올림 등 목표 조건이 모든 생성 문항에서 성립.
6. **연산 검증:** 같은 버전/설정/시드 재현, 독립 검산, 잘못된 답/명세 검출, 경계값, 중복 키와 domainSize 초과 거절, 종료 상한, 미지원 조건 거절.
7. **연산 저장:** 새 문서 kind의 생성·목록·재열기·복사/내보내기 지원 범위를 명시하고 버전/스냅샷 복원. 소유권 없는 읽기/수정 거절. 엔진 업데이트 후 기존 문서의 식과 답 유지.
8. **연산 출력:** 문제지와 답만 있는 정답지. 풀이·검증 로그 없음. 번호 대응, 페이지 잘림, 수식·세로셈 정렬, PDF 검증. 실제 종이 출력 여부는 별도 기록.
9. **브랜드/화면:** 오늘 수학/오늘 영어 표시, 오늘의 기억 유지. 폭별 주 행동·스크롤·키보드·초점 복귀 검증.
10. **회귀:** 기존 수학/영어 초안, 인쇄/PDF/HWPX, 채점·두 변형 복습, 지점·학생 권한 보존. 연산 문서가 문제은행 수량·풀이 없음 검수·SRS 기록에 섞이지 않음.

변경된 로직/API/컴포넌트의 의미 있는 시험, `npm run type-check`, 관련 lint와 대표 브라우저 시나리오를 수행한다. 문서만 검토한 이번 단계에서 테스트 통과나 운영 기능 완성을 주장하지 않는다.

## 조정자 목표 프롬프트

> 문제은행 개선을 최우선으로 수행하라. 이 계획서, 벤치마킹, AGENTS.md, DESIGN.md, 메뉴 구현 맵을 읽고 최신 main/운영 화면과 데이터 준비도를 확인하라. 전역 재고와 필터 가용량을 구분하고, 빈 범위 선택을 막으며, 교과서 두 지정 슬롯과 일반 유사문항을 구분하라. 다음으로 전용 연산 엔진의 7스킬군을 생성·독립 검산·유한 용량·스냅샷 저장·문제지/정답지 출력까지 연결하라. 연산에는 풀이·해설이 필요 없고 기존 연산 난이도 문항을 가져오지 않는다. 학생 자동채점·분석은 별도 후속 범위다. 표시 브랜드를 오늘 수학/오늘 영어로 바꾸되 오늘의 기억과 저장·API 식별자를 보존하라. 아래 소유권대로 Orca 워커를 운용하고 가용하지 않은 AI를 실행한 것으로 보고하지 마라. 합의된 수용 시나리오와 증거를 충족한 뒤 통합하라. 결제·주문을 하지 말고 푸시 직전 원격 최신 변경을 통합하라.

## 워커별 프롬프트

### Claude 문제은행 데이터

> bankSourceCounts, bankSource 계약, problemEligibility, 통합 문제 조회/선택, retryCandidates/retryPairPlan과 저장 복습 계약을 읽어라. 전역 count/open/kinds 의미를 보존하고 현재 조건의 가용량을 별도 계약으로 구현하라. 메타데이터의 확보/누락과 원문-변형 관계를 확인하고, 지정 슬롯의 자격·원문/차시 연결·중복·부족을 복습과 같은 규칙으로 반환하라. 원문 갱신 시 변형 잠금/재검증은 적재 도구에서 확인·보강하고 런타임에만 fingerprint 조건을 추가하지 마라. UI/CSS·연산 생성·브랜드는 수정하지 마라. 필터/권한/24대30/빈 범위/두 슬롯 상태와 출력 직전 재검증의 API 증거·시험·남은 공백을 제출하라.

### Grok 전용 연산 엔진

> 이 계획의 7스킬군 전용 카탈로그와 문항 명세, 결정적 생성, 독립 verify, 동일성 키, 조건별 정확한 domainSize, 초과/고갈 거절, 버전 있는 arithmeticSheet payload를 설계·구현하라. 기존 초등/중등 장이나 문제은행 행·난이도 연산 필터로 문항을 공급하지 마라. 순수 수학/표현 부품만 적합성을 확인해 재사용하라. 공개 연산 payload와 출력에 solution 필드를 두지 않는다. 식과 답만 제공하고 내부 검산 기록을 분리하라. 생성기 답을 오염시켜도 독립 검산이 실패를 검출하는 시험과 시드·경계·중복·용량·목표 기능 검증을 제출하라. 기존 Problem/Test·학생 기록에 삽입하지 말고 UI·브랜드·공통 저장 API는 임의 수정하지 마라. 지원/제외 스킬, 조건별 용량, 저장/인쇄 어댑터 경계를 보고하라.

### Codex 화면과 통합

> DESIGN.md·메뉴 맵의 Wire→Hi-fi와 관련 Next 가이드를 따른다. 운영 범위 모달의 크기·위치·0문항·미확인 상태를 재현하고 학년 맥락·출처별 탐색·준비/담김 수를 개선하라. Claude의 확정 읽기 계약으로 지정 두 슬롯과 유사 후보를 표시하라. 문제은행 P0 확인 후 연산 전용 화면과 arithmeticSheet kind의 저장·권한·복원·인쇄 연결을 구현하라. 기존 수학/영어 문서와 공통 인쇄 기반을 보존하고 연산은 해설 없는 문제지/정답지만 제공하라. 학생 채점·SRS 연결을 임의 추가하지 마라. 실제 API→저장→재열기→출력과 폭별 접근성 증거를 제출하라.

### Gemini 또는 명시적으로 인수한 Codex 감사와 브랜드

> 초기에는 코드 변경 없이 관찰/추론/미확인 기능, 데이터 준비도, 표시 문자열 위치와 호환성 위험을 감사하라. 통합 뒤 최신 main의 독립 작업트리에서 사용자 표시명만 오늘 수학/오늘 영어로 변경하라. 오늘의 기억, API/DB/저장 키, 외부 연동·내보내기 버전은 보존하라. 원 담당과 다른 관점에서 빈/미확인 범위, 수량, 두 슬롯, 연산 정의·검산·용량·스냅샷 저장·정답 전용 출력, 권한·영어/수학 회귀를 확인하라. 수학적 검산이나 운영 검증을 수행하지 않았으면 그 범위를 명시하라. 결함은 재현 단계와 실제/기대 결과로 보고하고 다른 담당 파일을 무단 수정하지 마라.
