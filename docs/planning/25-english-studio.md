## 1. 화면

### 1.1 셸 — 제품 전환 (작업실 셸 `UnifiedWorkspace`)

- 제품은 둘: `math`(지금 메뉴 8개) · `english`(메뉴 셋). **제품은 뷰에서 파생**한다 — 영어 뷰(`english*`)면 영어, 아니면 수학. 따로 저장하지 않는다.
- 브랜드 단추 = 고르기 단추(`aria-haspopup="listbox"`). 목록에는 **권한이 있는 제품만**(영어 메뉴가 꺼진 계정은 목록 자체가 없고 지금 모습 그대로).
- 고르면 그 제품의 **첫 뷰**로 간다 — 수학은 `defaultView`(지금 규칙), 영어는 `english`. 영어에 마지막으로 있던 뷰는 기억하지 않는다(단순).
- 영어 제품의 옆 메뉴: 파란 단추 «새 시험 등록»(⑸) → 나브 캡션 «오늘의 영어» → 탭 셋(⑹). 수학의 «현재 시험지» 카드 · 담기 바(`worksheetView`)는 **영어에서 안 뜬다** — 개념·SRS 마운트 블록과 같은 결로 붙인다(`worksheetView` 에 넣지 말 것).
- 접힘: 마크 + 딱지 «영»(⑷). 접힌 채 마크를 누르면 목록이 옆으로 뜬다(시안 C).
- 빠른 검색(Ctrl K)에는 영어 탭 셋도 같이 나온다(`availableNav` 가 한 목록이므로 그대로).

### 1.3 편집 화면 (검토·편집)

세트 이름 · 검토 상태(초안 · 검토 중 · 검토 완료) · 지문 · 문항마다 «QUESTION 01 · 유형» 머리 + 발문 · 보기 1~5 · 정답(번호 또는 인정 답안) · 해설/채점 기준 · 지문 속 근거 · 저장(`revision` CAS — 남이 먼저 저장했으면 «다른 곳에서 먼저 저장됐습니다. 다시 불러온 뒤 고쳐 주세요.» 409) · 인쇄(§5). 내용을 고치면 상태는 «초안»으로 내려간다(ChatGPT 앱 규칙 그대로).

### 1.4 모양

- 토큰은 **작업실 그대로**(05 §8.9 D-125 — `Workroom.module.css` · `--learn-*`). 새 색 없음. 상태 알약은 오늘의 개념과 같은 결(초안 호박 · 검토 중 회색 · 검토 완료 코발트 옅은 면). **왼쪽 색 막대 금지 · 카드·행에 손가락 커서 금지(D-30)** — ChatGPT 앱 CSS 의 전역 `cursor:pointer` 는 옮기지 않는다.
- 문구 D-08(느낌표·이모지 없음). ChatGPT 앱의 «수업의 다음 한 걸음» 류 장식 문구는 빼고 사무적으로.
- 영어 지문·보기는 지면과 화면 모두 **세리프 라틴 글꼴**(`PAPER_FONTS` 의 라틴 세리프 — 새 글꼴 싣지 않음), 발문·해설은 한글 본문 글꼴.

## 4. 문제 만들기 세 길

### 4.1 ChatGPT 로 제작 (키 없음 — 주 경로)

원장님이 ChatGPT 구독으로 만든다(«여기(ChatGPT)에서 할 거니까»). 앱은 **두 단추**:
1. **요청문 복사** — 학교·학년·이번 시험의 출제 설정·난이도·문항 수·지문 길이·(있으면) 저장한 지문을 넣은 요청문을 만들어 클립보드로. 요청문 끝에 **답 형식**(JSON 하나 — `{title, passage, questions:[{type,prompt,options,answer,explanation,evidence}]}`)을 못 박는다. 규칙 문장은 ChatGPT 앱의 시스템 프롬프트 요지(§4.3 과 같은 규칙)를 한국어로.
2. **결과 붙여넣기** — 붙여 넣은 글에서 JSON 을 찾아(코드펜스·앞뒤 잡설 허용 — `jsonRepair` 의 `extractJson` 계열 재사용) 계약으로 읽고 **검증기(§4.4)** 를 지나면 «초안»으로 저장 → 편집 화면. 실패는 어느 문항·어느 규칙인지 한 줄씩.

### 4.2 원문 복원 (규칙 기반, AI 아님)

ChatGPT 앱의 `makeCloze` 이식: 7단어 이상 문장에서 6글자 이상 가장 긴 단어를 빈칸(`________`)으로, 첫 글자·글자 수 힌트, 정답 = 그 단어, 근거 = 그 문장, 유형 «원문 복원»(보기 없음). 최대 문항 수 3·5·10·15. 순수 함수 `src/lib/english/cloze.ts` — 서버·클라이언트 같이.

### 4.3 DeepSeek 직접 생성

- `src/lib/english/generate.ts`: `callAi`(`src/lib/ai/client.ts`) + 프롬프트 `src/lib/ai/prompts/englishExam.ts`(버전 상수 + 사유 JSDoc). 입력 `{mode: new|original|variation, topic, passage, difficulty: 기본|표준|심화, count 1~8, words 80~400, types}`(ChatGPT 앱 `aiInput` 규칙: new 는 topic 필수 · original/variation 은 passage ≥80자 · 고른 유형 수 ≤ count). 🔵 2026-10-06(D-158 · §13): words 는 **30~400**, passage 는 **≥20자**.
- 응답은 **객체 하나**(배열이 아니다) — `parseAiJsonArray` 대신 같은 복구 단계로 객체를 읽는 `parseAiJsonObject` 를 `jsonRepair.ts` 에 더한다(배열 함수는 손대지 않는다). `withOneRetryOnParseFailure` 그대로.
- 라우트 오류 순서: `AiCapacityError` 502 → `AiConfigError` 503 → `AiGenerationError` 502. 검증기 실패는 502 `ENGLISH_DRAFT_REJECTED` + 어느 규칙인지.
- 🔴 시험은 `vi.mock("openai")` + `vi.stubEnv` — **실호출 금지**(절대 규칙 7). 워크트리엔 `.env` 가 없어 켜진 분기는 리드가 main 에서 표본 한 번(교훈 2026-09-20).
- 요금 고지 한 줄(«생성 시 소재·지문을 AI 서버로 보냅니다.»).

### 4.4 검증기 (세 길 공통 — `src/lib/english/validate.ts`)

  2026 수능 영어 24번(제목 · «선지에 지문에 없는 표현») · 34번(빈칸 오답률 79%, 복수정답 주장) — 분쟁 축이 곧 우리 축(정답 유일성 · 선지의 지문 근거).
- 🔴 **세 조사가 따로 찾은 제품 결함**: 학생용 지면이 **원 지문 전체를 상자에 찍고** 그 아래 빈칸 · 어법 · 삽입 · 원문 복원 문항을 둔다 → **정답이 지면에 보인다**

### 12.8 남은 결정 넷 — 3자 협의 (리드 · codex gpt-6-astra · grok-4.7, 2026-09-30 밤)

원장님 «코덱스 및 그록과 협의 도출 진행». §12.6 의 ① · ③ · ④ · ⑤ 를 안건으로 세 회차: 1차는 둘이 서로의 답을 보지 않고 따로 → 2차는 리드의 합의 초안에 이의만(둘 다 «아니오») →
3차 최종안(codex «예» · grok 은 문장 둘을 조건으로 — 그대로 넣어 닫음). 브리프와 답은 `docs/planning/tracks/reports/english-quality/consult/`. 아래가 **합의안**이다. 🔴 화면 · 지면의 형태가 걸린 항목은 원장님 시안 선택 뒤에 구현한다(D-07).

**리드 초안이 뒤집힌 곳**: ⑴ 학생용을 «두 부로 나눠 주게»는 운영 부탁일 뿐이라 부족 · «통합 지문»(빈칸 · 밑줄 · 삽입 자리를 한 글에)은 독해형의 측정 대상을 망가뜨려 기각(둘 다)
⑵ 프롬프트 v4 초안은 그대로 불가 — 지금의 오답 레시피(너무 좁음 · 넓음 · 정면 반대)가 지문 없이 지워지는 보기를 만든다(grok) · 표본에서 극단어(chief · only · replacement)가 오답에만 몰려 있다(codex)
⑶ «문항 속 지문이 세트 지문과 다릅니다»는 변형형에서는 정상이라 경고로 부적절(codex) ⑷ 둘이 따로 요구한 빠진 일 — **사람이 정답 키를 직접 풀어 보는 감사**(지금 «틀린 키가 저장되는 비율»을 모른다).

**1. 학생용 지면의 정답 노출**
- 독해용(원 지문 + 주제 · 내용 일치 · 서술형)과 변형용(어법 · 빈칸 · 삽입, 원 지문 없음)을 **별도 인쇄 묶음**으로. 쪽수는 분량에 따르고 한 묶음만 뽑을 수도 있다. 유형을 한 세트에 섞는 것은 막지 않는다.
- 배부 순서를 화면과 지면에 적는다: 변형용을 먼저 풀고 걷은 뒤 독해용. 같이 주면 답이 보인다는 점을 밝힌다 — **이 안내는 시안 확정을 기다리지 않고 먼저**.
- 변형 문항끼리의 누출 검사: 한 문항의 정답(빈칸 원문 · 삽입 문장과 원래 자리 · 어법의 원래 형태)이 다른 변형 문항의 지문에 보이는가를 **앞뒤 문맥 포함 연속 20자 이상 창**으로 대조. 걸리면 근거 구절과 함께
  «함께 주면 정답 단서가 보일 수 있습니다» + 그 문항을 따로 배부하거나 빼는 길. 기본값(같은 묶음에 못 넣게 / 알림만)은 시안에서 원장님이. 문자열 검사는 누출을 다 잡지 못한다.
- 한계: 먼저 읽은 글의 기억은 못 없앤다 — 같은 원문의 변형형 여럿은 독립 평가가 아니다.

**2. 주제 · 내용 일치의 수렴 단서 (프롬프트 v4)**
- 문장을 덧붙이지 않고 **주제 오답 레시피만 갈아 끼운다**. 공통: 다섯 보기의 추상도 · 범위 · 구체성 · 문장 형식을 맞추고 핵심 관계나 주장만 다르게 — 정답만 균형 잡힌 문장으로 남지 않게.
  갈린 곳은 두 판을 만들어 재서 정한다: (가) 엄격판 — 극단어 · 한정어를 다섯 보기 어디에도 쓰지 않고 «좁음/넓음/정면 반대» 범주 지시를 뺀다(grok) /
  (나) 완화판 — 낱말 · 범주를 금지하지 않고 «특정 낱말이나 범위 오류가 오답에만 되풀이되지 않게»만(codex).
- 내용 일치: 다섯 보기는 지문의 한 문장 또는 여러 문장에서 확인되는 비슷한 범위 · 구체성의 명제. 정답을 글 전체의 요지 문장으로 쓰지 않는다. 틀린 보기는 지문이 **이미 말한** 요소 하나만 바꾼다 —
  지문이 수치 · 순서 · 인과를 주지 않으면 그 요소로 오답을 만들지 않는다.
- 재는 법(재기 전에 적는다): 개발에 안 쓴 새 지문 12개 이상 · 보기 순서를 섞은 지문 없이 풀기 · v3 와 (가)(나)를 같은 조건으로 · 채점관 셋은 독립 표본으로 세지 않고 지문 단위로 · 지문 단위 구간을 같이.
  통과: 지문 없이 푼 정답률이 v3 보다 뚜렷이 낮고(구간이 0 을 벗어남) 40% 이하(잠정, 지향 35%). 보류: 지문을 보고 푼 정답 일치율 5%p 이상 하락 **또는** 루브릭 평균(1~5) 0.3 이상 하락.
  채택: 통과한 판만 후보 — 하나면 그 판, 둘이면 지문 없이 푼 정답률이 낮은 쪽, 차이 구간이 0 을 포함하면 (나), 없으면 v3 유지.
- AI 의 100% 는 강한 경고이지 학생에게도 그렇다는 증거는 아니다 — 아래 사람 가림 풀이로 확인한다.

**3. ChatGPT 붙여넣기 길의 고쳐 쓰기**
- 검증기가 **거절했을 때만** «고쳐 달라 요청문 복사». 요청문: 최신 전체 JSON · 원 지문 · 요청 조건 · 출력 계약 · 저장을 막은 규칙과 관측 사실(문항 번호 · 필드 · 자리 짚기).
  형식 위반은 그 필드만, 내용 위반은 관련 정답 · 해설 · 근거까지 최소 범위로 고치고 나머지는 그대로, 전체 JSON 만. 복사 전에 내용을 볼 수 있다.
- 통과한 세트에는 4 의 지적 정확성이 확인된 뒤, 원장님이 고른 지적만 담는 선택 단추로 넓힌다. 정밀도 0~41% 인 «정답 오류» 검사는 넣지 않는다.
- 재는 법: 거절 20건(탐색) — 재통과율 · 허용 범위 밖 변경률 · 강사 판정에 따른 기존 오류 해결률과 새 오류 발생률.

**4. 품질 검사 표시**
- 문항에 보이는 것(관측 사실과 위치로, 빨강이 아니다): 해설의 정답 번호 ≠ 정답 칸(«정답 칸 ③, 해설은 ④») · «모두 옳다/정답 없음» 보기 · 이스케이프 찌꺼기.
  앞의 둘과 찌꺼기는 **검사마다 따로** 사람 판정 보정표로 정밀도를 재고 95% 이상인 검사만 저장을 막는 검증으로 올린다(«보정표 없이 막는 규칙으로 올리지 않는다»).
- 세트 머리에 한 줄만: 정답 보기만 김 · 절대어가 오답에만 · 정답 번호 쏠림(문항 수가 충분할 때).
- 안 보이는 것: 어법 · 삽입 · 빈칸의 «정답 오류» 검사(내부 측정에만) · 근거 연속 인용(이미 저장 검증).
- «문항 속 지문 ≠ 세트 지문»은 유형별 변형 계약이 허용하지 않은 차이를 식별할 수 있을 때만 지적으로. 못 가리는 차이는 골라서 여는 중립적 대조 정보로만.
- 기각은 그 지적의 관련 입력과 검사 버전에 묶어 유지. 수정률 · 기각률 + 표본의 사람 판정으로 정확성을 확인한 뒤 표시 여부를 조정한다.

**5. 사람 감사 (둘이 따로 요구)**
- 변형형 키: 유형별 무작위 10문항(30문항)을 키 · 해설을 가리고 강사가 푼다. 오류 · 복수 정답 · 판정 불가를 적는다. 오류가 없어도 안전하다고 확정하지 않고 필요한 정밀도에 따라 늘린다.
- 가림 풀이: **목표 수준 학생만**, 유형별 10문항, 3~5명으로 시작(탐색). 정답률이 우연(20%) 근처면 미판정으로 두고 늘린다. 우연을 뚜렷이 넘을 때만 «학생에게도 단서».

**6. 순서**: 지금 — 배부 안내 · 1 의 시안 준비 · 5 의 감사(기존 레시피 기준선)를 **병행**. 시안 승인 뒤 1 구현. 2 는 벤치로 재고 채택한 뒤 가림 풀이를 한 번 더. 3 의 거절 시 복사는 독립 진행. 4 다음에 3 의 선택 단추.

**소수 의견**(grok, 받아들이되 남김): 정답 번호 불일치는 즉시 차단이 어울린다 · 차이 구간이 0 일 때 엄격판을 남길 여지.

**협의 중 잰 것(정밀도 선행 측정)**: 쌓인 214세트 · 1,280문항에서 «해설 번호 불일치»는 **0건**(정밀도를 잴 표본이 없다 — 검사가 너그러운지는 사람 감사 때 같이 본다) · «모두 옳다» 0건 ·
«이스케이프 찌꺼기» 12건(4세트, 세 세트가 luna)이 **12건 모두 진짜**(발문에 글자 `\n\n` — 그대로 인쇄하면 학생 지면에 보인다). 영어 글에 글자 `\n` 이 정당하게 들 일이 없으니
막기보다 **받을 때 줄바꿈으로 고치는 것**이 낫다(제안 — 모양 받아 주기 `coerceEnglishDraftShape`).

### 12.9 §12.8 의 «바로 할 수 있는 것» (원장님 2026-09-30 «바로 할 수 있는 것부터 진행해»)

화면 · 지면이 안 바뀌는 넷: ⑴ 글자 `\n` 자동 고침 ⑵ 프롬프트 v4 두 판을 벤치로 재기 ⑶ 변형 문항끼리 누출 검사 로직 ⑷ ChatGPT 길의 고쳐 달라 요청문 로직.

**⑴ 글자 `\n` 자동 고침** — `coerceEnglishDraftShape` 가 지문 · 발문 · 보기 · 해설 · 근거 · 서술형 답의 글자 `\n` · `\r\n` 을 줄바꿈으로, `\t` 를 빈칸으로 받는다(`unescapeLiteralBreaks`).
세 길(서버 AI · ChatGPT 붙여넣기 · 고쳐 쓰기)이 다 이 함수를 지난다. 실제로 걸렸던 4세트 12건 → 0건, 검증 결과는 그대로.

**⑵ v4 — 재기 전에 적는 계획**(판정 코드는 `scripts/qa/english-bench/analyze-v4.ts`, 이 절과 같은 커밋)
- 판 셋: v3(얼린 `promptV3.ts`) · v4a 엄격판 · v4b 완화판(`promptV4.ts` — v3 에서 주제 · 내용 일치 유형 안내 두 줄만 갈아 끼움. 내용 일치 문장은 두 판이 같다).
- 지문: 개발에 안 쓴 새 지문 열둘(`tasksV4.ts` — 우리가 지은 글, 중3 · 고1 · 고2 각 넷). 원문 유지 · 주제 1 + 내용 일치 1.
- 생성: 제품과 같은 호출(`openai:gpt-6-luna@medium`). 채점관: codex gpt-6-astra · claude fable(grok 은 §12.7 과 같은 까닭으로 뺀다).
- 재는 것(문항마다 채점관 평균 → 지문마다 문항 평균): 지문 없이 푼 정답률(보기 순서 섞음) · 지문 보고 푼 정답 일치율 · 루브릭 네 축 평균(1~5). 검증기에 거절된 세트는 문항 지표에서 빼고 채택률로 따로 본다.
- 통과(판마다, 넷 다): 지문 없이 ≤ 40% · v3 와의 차이 95% 구간(지문 단위 부트스트랩)이 0 을 벗어남 · 지문 보고 풀기 하락 < 5%p · 루브릭 하락 < 0.3.
- 채택: 통과한 판만 후보 — 하나면 그 판 · 둘이면 지문 없이 푼 정답률이 낮은 쪽 · 두 판의 차이 구간이 0 을 포함하면 v4b · 없으면 v3 유지.

**⑵ v4 — 결과: 두 판 모두 탈락, v3 유지**

| 판 | 검증 통과 | 지문 없이(세트 문항을 같이 — 미리 적은 규칙) | 지문 보고 | 루브릭(1~5) |
|---|---:|---:|---:|---:|
| v3 | 12/12 | 100% | 100% | 4.00 |
| v4a 엄격판 | 12/12 | 100% | 100% | 3.96 |
| v4b 완화판 | 12/12 | 95.8% | 95.8% | 4.03 |

- 통과 조건 ①(40% 이하) · ②(v3 보다 뚜렷이 낮음)를 둘 다 못 넘었다 → **v3 유지**. 제품 프롬프트는 안 바꿨다.
- v4b 의 오답 둘은 같은 한 문항이고 **복수 정답**이었다(내용 일치에서 보기 둘이 다 지문과 일치 — 두 채점관이 지문을 보고도 다른 보기를 고르고 키를 «동등 정답»으로 표시). 보기를 비슷하게 맞추라고 조이자 나온 결함이다.
- 문장 수준에서는 규칙이 먹혔다 — v4b 의 주제 보기는 다섯이 «The role of ○○ in urban cooling» 한 꼴이다. 그런데도 안 내려갔다.

**왜 안 내려갔나 — 사후 측정(채택 규칙 밖)**
- 가설 ①: 탐침이 세트의 문항을 **같이** 보여 줘 내용 일치의 보기가 주제의 답을 알려 준다 → 문항을 **하나씩 따로** 보여 주는 탐침(`judge.ts --kinds guessEach`)을 만들어 다시 쟀다: v3 48/48 · v4a 48/48 · v4b 46/48. **가설이 틀렸다** — 따로 보여 줘도 맞힌다(48건 중 45건에 «주어진 정보만으로는 풀 수 없음»을 표시하면서도).
- 가설 ②: 채점관 CLI 가 옆 폴더의 생성 파일을 읽었다 → 아니다(codex 는 셸 도구 차단 · 읽기 전용, claude 는 도구 없음).
- 가설 ③: 지문이 실제 현상(군중의 지혜 · 위약 · 철도 표준시)이라 AI 가 내용을 이미 안다 → **지어낸 내용의 지문 넷**(없는 마을 · 가게 · 학교 · 새 — `V4_FICTION_TASKS`)으로 쟀다.

| 지문 없이 · 문항 하나씩 | v3 | v4a | v4b |
|---|---:|---:|---:|
| 실제 현상을 다룬 지문 12 | 100% | 100% | 95.8% |
| 지어낸 내용의 지문 4(판정 16건씩) | 81% | 88% | 75% |

- 세상 지식이 한몫한다(100% → 75~88%). 그래도 우연(20%)보다 훨씬 높다 — 내용을 알 길이 없어도 정답 보기가 가려진다. 세 판 사이에는 뜻있는 차이가 없다.
- 🔴 앞서 §12.4 에 적은 «주제 · 내용 일치 116문항이 지문 없이 100%»는 **문항 결함만의 증거가 아니다** — 우리 표본 지문(창의성 · 수면)도 널리 알려진 내용이고, 최상위 AI 기준의 이 탐침은 천장에 붙어 있어 개선을 재는 자로 못 쓴다.
  오답 레시피를 더 만지는 것은 멈춘다. 학생에게도 단서인지는 §12.8 「5」의 **사람 가림 풀이**로만 알 수 있다.

**⑶ 변형 문항끼리의 누출 검사** — `src/lib/english/leak.ts` `findVariantLeaks`(시험 7 · 문맥 창을 없애는 변이에 3개 검출). 정답 자리에 앞뒤 문맥을 붙인 20자 이상 창이 다른 변형 문항의 지문에 그대로 있는가.
실측: 제품 경로(luna · v3) 15세트 중 **9세트(60%)** · v2 의 19개 모델 51세트 중 21세트(41%)에 누출 짝이 있다(어법의 원래 형태가 삽입 문항의 지문에 그대로 · 빈칸 원문이 어법 문항의 지문에 그대로).
→ 학생용을 독해용 · 변형용 묶음으로 가르는 것만으로는 부족하다. 화면에 어떻게 알릴지와 기본값은 시안에서(§12.8 「1」).

**⑷ ChatGPT 길의 «고쳐 달라 요청문»** — `buildChatgptFixRequest`(`chatgpt.ts`, 시험 6 · 품질 지적까지 싣는 변이에 2개 검출). 검증기가 거절했을 때만 글을 내고 통과면 null.
저장을 막은 사유 + 근거 자리 짚기(`englishRejectionReasons`) · 고치는 범위 · 조건 · 원문 · 붙여 넣었던 결과 · 답 형식. 막지 않는 품질 검사의 지적은 안 싣는다. 단추는 시안 뒤에.

### 12.10 검토 — 학생 정답지 사진을 올리면 AI 정답 분석 (원장님 2026-09-30 «돌릴 수 있을지 검토»)

**결론: 기술로는 된다. 다만 지금 저장소에서 «사진을 AI 로 보내는 배관»만 있고, 그 앞(어느 세트 · 어느 학생의 종이인가)과 뒤(영어 채점 결과를 담을 자리)는 없다.**
범위 결정이 먼저다 — PRD/TRD 는 «자동 채점»을 v2 로 미뤘고(01 L17 · 02 L18), §10.2 도 «학생 결과 기록»을 다음 판으로 두었다.

| 단계 | 있는 것 | 없는 것 |
|---|---|---|
| ① 사진을 AI 로 | 작업실 AI 배관(`src/lib/studio-ai/` — Gemini · Claude · OpenAI, base64 한 장, 본문 4.5MB 상한과 브라우저 축소 사다리, 재시도 · 동시성 · 오류 기록) | **답을 읽는 작업과 지시문** — 지금 여섯 작업은 전부 수학 문항 인식용이고 지시문이 «손글씨 · 동그라미 표시는 무시»다. 여러 장 · 판독 신뢰도 칸도 없다 |
| ② 어느 세트 · 어느 학생 | 학생 · 반 표(`Student` · `Class`), 지면의 손으로 쓰는 이름 줄 | **지면에 기계가 읽을 식별자가 없다**(세트 id · 판 · QR 0) · 객관식 **답 표기란이 없다**(보기 번호에 직접 표시) · 쪽 나눔이 세트마다 달라 문항 위치가 고정되지 않는다 · 이름 손글씨로 학생을 찾는 것은 금지(동명이인 — 스키마 주석) |
| ③ 채점 | 객관식 정답은 `"1"~"5"`, 서술형은 모범 답안 + 채점 기준(자유 글). 수학 쪽 순수 함수(`gradeAnswers` 등)와 «틀린 번호만» 입력 화면(`GradeSheet`) | 영어 세트는 **학생 · 반 · 제출 · 결과와 아무 관계가 없다**. 수학 채점 표는 `Problem`/`Test`/`Unit` 에 묶여 영어를 못 담는다. 영어 문항은 안정적 id 가 없고 고치면 옛 판이 안 남는다 → 인쇄 시점의 판을 붙잡아 둘 자리가 필요 · 서술형 자동 채점 코드 없음 |
| ④ 분석 | 수학의 단원 · 난이도 집계(`buildAnalysisReport`) | 영어의 축(유형 여섯 · 세트 · 기간)으로 모으는 집계와 화면 |
| ⑤ 보관 · 개인정보 | 파일은 Postgres `bytea`(영어 자료 4MB), 소유 범위 규칙(`ownerScope.ts`), 새 라우트의 `withErrorLog` 가드 | 채점용 사진을 받는 경로와 표 · **학생 답안 사진을 외부 AI 로 보내는 것에 대한 고지 · 보관 기한 · 삭제 규칙**(TRD 는 «이름만 수집 · 목적 달성 후 삭제») |

**판독 정확도가 갈리는 곳**
- 객관식: 답 표기란(번호 옆 ①~⑤ 칸, 또는 답 적는 칸)이 **한곳에 모여** 있으면 읽기 쉽다. 지금처럼 본문의 보기에 동그라미 치는 방식은 읽을 수는 있어도 고친 표시 · 겹친 표시에서 틀린다.
- 서술형: 영어 손글씨 판독 + 채점 기준 대조. AI 가 «읽은 글»과 «요소별 점수 제안»까지는 낼 수 있으나 **확정은 교사가** 해야 한다(기준이 자유 글이라 경계가 모호).
- 그래서 어느 경우든 **AI 가 읽은 답을 표로 보여 주고 교사가 확인한 뒤 저장**하는 흐름이어야 한다 — 잘못 읽은 답이 그대로 성적이 되면 안 된다.

**비용 · 시간**: 사진 한 장당 비전 호출 한 번(수 원~수십 원, 수 초~수십 초). 비용은 문제가 아니고, 정확도와 개인정보가 문제다.

**권하는 순서**
0. **먼저 재 본다(제품 변경 없음)** — 원장님이 실제로 표시된 학생 시험지 2~3장을 찍어 주시면, 지금 지면 그대로에서 객관식 표시와 서술형 손글씨를 얼마나 맞게 읽는지 모델 셋(Gemini · Claude · GPT)으로 잰다. 이 숫자가 아래 설계를 정한다.
1. 지면: **답 표기란 + 세트 코드**(짧은 코드나 QR)를 학생용에 넣는다 — §12.8 「1」의 묶음 분리 시안과 **같이** 정한다(D-07, 실물 인쇄 검수).
2. 자리: 영어 제출 · 결과 표(세트의 그 판을 붙잡아 둠 · 학생 · 문항별 답/정오 · 사진은 보관 기한을 둠) — 마이그레이션은 원장님 승인 뒤.
3. 화면: 사진 올리기 → 학생 고르기(손글씨 이름으로 자동 매칭하지 않는다) → AI 가 읽은 답 표 → 교사 확인 · 고침 → 저장 → 유형별 정답률.
4. 서술형 AI 채점 제안은 그다음.
- AI 없이 가는 길도 있다: 수학처럼 **«틀린 번호만» 입력**. 세트가 여섯 문항이면 학생당 몇 초다. 사진 판독은 문항 · 학생 수가 많을 때 값을 한다.

**Wire 선택 — 3자 합의(2026-10-01, 원장님 «codex · grok 에게 같은 질문을 던지고 claude 와 함께 3자 합의 도출해서 진행할 것»)**
같은 질문(`docs/planning/tracks/reports/english-quality/consult-wire/brief-r1.md` — 리드의 권고는 뺐다)에 셋이 따로 답하고(Claude 의 답은 둘의 답을 보기 전에 적어 둠), 합의 초안 → 최종안. codex «예» · grok 은 가-1 의 문장 하나를 조건으로 — 그대로 넣어 닫았다.
Claude 가 물러선 곳 둘: 누출의 기본값(«알리기만» → **기본으로 갈라 놓는다** — 60% 세트에서 뜨는 알림은 읽히지 않는다) · 종이의 묶음 이름(«1차 · 2차» → **«문제 묶음 1»** — 차수 고사로 읽힌다).

- **가. 묶음을 짓는 규칙** — 묶음은 순서가 있는 목록이다. 독해 묶음(원 지문 + 주제 · 내용 일치 · 서술형)은 맨 뒤다. 변형 문항(어법 · 빈칸 · 삽입)은, 아직 묶이지 않은 것 가운데 **남은 변형 문항의 답을 담지 않은 것**을 다음 묶음으로 삼는 일을, 그렇게 묶을 것이 더 없거나 아래 순환만 남을 때까지 반복한다. 묶음을 나누는 이유는 이 순서뿐이다.
  표본: 묶음 1(3 · 4번) → 묶음 2(5번) → 묶음 3(원 지문 + 1 · 2 · 6번). 누출이 없으면 묶음 둘(변형 · 독해).
  서로의 답을 보여 주는 쌍(양방향)이나 순환은 **순서로 없앨 수 없다** — 나누어 두고 같은 줄에 그 사실을 적는다. 누출이 없을 때의 문구는 «검사에서 찾은 누출 없음»(안전 보증이 아니다).
- **나. 인쇄 화면** — 묶음 목록을 문항 · 쪽 수 · 순서와 함께(«묶음 1 · 변형 · 3~4번 · 1쪽»). 묶음을 **하나씩 골라** 미리 보고 뽑는다(한 묶음 = 한 인쇄 작업 — 양면으로 뽑아도 다른 묶음이 같은 종이에 안 붙고, 뒤 묶음은 고를 때만 종이가 된다). 처음 열리면 묶음 1. 교사용은 따로.
  합치기는 영향을 같은 줄에 먼저 보인 뒤에만(«5번을 묶음 1에 합치기 — 합치면 3 · 4번의 답이 5번의 지문에 보입니다»).
  배부 안내는 묶음 수만큼 잇고 매번 회수를 적는다(«묶음 1을 풀고 걷은 뒤 묶음 2를 나눠 줍니다. …») + «한꺼번에 주면 가른 효과가 없습니다».
- **다. 지면** — 학생 종이의 머리 딱지 **«문제 묶음 1 · 3~4번»**(화면과 번호가 같다) · 학생 종이에 운영 문장 없음 · 문항 번호는 세트 번호 그대로.
  교사용은 학생용 선택과 관계없이 그 세트의 **모든 문항** + 머리에 배부 순서와 «어느 문항의 답이 어느 문항에 보이는지».
  어법의 밑줄을 그린다(글자 `<u>` · `</u>` 표기만 · 다른 꺾쇠는 글자로 · ①~⑤ 는 선 밖 · 줄이 바뀌어도 이어짐 · 내림 글자와 안 겹치게 · 실물 확인). 어법 문항에서 짝이 안 맞거나 **밑줄 구간이 하나도 없으면** 그 세트의 학생용 인쇄를 막고 문항 번호를 알린다. 다른 유형에 섞인 꺾쇠는 글자로 찍고 경고만.
  답 표기란 · 세트 코드는 넣지 않는다(실제 사진으로 판독을 잰 뒤에).
- **라. 한계** — 가른 것은 «누출 해결»이 아니다. 걷지 않으면 소용없고(숙제), 바꿔 쓴 단서와 먼저 읽은 글의 기억은 못 막는다.
- **마. 기각** — B(한 번에 이어 뽑기 — 갈라 주지 않으면 지금과 같다 · 안내 쪽 한 장) · D(문항 한 장씩 — 종이 · 배부 횟수).
- **다음 단계(Hi-fi)에서 달리해 보일 것** — ⓐ 머리의 묶음 이름 · 수록 문항 · 쪽 번호의 배치 ⓑ 인쇄 화면에서 묶음 목록과 안내 · 누출 줄의 자리 ⓒ 밑줄이 두 줄에 걸친 어법 문항과 교사용 머리의 안내 줄. 글꼴 · 색은 지금 지면 그대로.

### 12.14 어휘 유형 — 읽기 검사 뒤 생성 (D-153, 2026-10-01)

### 13.3 바뀐 것 (코드)

- **계약** `ENGLISH_QUESTION_TYPES` 에 여섯을 더했다(앞선 일곱의 차례는 그대로 · «원문 복원» 앞). `ENGLISH_OPEN_TYPES` 에 다섯 · 새 상수 `ENGLISH_FOUR_CHOICE_TYPES`(«언급 없음») · `ENGLISH_SOURCE_PASSAGE_MIN`(20) · `ENGLISH_WORDS_MIN`(30). **데이터베이스 마이그레이션은 없다** — 유형 글자를 묶는 CHECK 가 없다(`types` · `questions` 는 jsonb 배열이기만 하면 된다).
- **검증기**(`validate.ts`): «언급 없음»은 보기 4개 또는 5개 · 정답 번호는 보기 수 안(«정답은 보기 번호 1~4 여야 합니다.»). 공통 빈칸은 발문에 빈칸(`____`)이 둘 이상, 단어 배열은 « / » 가 둘 이상 — 빈칸 추론의 빈칸 규칙과 같은 «문제용 표지» 규칙이다. 뜻을 재는 규칙(배열한 말이 답과 맞는가 · 다른 낱말이 빈칸에 들어맞는가)은 **넣지 않았다** — 보정 없이 막는 규칙으로 올리면 멀쩡한 세트를 버린다(교훈 2026-09-30).

- **누출 · 묶음**(`leak.ts` `VARIANT_TYPES`): 공통 빈칸 · 단어 배열은 **변형**이다(문장을 원 지문에서 가져오면 원 지문 상자가 답을 보여 주므로 같은 장에 찍으면 안 된다). 두 유형은 답의 자리를 정렬로 찾지 않는다 — 공통 빈칸은 빈칸에 답을 넣은 문장으로, 단어 배열은 답 문장으로 대조한다(§13.7 의 2 · 3). 해석 · 영영풀이 · 언급 없음 · 문장 전환은 원 지문을 보고 푸는 쪽이라 독해 묶음에 남는다.

### 13.8 사진에서 글 읽기 — 구현과 검토 (2026-10-06)

원장님이 Wire 를 두 번(«A 는 사진이 거대할 때 가려지지 않을까? A-B 적절하게 믹스» → 2차 «가 나란히»), Hi-fi 를 한 번(읽기 창 **H4** · 자료 줄 단추 **r2**) 고르셨다. 확정 사항은 05 §8.23.3.

**길** — 사진 자료 한 장을 «사진을 보는 모델»에 보내 인쇄된 글자를 옮겨 받고, 선생님이 사진과 견주어 고친 뒤 **글 자료 한 줄**로 저장한다(«통째로 읽고 지운다»). 읽은 글은 저장 전이다 — 저장은 지금 있던 자료 POST(JSON `{ name, content }`)다. 새 표 · 마이그레이션은 없다.

| 자리 | 한 것 |
|---|---|
| 계약 | `englishMaterialReadResponseSchema` — `{ data: { text } }`(자료 지문 상한 30,000자) |
| 라우트 | `POST /api/english/materials/{id}/read` — 세션 401 → 메뉴 403(**`english-school` 만** — 사진이 외부로 나가는 일이라 자료를 다루는 메뉴에만) → 같은 출처 403 → 없는 자료 404 → 남의 시험 403 → 사진이 아닌 자료 400 → 한 사람의 동시 읽기 상한 429 → 모델. `withErrorLog` · `englishRouteAllowed` 에 등록 |

운영에는 사진을 보는 키가 셋 다 있다(2026-10-06 Vercel 의 변수 **이름**만 확인 — `GEMINI_API_KEY` · `OPENAI_API_KEY` · `ANTHROPIC_API_KEY`). 그래서 손대지 않으면 Gemini 3.8 Flash 로 읽는다.

**실패는 까닭을 갈라 알린다** — 처음 판은 모든 실패가 «사진이 흐리거나 글자가 작을 수 있습니다»였다.

| 응답 | 때 | 문구 |
|---|---|---|
| 503 | 사진을 보는 키가 없다 · 상류가 키나 모델 이름을 거절(401 · 403 · 404) | «AI 연결이 설정되지 않았습니다.» |
| 503 | 상류가 바쁘다(5xx — 배관이 다시 해 본 뒤) | «AI 서버가 응답하지 않습니다. 잠시 후 다시 시도해 주세요.» |
| 429 | 상류의 사용량 한도(`Retry-After` 를 싣는다) | «AI 사용량 한도에 도달했습니다. 잠시 후 다시 시도해 주세요.» |
| 429 | 한 사람이 동시에 띄운 읽기가 둘을 넘는다 | «진행 중인 AI 작업이 끝나면 다시 시도해 주세요.» |
| 504 | 배관의 제한 시간(110초) | «AI 작업 시간이 초과되었습니다. 다시 시도해 주세요.» |
| 499 | 화면이 요청을 끊었다 | (본문 없음) |
| 502 | 모델이 사진을 거절 · 끝까지 쓰지 않음 · 글이 비었다 | «글을 읽지 못했습니다. 사진이 흐리거나 글자가 작을 수 있습니다. 다시 찍어 올리거나 지문을 직접 입력해 주세요.» |
| 500 | 그 밖의 예외(우리 쪽 결함) — 덮지 않고 던진다 | — |

모델이 왜 멈췄는지는 화면이 아니라 **오류 기록**에 남긴다(`noteErrorLog` — `kind: ai-rejected` · 까닭 원문). 대조(둘째 호출)가 실패하면 처음 읽은 글을 돌려준다 — 읽기는 성공이다.

**값이 드는 호출을 겹치거나 되풀이하지 않는다**
- 읽기 창이 띄우는 읽기는 한 번에 하나다 — 넘기거나 닫으면 읽던 요청을 끊는다(서버도 `request.signal` 을 모델 호출에 넘긴다). 끊긴 사진은 돌아오면 다시 읽는다.
- 읽어 둔 글은 자료 화면이 들고 있어(`readCache`) 창을 닫았다 열어도 같은 사진을 다시 읽지 않는다.
- 저장한 그대로면 다시 저장하지 않는다(같은 글 자료가 두 줄 되지 않게). 글이나 이름을 고친 채 넘기거나 닫으려 하면 먼저 묻는다.
- «올리고 읽기»로 연 창은 **방금 올린 그 사진 한 장만** 본다 — 화면은 새 자료를 맨 위에 올리므로, 전체를 넘겨 보게 두면 «저장하고 다음 사진»이 예전 사진을 읽으러 갔다.
- 서버는 한 사람의 동시 읽기를 둘로 막는다(작업실의 «한 사람 둘»과 같은 결 · 서버 한 대 안에서만 센다).

**창이 죽지 않는다** — 브라우저는 Esc 를 거듭 누르면 `cancel` 을 못 막고 창을 스스로 닫는다. 그때 바쁘거나 부모가 닫기를 받아들이지 않으면(저장하지 않은 글을 묻는 중) 창 틀이 **다시 연다**(`EnglishDialog.tsx` — 영어의 작은 창 전부에 걸린다). 전에는 닫힌 창이 상태만 남아 같은 줄의 «글 읽기»가 아무 일도 하지 않았다.
지금 보는 사진은 **자료 id** 로 기억한다 — 목록이 다시 와 차례가 바뀌어도 다른 사진으로 건너뛰지 않는다. 열려던 사진이 목록에 없으면 다른 사진을 대신 읽지 않고 닫는다.

**적대적 검토**(이 세션의 변경을 모르는 Claude · 커밋 `220de7586`) — 관문 · 누출 쪽은 깨끗했고(메뉴 · 소유 · 같은 출처 · 응답에 비밀 값 없음), 병합을 막을 것 하나(시험의 타입 오류)와 고칠 것 여덟을 받아 **전부 시험과 함께 고쳤다**: ① `vi.fn` 의 호출 인자 타입 ② 스스로 닫힌 창이 죽음 ③ 값 조절(동시 상한 · 끊기 · 읽어 둔 글 · 올리고 읽기의 범위 · 바이트 복사) ④ 오류 갈래와 기록 ⑤ 같은 탭을 다시 누르면 고른 파일이 지워짐 ⑥ 같은 글을 두 번 저장 ⑦ 사진을 차례로 기억 ⑧ 이름만 사진인 파일 ⑨ 이름만 고친 것은 묻지 않음. 고친 줄을 하나씩 되돌려 보아(변이 열넷) 새 시험이 **열넷 다** 무는 것을 확인했다.

**검증** — 영어 화면 · 라우트 · 뒷단 · 메뉴 · 울타리 · 오류 기록 전수 시험 통과. 타입 검사는 **고친 파일과 그 파일이 끌어오는 것만** 좁혀 돌렸다(전체 `npm run type-check` 는 기기 메모리가 모자라 이 묶음에서 돌리지 못했다 — 푸시 전 관문이 돌린다). 실제 브라우저로는 읽기 창의 치수(1080×690)만 봤다.

**남은 것**
- 🔴 **운영 API 로는 한 번도 읽히지 않았다**(유료라 묻고 돌린다). §13.9 의 수치는 구독 CLI 로 잰 것이다.
- **폰으로 찍은 사진은 4MB 를 넘기 쉽다** — 자료 상한(4MB · Vercel 본문 상한)에서 «4MB 이하의 파일만 올릴 수 있습니다»로 막힌다. 카카오톡으로 받은 사진(1 ~ 1.4MB)은 지난다. «올리고 읽기»에서 브라우저가 줄여 올리는 길은 만들지 않았다.
- 읽기에는 감사 기록(`recordAudit`)이 없다 — `/api/english/generate` 와 같다(작업실에는 있다). 실패만 오류 기록에 남는다.
- 30,000자를 넘는 글은 말없이 자른다 · 읽기 창은 넘길 때마다 사진을 다시 받는다 · 실패 알림과 사진 칸 사이의 여백 — 작은 것들.

- **표본**: 원장님이 주신 사진 11장 전부 — 학습지 다섯(1920×2560 · 빈칸과 표에 연필 · 펜 손글씨 · 동그라미 · 짝짓기 선) + 총괄 평가 시험지 여섯(1080×1440 · 2단 · 주황 펜 답과 필기).
- **읽히는 길**: 유료 API 가 아니라 로그인된 구독 CLI. Claude 는 `claude -p`(사진을 메시지에 바로 싣는다 · 도구 없음), Gemini 는 Antigravity CLI `agy -p`(에이전트의 파일 보기 도구로 사진을 연다 — 머리말 한 줄이 그 길을 시킨다). gemini CLI 의 구글 계정 로그인은 막혀 있다(«Antigravity 로 옮기라»는 오류).
- **기준 글**: 세 모델의 첫 회차를 낱말 단위로 대조해, **갈린 자리마다 사진을 원본 해상도로 오려 보고** 정했다. 읽는 차례가 둘 다 옳은 쪽(짝짓기 표 · 나란한 낱말표) 넷은 기준을 하나 더 둔다. 판정이 갈리는 글(쪽 번호 · 답 줄의 빈칸 · 인쇄된 화살표 · 가장자리에서 잘린 줄 · 손으로 매겨 복사한 번호)은 «있어도 없어도»다.
- **흠**: 큰 흠(인쇄된 낱말이 빠짐 · 손글씨 낱말이 섞임 · 오독 · 지어냄 · 자리 옮김 · 배열 문제의 «/») / 작은 흠(문장부호 · 빈칸 표시 · 괄호만 다름). «흠 없이 옮긴 쪽» = 큰 흠이 0인 쪽.
- 조합마다 2 ~ 3회차(22 ~ 33번 읽기). 제품 지시문과 잰 지시문이 **글자 그대로 같은지**는 `dump-prompt.ts` 로 뽑아 견줬다.

**읽은 것**

1. **물으신 둘은 비슷하다.** 시험지에서는 Gemini 3.8 Flash 가 거의 다 맞고(대조를 붙이면 18/18), Sonnet 5.5 는 한글 받침 오독(«강수량» → «장수량») · 배열 문제에 없는 «/» 같은 흠이 가끔 난다. 손글씨가 빈칸과 표를 채운 학습지는 둘 다 반 남짓이다.
2. **가장 덜 틀리는 것은 묻지 않으신 Opus 5.5 다** — 99번 읽어 98번을 흠 없이 옮겼고, 학습지도 다 맞혔다. 낮은 강도로도 같고(66번에 66번) 한 장 10 ~ 13초다.
3. 운영 서버의 작업실 목록에 있는 Claude(Opus 5 · Sonnet 4.6 · Haiku 4.5)는 **Gemini 3.8 Flash 보다 못하다.** Haiku 4.5 는 열한 장을 다 틀렸다.
4. 지시문을 조인 몫은 Gemini 에서 흠 없는 쪽 77% → 88%, 큰 흠 72곳(22번 읽기) → 8곳(33번)이다. 대부분은 **동그라미 친 낱말표의 뜻 칸이 통째로 빠지던 것**이 돌아온 몫이다(r1 은 «동그라미 낙서는 옮기지 않는다»였고, 모델 둘이 그것을 동그라미 친 인쇄 글자까지 빼는 것으로 읽었다). r2 는 틀을 뒤집었다 — «인쇄된 글자는 전부 옮기고, 손으로 써 넣은 것만 뺀다».
5. **남은 흠**(Gemini · r2 + 대조): 첫 글자만 인쇄된 빈칸에 손글씨가 들어찬 학습지 한 장에서 세 번에 두 번(«h____» 를 «hot____» 으로 · 첫 글자를 빠뜨림 — 서너 곳), 낱말표의 «삼림»을 «산림»으로(세 번에 두 번).

**그래서 정한 것**

- 지시문 **r2** · 대조(읽은 글을 같은 사진과 한 번 더 맞춰 보는 둘째 호출)는 **Gemini 일 때 기본 켬** · 기본 제공자는 지금처럼 **Gemini 3.8 Flash**(물으신 둘 가운데 시험지를 더 잘 읽고, 값이 가장 싸고, 운영 배관이 이미 쓰는 모델이다).
- **Opus 5.5 로 바꾸는 길은 운영 변수 하나다** — `ENGLISH_READ_VENDOR=anthropic`(코드를 다시 내보내지 않는다). 값은 한 장에 수십 원쯤이다(2026-10-06 가격표 — 입력 100만 토큰 4달러 · 출력 20달러. 한 장이 입력 3 ~ 6천 · 출력 1천 토큰쯤). Gemini Flash 의 스무 배 안팎이다.
  🔴 **운영 API 로는 한 번도 부르지 않았다.** Opus 5.5 는 생각이 늘 켜져 있어 `output_config.effort: "low"` 로 부르게 했다(공식 문서 기준 — temperature 는 같이 보내지 않는다). 바꾸기 전에 한 장 읽혀 본다.

**이 수치가 말하지 못하는 것**

- 🔴 **구독 CLI 다** — 운영 API 와 사진을 싣는 길이 다르다(Gemini 는 에이전트의 파일 보기 도구로 들어가고, 13,000 토큰짜리 에이전트 지시문이 앞에 붙는다). **걸린 시간은 특히 그렇다** — Gemini 의 45 ~ 110초는 에이전트가 두 번 오가는 시간이다(운영 API 의 Flash LOW 는 다른 작업에서 4 ~ 7초였다 — 도형 사양 · 2026-09-18).
- 표본은 **한 학교 · 한 학생의 자료 11장**이다. 학습지 다섯 장의 수치는 «이런 종이에서 약하다»까지만 말한다.
- 기준 글은 세 모델이 갈린 자리만 사진과 맞췄다 — **셋이 똑같이 틀린 자리는 못 잡는다.** 판정은 이 세션(Claude)이 사진을 보고 했다.
- 조합마다 서른 번 남짓이라 **몇 쪽 차이는 회차 변동 안**이다(같은 Sonnet 조합이 82%와 73%를 오갔다). 말할 수 있는 것은 큰 차이뿐이다 — Opus 5.5 가 나머지보다 훨씬 낫다 · Haiku 4.5 와 Sonnet 4.6 은 훨씬 못하다 · Gemini 의 뜻 칸 누락이 r2 에서 사라졌다(세 번에 세 번 → 한 낱말).

**다시 재려면**

```bash
node --import tsx scripts/qa/english-read-bench/dump-prompt.ts <폴더>          # 제품 지시문을 파일로
node scripts/qa/english-read-bench/run.mjs --photos <사진 폴더> --out <결과 폴더> \
  --prompt <폴더>/read.txt [--verify <폴더>/verify.txt] --tag <판 이름> --arms gemini-low,opus-low --run 1
node scripts/qa/english-read-bench/matrix.mjs <결과 폴더>                       # 쪽 × 조합 표
node scripts/qa/english-read-bench/score.mjs <결과 폴더> --detail <조합>/<회차>  # 어긋난 자리
```

기준 글(`<결과 폴더>/ref/`)은 보관 폴더의 것을 쓴다. 새 사진을 더하면 `mkref.mjs` 로 기준을 만들고, 갈린 자리는 `crop.mjs` 로 오려 사진과 맞춘다. 🔴 워크트리(정션 `node_modules`)에서는 `--import tsx` 가 안 돈다 — 본 저장소 폴더에서 돌린다.
