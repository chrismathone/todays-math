# 수학 문제은행 보강 계획

작성: Codex · 2026-10-18 · 판본 R1 · 상태: **Claude 승인 대기**.

사용자 지시: 「보강 계획세우고 클로드한테 승인 후 진행」.
이 계획의 문항 제작·생성기 구현·공유 DB 적재는 Claude의 명시적 계획 승인 후 시작한다.
승인은 검토한 계획 파일의 SHA-256과 연결한다. 수정 요청은 승인으로 취급하지 않는다.

## 1. 출발점과 목표

[전수 수량 점검](../../reports/problem-bank-reinforcement-20261018/math-capacity.md) 기준
출제 가능 115,383행, 초3~~중3 360차시 모두 기본 8~~10문항을 구성한다.
따라서 전체 행 수를 목표 없이 늘리지 않고 반복 여유·풀이 유형·서술형을 보강한다.
고등 54차시의 기본 8문항 미달은 현재 일반 출제 지원 범위 밖의 확장 준비로 분리한다.

이 계획의 **이번 실행 범위는 1차 한 묶음**이다. 아래 후속 로드맵 전체가 끝났다고 보고하지 않는다.
1차 결과를 재측정하고 내용 검토에서 통과한 것만 적재한다. 부족한 수를 맞추기 위한
문항류 키 바꾸기·난이도 이름 바꾸기·선택지 형식 복제는 하지 않는다.

| 작업               | 1차 제작 범위                                          | 정량 완료 기준                                                   |
| ------------------ | ------------------------------------------------------ | ---------------------------------------------------------------- |
| A. 초4 반복 공급   | 4차시에 새 문형 9개, 문형당 서로 다른 발문 3개 이상    | 네 차시 모두 같은 문항류 1개/장, 고유 발문 8개×5회 용량 ≥40      |
| B. 중3 유형 다양성 | 4차시에 새 유형 각 3개, 유형당 서로 다른 발문 3개 이상 | 차시별 기존과 실질적으로 다른 문항류 +3, 기존 11개에서 최소 14개 |
| C. 본래 서술형     | 6개 풀이 유형 × 변형 2개 = 12문항                      | 초4 6개·중3 6개, 독립 풀이·부분점수 기준·표시 검증 12/12 통과    |

A와 B는 단답형이 기본이며 기존 객관식 파생이 유효한 경우에만 함께 저장한다.
저장 상한은 A 54행 + B 72행 + C 12행 = **138행**이다.
새 내용은 최소 75개(27+36+12), 새 문항류는 최소 27개(9+12+6)를 목표로 한다.
이는 1차 제작 목표이며 최종 적재 수는 검토·중복·멱등성 검사 결과로 확정한다.
객관식 파생이 불가능하면 사유를 기록하고 단답형만 적재해도 된다.
유형 설계가 기존과 같은 경우 해당 신규 키를 거부하고 설계를 보완한다.

native 서술형 등록/생성/적재/미적재 검사/갱신이 같은 계약을 쓰도록 필요한 최소 연결을 만든다.
일반 단답·객관식 `expandFamily`를 우회해 서술형을 복제하는 길을 만들지 않는다.

## 5. 역할과 승인 순서

1. **Codex(root):** 이 계획과 기준 수치·완료 조건을 작성한다.
2. **Claude:** 계획 파일과 현재 소스를 독립 검토하고 `approved` / `changes_requested` / `blocked` 중
   하나를 서면으로 남긴다. 계획 SHA-256, 허용 범위, 필수 조건, 의견 근거를 JSON과 Markdown으로 기록한다.
3. `approved`이고 SHA가 일치할 때만 **Codex A/B/C 독립 Orca 작업 세션**을 시작한다.
4. Codex 작업자는 새 문형 설계표, 실제 문항, 독립 검산, 회귀 검사와 원장용 메타데이터를 만든다.
   작업자는 공유 DB를 쓰거나 다른 작업자의 파일을 수정하지 않는다.
5. 통합 후 **Claude가 실제 적재 후보 전부**의 내용과 채점 기준을 검토한다. 생성기 정답만 보고
   동의하지 않으며 가능한 경우 정답을 가린 문제를 직접 풀어 결과를 대조한다.
6. 내용·계약·표시·회귀 검사와 배치 SHA 검토가 모두 통과하면 **root 한 곳에서만 적재**한다.
   미통과 문항은 격리하고, 수를 맞추려고 관문을 낮추지 않는다.
7. 적재 후 재조회·멱등성 드라이런·용량 재측정, 로컬 main 병합, 완료 세션 정리까지 수행한다.

서로 다른 유형인지는 등록 키의 개수로 증명하지 않는다. 원형/새 문형 대응표와 Claude 내용 검토를
근거로 함께 제시한다. 승인 후 계획의 범위나 관문을 완화해야 하면 변경한 판본을 다시 검토받는다.

## 6. 검증과 적재 조건

- 소스 기준: 기존 `load-engine-problems.ts`, `variants.ts`, `expandEngine.ts`,
  `checkUnloadedTypes.ts`, `refresh-engine-content.ts`와 저작 엔진을 우선 재사용한다.
  신규 경로가 필요하면 계약·적재·갱신·미적재 검사까지 연결하고 중복 구현을 피한다.
- 검산: 발문의 수치/조건을 다시 읽거나 생성기와 독립인 수학식·완전탐색으로 답과 풀이를 검증한다.
  각 새 유형에 대표/경계/퇴화 입력을 포함해 결정적 100씨앗 이상을 검사한다.
  테스트가 생성기의 `facts`나 정답을 정답 원천으로 그대로 쓰지 않게 한다.
- 형식: 원문 파서·정답 표시·선택지 5개/중복/동치·단위·조건의 충분성,
  실제 MarkdownRenderer와 renderMathHtml을 모두 확인한다. raw/red/merror 0을 요구한다.
- 지면: 최종 후보 75개 이상 전부를 기존 문제/인쇄 본문 컴포넌트로 렌더하고,
  새 도형 유형과 서술형 12개는 기존 A4 양식에서 실제 배치·잘림·답 노출을 확인한다.
  양식 자체는 수정하지 않는다. 실물 프린터 출력 여부와 파일/화면 검증을 구분해 보고한다.
- 적재: 저작한 deterministic 엔진 산출과 승인된 native 서술형만 다룬다.
  기존 문제 ID·본문·정답·학생 기록·교과서 원문·출처 연결을 제자리에서 변경하지 않는다.
  `ALLOW_SHARED_IMPORT=1`과 `--apply`가 모두 있어야 쓰고, 되돌리기 원장을 **먼저** 보관한다.
- 동시성: 대상 unit·family·externalId·본문/정답/해설 digest를 고정해 현재 상태를 다시 비교한다.
  동일 ID/외부 키가 다른 내용이면 덮어쓰지 않고 중단한다. 재실행은 신규 적재 0이어야 한다.
  다른 세션의 초5 그림 문형 적재와 main 변경을 보존하고 전체 증감량을 우리 작업 수로 돌리지 않는다.
- 승인/출제: 계획 승인만으로 내용이 검수됐다고 하지 않는다. Claude의 최종 배치 검토와
  독립 결정적 검산을 통과한 행만 기존 승인 정책대로 출제 자격을 갖게 한다.
- 완료 보고: 생성 시도/후보/통과/보류/신규 적재/기존 일치 건수를 각각 적고,
  차시별 고유 발문·문항류·난이도·서술형·8×5 반복 용량의 전후 수를 제시한다.

이번 보강을 전체 성취기준 대응이나 학습 효과의 실증으로 표현하지 않는다.

이 계획으로 완료 처리하지 않는다.
