# 수학 문제은행 보강 계획

작성: Codex · 2026-10-18 · 판본 R2. 승인 여부는 별도 Claude 검토 원장의 판정과 이 파일 SHA-256으로 확인한다.

사용자 지시: 「보강 계획세우고 클로드한테 승인 후 진행」.
이 계획의 문항 제작·생성기 구현·공유 DB 적재는 Claude의 명시적 계획 승인 후 시작한다.
승인은 검토한 계획 파일의 SHA-256과 연결한다. 수정 요청은 승인으로 취급하지 않는다.

## 1. 출발점과 목표

[전수 수량 점검](../../reports/problem-bank-reinforcement-20261018/math-capacity.md) 기준
그 측정 시점에 출제 가능 115,383행, 초3부터 중3까지 360차시 모두 기본 8~10문항을 구성한다.
따라서 전체 행 수를 목표 없이 늘리지 않고 반복 여유·풀이 유형·서술형을 보강한다.
고등 54차시의 기본 8문항 미달은 현재 일반 출제 지원 범위 밖의 확장 준비로 분리한다.

이 계획의 **이번 실행 범위는 1차 한 묶음**이다. 아래 후속 로드맵 전체가 끝났다고 보고하지 않는다.
1차 결과를 재측정하고 내용 검토에서 통과한 것만 적재한다. 부족한 수를 맞추기 위한
문항류 키 바꾸기·난이도 이름 바꾸기·선택지 형식 복제는 하지 않는다.

| 작업               | 1차 제작 범위                                          | 정량 완료 기준                                                   |
| ------------------ | ------------------------------------------------------ | ---------------------------------------------------------------- |
| A. 초4 반복 공급   | 4차시에 새 문형 9개, 문형당 서로 다른 발문 3개 이상    | 네 차시 모두 같은 문항류 1개/장, 고유 발문 8개×5회 용량 ≥40      |
| B. 중3 유형 다양성 | 4차시에 새 유형 각 3개, 유형당 서로 다른 발문 3개 이상 | 차시별 기존과 실질적으로 다른 문항류 +3, 기존 11개에서 최소 14개 |
| C. 본래 서술형     | 6개 풀이 유형 × 변형 2개 = 12문항                      | 초4 6개·중3 6개, 독립 풀이·부분점수 기준·표시 검증 12/12 통과    |

A와 B는 단답형이 기본이며 기존 객관식 파생이 유효한 경우에만 함께 저장한다.
저장 상한은 A 54행 + B 72행 + C 12행 = **138행**이다.
새 내용은 최소 75개(27+36+12), 새 문항류는 최소 27개(9+12+6)를 목표로 한다.
이는 1차 제작 목표이며 최종 적재 수는 검토·중복·멱등성 검사 결과로 확정한다.
객관식 파생이 불가능하면 사유를 기록하고 단답형만 적재해도 된다.
유형 설계가 기존과 같은 경우 해당 신규 키를 거부하고 설계를 보완한다.

독립 풀이 검산과 실제 파서 기준의 발문·그림 중복 제거 후 반복 용량을 다시 계산한다.
기본 8문항 난이도 배분을 대체 없이 채우는 기존 성질을 보존한다.

기본 수준 유형을 우선하되, 특정 난이도 슬롯을 채우기 위해 개념 판단을 연산으로 표시하지 않는다.
현재 차시별 교육과정 안에서 풀 수 있고 조건과 정답이 유일한 문항을 만든다.

이 넷은 수·대수·상황 모델링·자료 판단을 한 묶음에서 검증하고 서술형 C와 세 차시를
함께 검토할 수 있어 골랐다. 문항류 10개인 `원과 현`·`이차함수의 최댓값과 최솟값`보다
긴급한 차시라고 단정한 선정이 아니다. 새로운 중3 도형/함수 그림 엔진을 열지 않는 1차의 범위다.
각 새 유형의 실제 난이도를 설계표에 기록한다. 대체 없는 기본 배분 충족 수는 현재 6·6·6·7/8이며
전후를 관측해 보고하되 슬롯을 채우는 수치 목표로 삼지 않는다.

중등 전체 20문항 비교에서의 문항류 부족은 167자리, 중3의 몫은 141자리다.
이번 +12유형은 그 전체 부족을 해소하지 않는다. 20문항은 비교 시나리오이며 제품 기본값으로
바꾸거나 모든 차시에 의무로 적용하지 않는다.

| ------------------------- | ------------------------------------------------------------------ | ------: |
| 초4 정삼각형의 성질       | 주어진 조건으로 길이·각을 판단하고 성질로 근거 설명                |       2 |

| 초4 사다리꼴              | 평행 조건을 읽어 분류하고 충분한 조건·반례를 설명                  |       2 |
| 중3 인수분해              | 잘못된 전개/인수분해의 오류를 찾고 올바른 식을 독립 검산           |       2 |

| 중3 대푯값과 산포도       | 자료 변화를 비교해 대푯값/산포도의 변화와 선택 근거 설명           |       2 |

처음부터 추론·근거·판단을 요구하는 문항으로 작성한다. 단답형 끝맺음만 바꾼 파생 서술형을
금지한 기존 결정과 `expandEngine.ts`의 금지를 유지한다.
채점 기준에는 독립적으로 평가할 근거·중간 과정·결론, 각 부분점수와 합계,
허용할 다른 풀이와 흔한 오류를 명시한다. 단순 풀이 줄 수로 서술형의 타당성을 판정하지 않는다.
부등호·도형 포함 관계·사다리꼴 정의의 애매함을 피하고, 필요하면 발문 안에서 사용할 정의를 명시한다.

현재 `Problem`의 `questionType`, `problemType`, `content`, `answer`, `solution`으로 표현한다.
부분점수 기준은 저작 데이터에 구조화하고 교사용 해설에 함께 보관한다.
기준의 모양은 `criterionId / 기대 근거·과정 / 부분점수 / 허용할 다른 풀이 / 오류`이며 총점을 함께 둔다.
`solution`에는 모범 풀이 뒤 `채점 기준` 절로 직렬화한다. 학생용 질문/인쇄 컴포넌트에
실제 후보의 정답·해설을 포함한 입력을 전달해도 `solution`·채점 기준이 출력되지 않는지 검사한다.
테스트에서는 교사용 `solution`에만 둔 고유 표식이 학생 DOM에 없고 교사 DOM에는 있는지도 확인한다.
새 DB 표·자동 서술형 채점·학생 점수 갱신·UI/인쇄 양식 변경은 하지 않는다.
native 서술형의 정체성은 `familyKey = native-desc:<definitionId>`,
`externalId = engine-native-desc:<definitionId>|s<seed>|v<variant>`로 고정한다.
`definitionId`는 판본을 포함한 고유 ASCII 키로 최대 64자이며, 학년·차시 대응은 등록부에서 정한다.
`elem:`·`mid:`와 분리해 기존 파생 서술형 삭제 쿼리의 대상이 되지 않음을 회귀 검사로 고정한다.
native 서술형 등록/생성/적재/미적재 검사/갱신/되돌리기가 같은 exact-key 계약을 쓰도록 최소 연결한다.
`checkUnloadedTypes.ts`는 이를 별도 부류로 세고, `refresh-engine-content.ts`는 동일 target 생성 함수를
호출해 현재 배치 계획으로 재생성·대조한다. 이번 실행에서는 기존 행에 refresh 쓰기를 하지 않는다.
되돌리기는 새 `engine-native-desc:` 접두사를 정확히 허용하고 아래 참조 보호 조건을 적용한다.
일반 단답·객관식 `expandFamily`를 우회해 서술형을 복제하는 길을 만들지 않는다.

## 5. 역할과 승인 순서

1. **Codex(root):** 이 계획과 기준 수치·완료 조건을 작성한다.
2. **Claude:** 계획 파일과 현재 소스를 독립 검토하고 `approved` / `changes_requested` / `blocked` 중
   하나를 서면으로 남긴다. 계획 SHA-256, 허용 범위, 필수 조건, 의견 근거를 JSON과 Markdown으로 기록한다.
3. `approved`이고 SHA가 일치할 때만 **Codex A/B/C 독립 Orca 작업 세션**을 시작한다.
4. Codex 작업자는 새 문형 설계표, 실제 문항, 독립 검산, 회귀 검사와 원장용 메타데이터를 만든다.
   작업자는 공유 DB를 쓰거나 다른 작업자의 파일을 수정하지 않는다.
5. 통합 후 **Claude가 실제 적재 후보 전부**의 내용과 채점 기준을 검토한다. 생성기 정답만 보고
   동의하지 않으며 가능한 경우 정답을 가린 문제를 직접 풀어 결과를 대조한다.
6. 내용·계약·표시·회귀 검사와 배치 SHA 검토가 모두 통과하면 **root 한 곳에서만 적재**한다.
   미통과 문항은 격리하고, 수를 맞추려고 관문을 낮추지 않는다.
7. 적재 후 재조회·멱등성 드라이런·용량 재측정, 로컬 main 병합, 완료 세션 정리까지 수행한다.

서로 다른 유형인지는 등록 키의 개수로 증명하지 않는다. 원형/새 문형 대응표와 Claude 내용 검토를
근거로 함께 제시한다. 승인 후 계획의 범위나 관문을 완화해야 하면 변경한 판본을 다시 검토받는다.

## 6. 검증과 적재 조건

- 소스 기준: 기존 `load-engine-problems.ts`, `variants.ts`, `expandEngine.ts`,
  `checkUnloadedTypes.ts`, `refresh-engine-content.ts`와 저작 엔진을 우선 재사용한다.
  신규 경로가 필요하면 계약·적재·갱신·미적재 검사까지 연결하고 중복 구현을 피한다.
- 검산: 발문의 수치/조건을 다시 읽거나 생성기와 독립인 수학식·완전탐색으로 답과 풀이를 검증한다.
  각 새 유형에 대표/경계/퇴화 입력을 포함해 결정적 100씨앗 이상을 검사한다.
  테스트가 생성기의 `facts`나 정답을 정답 원천으로 그대로 쓰지 않게 한다.
- 형식: 원문 파서·정답 표시·선택지 5개/중복/동치·단위·조건의 충분성,
  실제 MarkdownRenderer와 renderMathHtml을 모두 확인한다. raw/red/merror 0을 요구한다.
- 지면: 최종 후보 75개 이상 전부를 기존 문제/인쇄 본문 컴포넌트로 렌더하고,
  새 도형 유형과 서술형 12개는 기존 A4 양식에서 실제 배치·잘림·답 노출을 확인한다.
  양식 자체는 수정하지 않는다. 실물 프린터 출력 여부와 파일/화면 검증을 구분해 보고한다.
  새 도형 문형과 서술형의 실물 확인은 기존 `/dev/print-check` 등록부에 `대기`로 남긴다.
  실제 실물 검수가 없으면 `통과`로 올리지 않고 완료 보고에서도 별도 대기로 표시한다.
- 적재: 저작한 deterministic 엔진 산출과 승인된 native 서술형만 다룬다.
  기존 문제 ID·본문·정답·학생 기록·교과서 원문·출처 연결을 제자리에서 변경하지 않는다.
  `ALLOW_SHARED_IMPORT=1`과 `--apply`가 모두 있어야 쓰고, 되돌리기 원장을 **먼저** 보관한다.
- 동시성: 대상 unit·family·externalId·본문/정답/해설 digest를 고정해 현재 상태를 다시 비교한다.
  동일 ID/외부 키가 다른 내용이면 덮어쓰지 않고 중단한다. 재실행은 신규 적재 0이어야 한다.
  다른 세션의 초5 그림 문형 적재와 main 변경을 보존하고 전체 증감량을 우리 작업 수로 돌리지 않는다.
- 승인/출제: 계획 승인만으로 내용이 검수됐다고 하지 않는다. Claude의 최종 배치 검토와
  독립 결정적 검산을 통과한 행만 기존 승인 정책대로 출제 자격을 갖게 한다.
- 완료 보고: 생성 시도/후보/통과/보류/신규 적재/기존 일치 건수를 각각 적고,
  차시별 고유 발문·문항류·난이도·서술형·8×5 반복 용량의 전후 수를 제시한다.

### 6.1 R1 검토에서 요구한 여섯 적재 관문

[Claude R1 검토](reports/math-bank-reinforcement-20261018/claude-plan-review-r1.md)의
`R2-1`부터 `R2-6`을 아래 조건으로 반영한다. **이 성질들이 기존 적재기에 이미 있다는 뜻이 아니다.**
승인 뒤 필요한 최소 기능과 테스트를 구현하고, root는 구현·검증 완료 전 DB에 쓰지 않는다.

1. **새 키만 선택(R2-1).** 초등 `formIds`와 중등 `typeKeys` 또는 동일 효과의 명시적인
   frozen allowlist로 이번 새 문형/유형만 선택한다. 빠진 키·빈 목록·중복·모르는 키는 중단한다.
   기존 계획에서 선택자를 생략한 동작은 보존한다. 적재 직전 드라이런에서 기존 문항류에
   추가할 행 0, 새 키 이외 행 0, 총 적재 후보 ≤138임을 확인한다.
2. **서술형 정체성과 호환(R2-2).** §4의 `native-desc:` / `engine-native-desc:`를 정본으로 삼는다.
   등록·생성·적재·미적재 계수·갱신·되돌리기가 같은 키 생성/해석 함수를 사용한다.
   기존 `delete-derived-descriptive.ts`의 SQL 조건에 안 잡힘, 되돌리기 접두사 허용,
   미적재 여부·갱신의 키 왕복을 테스트한다. 기존 네 종류 엔진의 정체성과 동작은 보존한다.
3. **같은 외부 키의 내용 대조(R2-3).** 이미 있는 `externalId`도 조용히 건너뛰지 않는다.
   기존 행의 `unitId`, `familyKey`, `questionType`, `difficulty`와 본문·정답·해설·실제 SVG digest를
   다시 만든 후보와 비교한다. 불일치가 하나라도 있으면 **모든 쓰기 전에 중단**하며 덮어쓰지 않는다.
   이 비교를 통과한 뒤 신규 0인 경우에만 멱등성을 확인했다고 보고한다.
4. **쓰기 전 원장(R2-4).** 적재할 모든 외부 키·내용 digest·계획/소스 근거를 담은 배치 목록과
   root가 선할당한 UUID를 `--apply` 전에 원장으로 보관·커밋한다. 기존 200행 단위 flush에 의존하지 않는다.
   중단 시 사전 원장의 외부 키/UUID로 현재 DB를 읽어 동일 digest인 본인 행만 복구 대상으로 삼는다.
   가능하면 배치 전체를 한 트랜잭션으로 쓰며, 실패 시 전부 rollback됨과 재실행을 검사한다.
   결과 원장은 앞 회차를 덮어쓰지 않고 덧붙인다.
5. **최종 승인과 실제 쓰기 묶기(R2-5).** 드라이런은 외부 키 정렬 순서의 JSON 배치 목록을 낸다.
   각 행에 `externalId / unitId / familyKey / questionType / difficulty / payloadSha256`을 포함한다.
   `payloadSha256`은 UTF-8 `JSON.stringify([content, answer, solution, figureSvg ?? null])`의 SHA-256이다.
   목록 파일의 실제 바이트 SHA-256을 배치 SHA로 정하고 Claude가 그 목록과 실제 후보/렌더를 검토한다.
   최종 승인 JSON에 배치 SHA를 기록한다. `--apply`는 계획·씨앗으로 다시 만든 행과 실제 SVG를 비교해
   키·메타데이터·digest·목록 SHA 하나라도 다르면 **쓰기 전에 거부**한다.
   승인된 목록과 다른 행이 추가되거나 빠진 경우도 거부한다.
6. **참조를 보존하는 되돌리기(R2-6).** 현행 스키마의 모든 문항 참조 관계를 확인한다.
   시험지·정답 기록·검수·신고·다른 문항의 원문 참조 등에 물린 행은 지우지 않는다.
   사전/결과 원장의 본인 ID·외부 키·내용 digest가 여전히 일치하는 참조 행은
   `directUseAllowed=false`로 잠그고, 참조 수·잠근 수·보류 수를 보고한다.
   참조가 없고 원장과 일치하는 본인 신규 행만 삭제할 수 있다. 내용이 달라진 행은 자동 변경하지 않는다.
   참조된 시험/학생/검수 기록을 cascade로 지우거나 전역 문항류 정리를 수행하지 않는다.

최종 후보와 실제 DB 기준선은 실행 직전에 다시 읽는다. 다른 세션의 초5 42행 적재 원장
`559774350`을 보존하며, 전역 증감 대신 이 배치의 실제 새 ID와 차시별 공급량으로 성과를 센다.
