## 3) 항목별 동의 여부

- **Wire A / H1 — 동의.** URL이 지점 맥락을 보존하고, 기존 계정 화면과 디자인 토큰을 그대로 재사용합니다. 레거시 URL 재이동과 소속 불일치 404 규칙도 명확합니다.
- **원장도 지점 체크리스트 준수 — 동의.** `isAdmin`의 메뉴 자동 부여만 제거하고 소유권 판정은 유지하는 구분이 맞습니다. 우회 지점 목록과 "단순 전체 치환 금지"가 명시돼 있고, 메뉴가 0개여도 관리·내 정보·로그아웃 경로가 유지됩니다.
- **개인 설정 보존 — 동의.** 1차에서 제가 낸 원장 개인 설정 초기화 제안은 철회합니다. `[]`가 전체 허용이고 원장 2명과 최고관리자 1명의 차단값이 모두 비어 있어 초기화할 이유가 없습니다. 강사 정책을 건드리지 않는다는 제약과도 맞습니다. 체크박스는 실제 결과를 표시하고 원본은 `configuredMenus`로 따로 보존하며, 메뉴를 바꾸지 않은 저장은 `menus`를 전송하지 않는다는 조정안도 수용합니다.
- **기존 관리 접근 범위 유지 — 동의.** 콘솔과 지점 메뉴 상한 변경은 `isSuperAdmin` 전용이고, 원장의 `/branch`는 현행 그대로입니다. `/admin` API를 원장에게 넓히지 않는 것이 명시된 범위와 일치합니다.
- **조건부 갱신·감사 — 동의.** `{id, menuRevision}` 조건부 갱신이 정확히 1행일 때만 성공하고, 누락은 400, 충돌은 409입니다. 감사 기록은 같은 트랜잭션이며 실패하면 롤백합니다. 이름만 바꾸는 PATCH는 revision과 무관합니다. 비밀번호 재발급에 `expectedUpdatedAt`·`expectedBranchId`를 추가하는 것도 타당합니다.
- **정확히 두 테이블의 RLS 폐쇄 — 동의.** `branch`·`user`에만 RLS를 켜고 `anon`·`authenticated` 권한을 회수하며, 새 정책은 열지 않습니다. 서버 역할의 소유·우회 여부를 사전 확인하고 로그인과 접근 거부를 사후 검증하는 절차가 포함돼 있어 충분합니다.
- **DB 우선·대상 지정 배포 — 동의.** 추가 컬럼이 기본값을 가져 구 코드와 호환됩니다. 관련 없는 미적용 migration은 체크섬 대조만 하고 실행하거나 조작하지 않는다는 조정안을 수용합니다.

## 비차단 실행 유의점 (승인 조건 아님)

- **재집계:** 익명 집계는 10월 3일 시점 값입니다. 계획에 적힌 대로 적용 직전에 원장 차단값을 다시 집계하고, 값이 생겼다면 초기화하지 말고 그대로 존중해야 합니다.
- **감사 테이블 구조:** `AccountAuditLog`가 대상 계정을 필수로 요구하면 지점 메뉴 변경을 기록할 수 없습니다. 구현 초기에 확인하고, 보정이 필요하면 같은 단일 migration 안에서 처리해야 합니다.
- **RLS 사전 확인:** 서버 역할이 테이블 소유자가 아니거나 `FORCE ROW LEVEL SECURITY`가 걸려 있으면 로그인이 전면 실패합니다. 확인 결과가 기대와 다르면 적용을 중단하고, 권한 회수의 되돌림 SQL을 미리 준비해 두어야 합니다.
- **문서 상태:** 문서 상단의 "초안 — 검토 중" 표기를 최종 합의 결과로 갱신하면 됩니다.
