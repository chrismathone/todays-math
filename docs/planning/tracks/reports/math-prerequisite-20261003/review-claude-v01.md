## 2. P0 — 구현 전에 반드시 풀 것

### P0-1. 다음 문제를 정하는 것은 «오늘의 탐험» 가드다 — 계획에 없다

근거:

- 모든 쓰기가 `updateExpedition(updateDailyJourney(...))` 를 지난다 — `serverStore.ts:87-93`.
- 초등 미션이 열려 있으면 새 세션은 `expeditionCourseRecommendation(previous)` 가 낸 소단원 · 모드와 **같아야** 한다. 다르면 `SrsConflict` — `expedition.ts:657-676`.
- 개념 · 중등 미션이 열려 있으면 `course` 를 바꾸는 쓰기는 전부 거절 — `expedition.ts:615-626`.
- 학생의 시작 요청은 몸통이 `z.strictObject({})` 다. 소단원을 학생이 고를 수 없고 서버 추천만 쓴다 — `courseRoutes.ts:77-98`.
- 추천이 미션 단원과 다른 탐험 단원을 가리키면 버리고 «오늘 시작한 학습의 남은 문제»로 바꾼다 — `expedition.ts:561-582`, `expeditionStart.ts:10-19`.

결과: P3 의 «기존 route/DTO/state 최소 확장»으로 선수 확인 세션을 따로 시작시키면 가드와 충돌한다. 가드를 우회하면 통합 탐험 결정(«학생당 열린 오늘의 탐험은 하나 · 설정 변경이나 다른 엔진 완료로 대체할 수 없다»)을 깬다.

해결안: 끼우는 자리를 **하나**로 정한다 — `courseSummary()` 의 추천 사슬(`courseAutomation.ts:299-319`). 순서는 `이어 풀기 → (꺼짐 · 오늘 목표 달성이면 없음) → 선수 확인 → 만기 복습 → 다음 학습`. 경로(`courseRoutes.ts`)와 가드(`expedition.ts:661`)가 같은 함수를 부르므로 둘이 저절로 일치한다. 새 끝점 · 새 세션 종류 · 새 미션 종류는 만들지 않는다. v1 은 선수 소단원이 목표와 **같은 탐험 단원**일 때만 낸다(§6). 다른 탐험 단원은 «선수 확인 날»이 필요하고 P1-6 이 먼저다.

시험:

- 선수 확인이 추천될 때 `startRecommendedCourse` 가 만든 세션이 `updateExpedition` 을 통과한다(경로와 가드의 일치).
- 미션 종류 셋(초등 · 중등 · 개념) × 선수 확인 조건 참: 중등 · 개념 미션 중에는 추천이 바뀌지 않는다.
- 변이: 추천 사슬에서 선수 가지를 가드 쪽에만 빼면 시험이 빨개진다.

### P0-3. `strictObject` — 새 칸을 쓰면 옛 코드가 그 학생을 못 읽는다

근거:

- `payloadSchema` 는 `z.strictObject` 이고 `version: z.literal(1)` — `serverState.ts:57-66`. 파싱이 실패하면 `SrsUnavailable`(«저장된 학습 기록을 확인해야 합니다») — `serverState.ts:162-169`.
- `storedCourseSchema` · 세션 · 문항 · 답안도 전부 `strictObject` — `courseAutomation.ts:48-63`, `math-srs/elementary/progress.ts:67-148`. 세션 모드는 `learn | review` 둘, 문항은 정확히 5.
- 반 현황은 반 학생의 줄을 모두 파싱한다. 한 줄이 실패하면 반 전체가 실패한다 — `courseServer.ts:159-166`.
- 워크트리 개발 서버와 운영이 같은 DB 를 본다(10-handoff · 24번 문서의 «공유 DB»).

결과: 계획 §4.2 의 «StudentSrsState 의 optional versioned 필드»를 쓰는 코드가 배포되거나 워크트리에서 실제 학생에게 한 번이라도 쓰면, 그 칸을 모르는 판(되돌린 배포 · 다른 워크트리)은 그 학생의 초등 · 중등 · 개념 · 탐험 기록을 전부 못 연다.

해결안: **v1 은 저장 꼴을 바꾸지 않는다.** 필요한 사실이 이미 저장돼 있다(§5 D2 · P1-3). 나중에 칸을 더해야 하면 두 번 배포한다 — 읽는 쪽(칸을 허용하되 아무도 안 씀)을 먼저 운영에 내고, 쓰는 쪽은 그 뒤. 되돌릴 수 있는 최저 판은 읽는 쪽이다. 워크트리에서는 실제 학생 줄에 쓰지 않는다.

시험:

- 저장 꼴 고정: 선수 확인을 거친 상태를 **현재 main 의** `parseSrsState` 로 파싱해 통과한다(새 키 0).
- 기존 픽스처(`mathExpeditionRecordCompat.test.ts` 의 옛 기록)가 그대로 읽힌다.

## 3. P1 — 계약을 확정하기 전에 정할 것

### P1-1. 단원 전체와 일부 유형 — 가장 작은 구조는 «저장하지 않는 것»

- 그래프 단원 하나는 소단원 여러 개다. E56-N03 = 초5 `1-4-1 ~ 1-4-5`, `1-5-1 ~ 1-5-4`(`units.ts:1671-1721`).
- 시드의 대단원이 그래프 단원 둘로 갈리는 곳이 있다. 초3 `1-6 분수와 소수` 의 `1-6-6 · 1-6-7` 은 소수(E34-N05), 나머지는 분수(E34-N04) — `units.ts:1012-1048`. 그래서 매핑 단위는 **소단원**이다.

해결안: 단원 수준 상태를 저장하지 않는다. 읽을 때 소단원 근거에서 뽑는다 — `{ unitId, mapped: n, observed: k, passedFresh: p, lastObservedAt }`. `demonstrated` 는 `p === n` 이고 매핑이 `partial: false` 일 때만. 화면에는 «9개 소단원 중 3개 확인 · 2개 통과» 같은 문장으로 싣는다(D-134 — 종합 점수 없음).

시험: 소단원 하나가 두 그래프 단원에 들어가지 않는다(분할). 일부만 통과한 단원이 `demonstrated` 가 아니다. `partial: true` 단원은 전부 통과해도 `demonstrated` 가 아니다.

| 기록 없음 | 기억 칸이 없다 | `unassessed`. 약점이 아니다 |
| 풀이 시간 | 초등 답안에 없다 | 쓰지 않는다 |
| `memories[].mastery` | 힌트 정답을 52로 당기는 지수 평균 — `courseAutomation.ts:688-697` | 근거로 읽지 않는다 · 확률로 보이지 않는다 |

**통과 기준을 새로 만들지 않는다.** «소단원 완료» 판정(`courseAutomation.ts:761-772` — 자동 채점 문항의 80% 이상을 스스로 맞음)을 함수로 뽑아 선수 확인의 통과에도 쓴다. 문턱이 둘이면 «완료했는데 확인은 실패»가 생긴다.

v1 에서 근거로 쓰지 않는 것: `TestResult` · `ProblemAnswer` · `AnalysisReport`(운영 0행, 서술형 60% · 추천 단원 60% 는 잠정 — `schema.prisma:1144, 1168-1169`), 중등 `memories`(다른 개념에 최대 0.2 를 나눠 주는 간접 근거 — `memory.ts:80-87`), 개념 카드 기록.

시험: 위 표의 줄마다 하나. 힌트 정답 5개로 통과하지 못한다. 재도전 정답이 판정을 바꾸지 않는다. 결시 · 기록 없음이 `needs_*` 가 되지 않는다.

### P1-3. 중복 · 재채점 — 누적하지 않으면 생기지 않는다

- 같은 요청의 재전송은 상태를 안 바꾸고, 다른 답으로 다시 내면 409 — `courseAutomation.ts:611-624`.
- 저장된 `correct` 는 파싱할 때마다 **현재 채점기로 다시 채점해** 대조한다 — `math-srs/elementary/progress.ts:121-134, 189-196`.

결과: 선수 판정을 읽을 때 뽑으면 중복 반영과 재채점 교체가 구조적으로 없다. 반대로 판정을 따로 저장해 두면 채점기가 바뀐 날 원본과 갈린다. 계획 §4.2 의 «이전 기여를 교체»는 v1 에서 필요 없는 장치다.

나중에 `TestResult` 를 근거로 들일 때의 열쇠만 적어 둔다: `(testId, studentId, problemId)`, 같은 시험의 여러 줄은 `takenAt` 최신 한 줄, `absent` 줄은 건너뛴다(`schema.prisma:1097-1117`).

시험: 같은 답을 두 번 보내도 추천이 같다. 추천은 `(상태, 지금)` 의 순수 함수다 — 같은 입력에 같은 출력.

### P1-4. 학습 요소 ID 가 순서에서 나온다

`M3-R02.t01` 은 `;` 목록의 자리다 — `math-graph.cjs:439-444`. 성취기준 대조가 끝나지 않았으니 목록은 바뀔 것이고, 가운데에 하나를 넣으면 뒤의 ID 가 전부 다른 요소를 가리킨다.

해결안: v1 은 학습 요소 ID 를 저장하지도, 매핑 열쇠로 쓰지도 않는다(화면 표시만). 단원 ID 는 덧붙이기 전용으로 고정한다. 그래프에 `graphVersion` 을 둔다 — 지금은 `schemaVersion` 뿐이다(617행).

시험: 단원 ID 100개의 목록을 고정한다(사라지거나 바뀌면 빨강). 그래프 내용의 해시를 고정해, 내용을 바꾸고 `graphVersion` 을 안 올리면 빨강.

### P1-5. CLI 가 조회만 해도 파일을 쓴다

- `--target` 만 줘도 현재 폴더에 JSON 과 Markdown 을 쓴다 — `math-graph.cjs:828-846`. 저장소 루트에서 돌리면 추적되지 않는 파일 둘이 main 에 생긴다.
- 모듈 최상위에서 바로 실행된다. 시험이 불러올 수 없다.
- `validation` 의 0 셋은 계산값이 아니라 글자다(669-671행). 앞의 `throw` 가 보장하지만, «0» 이 «셌더니 없다»인지 «안 셌다»인지 결과만 보고는 모른다.

해결안: `buildGraph()` 를 내보내고 `require.main === module` 일 때만 쓴다. `--out` 이 없으면 쓰지 않는다. 정본은 생성기의 데이터, JSON 은 커밋하는 파생물로 정하고(§5 D13), 시험이 `buildGraph()` 결과와 커밋된 JSON 의 일치를 본다.

시험: 중복 ID · 없는 ID · 자기 간선 · 순환을 시험이 직접 센다. 제외 11과목 이름이 `scope.excluded` 에 다 있고 어느 단원의 `course` 도 거기 없다. 소단원 간선이 0 이다.

### P1-6. 다른 탐험 단원의 만기 복습이 진도를 세울 수 있다 — **읽은 결과 · 미확인**

`courseSummary` 는 만기 복습을 다음 학습보다 먼저 추천한다(`courseAutomation.ts:307-318`). 탐험 쪽은 그 추천이 미션 단원 밖이면 버리고 미션 단원의 소단원을 **복습 모드**로 연다(`expeditionStart.ts:10-19`, `expedition.ts:572-581`). 복습 모드는 진도를 올리지 않는다(`courseAutomation.ts:761-763`). 읽은 대로라면 가장 오래된 만기가 다른 단원에 있는 동안 새 소단원이 `learn` 으로 열리지 않고, 그 만기는 풀리지도 않는다.

돌려 보지 않았다. 내가 놓친 분기가 있을 수 있다. 다만 선수 확인이 다른 탐험 단원에 기억을 만들면 바로 이 자리를 밟는다.

해결안: v1 은 같은 탐험 단원으로 좁혀 이 자리를 밟지 않는다. 다른 단원으로 넓히기 전에 «다른 단원 만기 + 다음 학습» 상태의 특성 시험을 먼저 쓴다. 지금 동작이 결함이면 이 트랙과 따로 알린다.

### P1-7. 화면과 권한

- 교사용 그래프 조회(완료 흐름 6)는 새 화면이다. D-07 에 따라 Wire 4~5안 → 원장님 선택 → Hi-fi → 구현. 계획 P4 에 이 단계가 없다.
- 학생이 보는 추천 이유는 이미 화면에 있는 문자열 칸이다 — `StudentReviewHome.tsx:196, 226`, `StudentCourseSrs.tsx:363`, 교사는 `CourseDashboard.tsx:845`. 새 컴포넌트 없이 문장 하나가 바뀐다. 그 문장은 원장님 확정이 필요하다(D-08).
- 새 교사 끝점은 `teacherGate`(`courseTeacherRoutes.ts:32-49`) · 학생 소유 검사 · `withErrorLog` 를 지나야 한다. 전수 가드가 있다(`errorLogRouteCoverage.test.ts`, `mathSrsTeacherBranchScope.test.ts`).

해결안: 완료 흐름 6 을 별도 트랙으로 뗀다(정적 데이터만 읽고 학생 기록과 무관). 첫 폐회로는 새 화면 없이 닫힌다.

### P1-8. 운영 자료가 없다

`student_srs_state` 1행 · 개념 카드 0건(27번 문서 132-134행), `test_result` 0행(23번 문서). 계획 §4.2 의 «실제 교사 라벨로 보정»은 지금 할 수 없다.

해결안: 수치는 이름 붙은 상수로 한 파일에 둔다(§5). «맞춘 값이 아니라 정한 값»이라고 적는다. 틀렸음을 아는 측정을 같이 적는다 — 확인 통과율이 절반을 넘으면 발동이 이르다, 확인 뒤 목표 통과율이 확인 없는 재시도보다 낮으면 해롭다.

### P1-9. 재사용 목록의 두 줄이 맞지 않는다

- `selectProblems.ts` 는 인쇄 시험지의 DB 문항 선정이다(자리 높이 판정 포함 — `selectProblems.ts:1-70`). 학생 연습의 공급기는 `generateCourseSession`(`math-srs/elementary/generator.ts:21-81`)과 `loadCourseBankCandidates`(`courseBank.ts:14-64`)다.
- `memory.ts` 는 중등 전용이다. 초등의 기억은 `courseAutomation.ts:676-743` 에 있다.

v0.2 의 §3 표를 고친다. 첫 경로는 `selectProblems.ts` 를 쓰지 않는다.

### P1-10. 은행 문항의 정체가 세션에 남지 않는다 (조정자 추가 요청 ①)

근거:

- `BankCourseCandidate` 는 `content · answer · solution · tier` 넷뿐이다. 조회가 문항 ID 와 문항류 열쇠를 읽지 않는다 — `courseBank.ts:8-11, 34-41`.
- 저장되는 문항 스키마에 원천을 적을 칸이 없다 — `math-srs/elementary/progress.ts:76-104`. 엔진에서 왔는지 은행에서 왔는지도 남지 않는다.
- 은행 문항은 `problemSeed % 후보 수` 로 고른다. 최근에 낸 것을 빼지 않는다 — `math-srs/elementary/generator.ts:41-50`.
- 엔진 문항은 소단원 × 갈래마다 생성기가 하나다(예: `fm221Calc` · `fm221Read` · `fm221Apply`). 씨앗을 바꾸면 같은 틀의 숫자가 바뀐다.

결과:

- 계획 §4.3 의 «동일 문항 · 동일 family 반복 노출 제한»은 은행 문항에 대해 ID 나 문항류로 구현할 수 없다.
- 목표로 복귀한 세션이 방금 틀린 바로 그 은행 문항을 다시 낼 수 있다. 그 정답은 «같은 문항 재시도»인데 독립 근거로 세어진다.
- v1 에서 «서로 다른 유형»으로 가를 수 있는 것은 갈래 셋(연산 · 기본 · 응용)까지다.

해결안(저장 꼴 불변):

- 반복은 **본문 글자**로 막는다. 은행 후보를 세션 생성에 넘기기 전에, 보존된 이력(세션 30개 · 최근 답안 100개)에 같은 `content` 가 있는 후보를 뺀다. 거르는 자리는 경로다(`courseRoutes.ts:85-97` 과 탐험 시작 경로) — 생성기는 건드리지 않는다.
- 후보가 다 걸러지면 지금처럼 엔진 문항으로 떨어진다. 규칙을 풀어 같은 문항을 내지 않는다.
- 문항류 중복 제한은 v1 에서 **주장하지 않는다.** 계획 문구를 «보존된 이력 안에서 같은 본문을 다시 내지 않는다»로 좁힌다. 원천 칸(`problemId` · `familyKey`)을 더하는 것은 저장 꼴 변경이라 P0-3 의 두 번 배포 뒤다.

시험: 이력에 있는 본문과 같은 은행 후보가 뽑히지 않는다. 후보가 전부 이력에 있으면 엔진 문항이 나온다. 목표 복귀 세션의 다섯 문항 본문이 직전 실패 세션과 겹치지 않는다.

## 6. 첫 폐회로 경로

**간선: E56-N03 분수 덧셈 · 뺄셈 → E56-N04 분수 곱셈 · 나눗셈** (`math-graph.cjs:152`)

| 같은 탐험 단원 | `g5-fractions` = `5-1-4` · `5-1-5` · `5-2-2` | `curriculumBridge.ts:23` |

이 경로를 고른 까닭:

- 문항이 AI 없이 엔진에서 나온다(`generateElementaryProblem`). 서버가 채점하고 학생별로 저장한다. 힌트 · 자기채점 · 재도전 기록이 이미 있다.
- 목표와 확인이 같은 탐험 단원이라 가드(P0-1)와 만기 문제(P1-6)를 밟지 않는다.
- 저장 꼴 · 계약 · 학생 화면 컴포넌트가 바뀌지 않는다. 바뀌는 것은 추천 사슬의 한 가지와 이유 문장 하나다.

흐름(하루 목표 10문항 = 세션 둘):

1. 첫날 — `5-2-2-1` 을 `learn` 으로 풀고 통과하지 못한다(실패 1). 둘째 세션은 지금처럼 같은 소단원.
2. 다음 날 — `5-2-2-1` 을 다시 `learn`, 또 통과하지 못한다(실패 2). **발동.**
3. 다음 세션 — `5-1-4-2` 확인 5문항. 이유 문장이 화면에 나온다.
4. 그 뒤 — `5-2-2-1` 을 새 문항으로 다시 `learn`. 통과하면 `completedSectionIds` 에 들어가고 끝.
5. 확인을 통과하지 못했으면 `5-1-4-2` 가 다음 날 만기 복습으로 한 번 더 오고, 그 뒤 목표로 돌아간다.

v1 에서 지원하지 않는다고 **표시**할 것: 같은 단원의 `6-1-1` · `6-2-1`(분수의 나눗셈 — 다른 탐험 단원), E56-N04 의 또 다른 선수 E34-N04(초3 · 초4 — 다른 탐험 단원), 중등 · 고등 전부, 초1 · 초2.

원장님께 여쭐 것 둘: ① 분수 곱셈의 확인 소단원으로 약분(`5-1-4-2`)이 맞는가 — 교과 판단이다 ② 학생에게 보일 이유 문장.

## 8. 회귀 시험

새로 쓰는 것(순수 함수 — `src/lib/math-prerequisite/`):

1. 학생 A 의 실패가 학생 B 의 추천을 바꾸지 않는다(함수가 한 학생의 상태만 받는다).
2. 실패 1개 → 발동 없음. 실패 2개 → 발동. 14일 밖의 실패는 세지 않는다.
3. 힌트 정답 · 자기채점 · 재도전 정답은 통과로 세지 않는다. 기록 없음은 약점이 아니다.
4. 확인 소단원을 14일 안에 푼 기록이 있으면 건너뛴다. 15일째에는 다시 후보다.
5. 하루에 확인 세션은 하나. 확인 2개 뒤에는 더 내지 않는다.
6. 확인이 끝나면 다음 추천이 목표의 `learn` 이고 `selectedSectionId` 가 그대로다.
7. 선수의 선수는 후보에 없다. `support` 간선은 후보를 만들지 않는다.
8. 환경변수가 꺼지면 추천 사슬이 지금과 글자까지 같다.
9. 이력이 30개에서 잘려도 확인이 되풀이되지 않는다.

기존 묶음에서 반드시 초록이어야 하는 것: `mathSrsElementaryCourse` · `mathSrsElementaryRoutes` · `mathSrsCourseServer` · `mathSrsCourseRoutes` · `elementaryCourseProgress` · `mathSrsDailyJourney` · `mathExpeditionJourney` · `mathExpeditionForecast` · `mathExpeditionRecordCompat` · `mathExplorersCurriculumBridge` · `mathSrsTeacherBranchScope` · `errorLogRouteCoverage` · `StudentCourseSrs` · `CourseDashboard`. 여기에 P0-1 의 가드 일치 시험, P0-3 의 저장 꼴 고정 시험, P1-5 의 그래프 시험을 더한다.

브라우저 검증: 학생 계정 둘로 로그인해 A 만 두 번 실패시킨다. A 에게만 확인 세션과 이유 문장이 뜨고, B 의 화면과 `revision` 이 그대로이고, A 가 확인 뒤 목표의 새 문항을 받는지 본다.
