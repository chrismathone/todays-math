# 학생별 선수학습 진단·맞춤 문제 제시 계획 — v0.1 (검토 전)

작성일: 2026-10-03
상태: 계획 전용. Codex·Grok·Claude가 동일 최종 개정안에 명시적으로 동의한 뒤 구현한다.
조정자/최종 구현 책임자: 현재 Codex 세션. 독립 검토자는 구현 파일을 변경하지 않는다.

## 1. 사용자 목적과 완료 조건

학생의 실제 풀이가 누적되면 부족할 가능성이 있는 단원을 찾고, 필요한 선수 단원을 확인하는 문제와 보충 문제를 제시한다. 보충 뒤에는 원래 목표 단원의 새 문제로 돌아와 개선을 확인한다.

예: 이차방정식 M3-R02를 반복해서 어려워하면 인수분해 M3-R01, 제곱근 M3-N01, 일차방정식 M1-R02 중 확인이 필요한 가까운 선수를 먼저 검사한다. 목표 단원의 오답을 모든 조상의 오답으로 복제하지 않는다.

완료 흐름:
1. 학생 A와 B의 풀이가 서로 섞이지 않고 서버에서 채점·저장된다.
2. A의 직접 풀이 근거로만 A의 측정 상태를 갱신한다.
3. A에게 목표 단원의 가까운 선수 확인 또는 보충 문제를 이유와 함께 제시한다.
4. 정답·힌트·재시도·서로 다른 유형의 결과를 구분한다.
5. 목표 단원으로 복귀하고 이후 정답이 상태에 반영되는 흐름이 실제 화면에서 검증된다.
6. 교사는 단원을 선택해 학습 요소, 직접 선수, 후속 단원, 도움 관계를 보고 학교급·학년군·과목·영역으로 검색·필터링한다.

## 2. 교육과정 범위와 불변 조건

유지: 초등·중학교 수학, 공통수학1·2, 기본수학1·2, 대수, 미적분Ⅰ·Ⅱ, 확률과 통계, 기하.
제외: 경제 수학, 인공지능 수학, 직무 수학, 수학과 문화, 실용 통계, 수학과제 탐구, 전문 수학, 이산 수학, 고급 대수, 고급 미적분, 고급 기하.

현재 저장된 math-graph.cjs는 이 제외를 반영한 100개 편집 단원 초안이다. 아직 실행·결과 생성은 하지 않았다. 실제 집계는 합의 후 실행 결과로 확정한다.

- units는 편집 단원, topics는 학습 요소 목록이다.
- prerequisite는 교육적 추론, support는 도움 관계, contains는 포함 관계다.
- courseRelations는 과목 순서·대체·권장 관계로 별도로 유지한다.
- 단원 간 관계를 소단원 전체의 관계로 확대하지 않는다.
- 학습 요소 순서와 DB Unit.orderIndex를 선수 간선으로 변환하지 않는다.
- 소단원 간 직접 선수 간선은 현재 없다.
- 성취기준 전수 대조는 미완료다. needsCurriculumAudit와 빈 achievementStandardIds를 유지한다.
- isOfficialEnrollmentRequirement는 false를 유지한다.
- 중학교 ID의 학년 배치 제안과 공식 학년군을 구별한다.
- 교육과정 정적 데이터와 화면 코드, 학생별 기록을 분리한다.

## 4. 제안 아키텍처

정적 그래프 → 명시적 단원/문항 매핑 → 직접 풀이 관찰 → 학생별 측정 상태 → 제한된 선수 확인 → 기존 문제 공급기 → 서버 채점·저장 → 원래 단원 재확인.

새 순수 로직은 src/lib/math-prerequisite/, API 계약은 src/contracts/mathPrerequisite.contract.ts에 둔다. 정적 JSON은 생성된 math_graph_2022.json을 단일 기준으로 사용하고, UI에는 필요한 DTO만 보낸다. 정확한 화면 진입점과 기존 학습 API의 연결 위치는 검토자의 저장소 조사 후 최종안에서 확정한다.

### 4.1 명시적 매핑과 공급 확인

- 그래프 ID, 기존 DB 단원 UUID, 초등 section ID, 중등 엔진 typeKey/ConceptId는 서로 다른 식별자다.
- grade/chapter/section 및 엔진 분류를 근거로 사람이 읽을 수 있는 명시적 매핑을 작성한다.
- 제목 유사도만으로 자동 확정하거나, 여러 의미가 섞인 단원을 임의로 하나에 매핑하지 않는다.
- 학습 요소 태그는 실제로 확인한 매핑이 있을 때만 붙인다. 없으면 단원 수준만 제공한다.
- 매핑 상태는 verified/ambiguous/unmapped, 문제 공급은 available/unavailable로 별도로 표현한다.
- 첫 폐회로는 실제 문제가 공급되는 좁은 경로를 선택한다. M3-R02 사례는 공급 검증 후 지원하거나, 지원되지 않음을 표시한다. 다른 단원으로 조용히 치환하지 않는다.
- 나머지 100개 단원은 그래프 조회가 가능하며, 검증된 경로부터 순차적으로 문제 제시를 확장한다.

### 4.2 직접 관찰과 학생 상태

관찰에는 원본 출처, 학생 ID, 사건/응답 ID와 개정, 문항/유형/단원 ID, 채점 결과, 힌트·재시도·자기채점 여부, 시간, 매핑 버전을 남긴다. 서버 채점값을 사용하며 학생이 보낸 correct/mastery는 신뢰하지 않는다.

- 중복 제출과 재생은 같은 관찰을 중복 반영하지 않는다.
- 수정 채점은 이전 기여를 교체한다. 무한 누적 ledger를 학생 payload에 넣지 않는다.
- 결시·풀이 전·미측정은 약점이나 0점으로 확정하지 않는다.
- 힌트 정답, 즉시 재시도 정답, 같은 유형의 숫자 바꾸기는 독립 숙달 근거와 구분한다.
- 시간은 보조 자료이며 느린 정답만으로 약점 판정을 내리지 않는다.
- 상태 예시: unassessed, needs_check, needs_practice, demonstrated. observed facts와 파생 추정을 구분한다.
- 단원 전체 demonstrated에는 여러 학습 요소/유형의 직접 근거가 필요하다. 소수 문항만으로 전체 단원 숙달을 주장하지 않는다.
- 초기 수치 기준은 정책 설정과 tests에 명시하고 실제 교사 라벨/관찰로 보정한다. 확률이라는 의미가 없는 휴리스틱 점수를 숙달 확률로 표시하지 않는다.
- 기존 기록에서 관찰을 만들 수 있는 범위를 먼저 정하고, StudentSrsState의 optional versioned 필드 또는 별도 파생 캐시 중 더 단순한 방식을 최종 합의한다. 기존 payload를 읽을 수 있어야 한다.

### 4.3 선수 확인·보충·복귀 정책

- 목표 단원의 반복 어려움은 가까운 직접 선수의 확인 후보를 만든다. 조상 전체를 취약으로 판정하지 않는다.
- CLI의 reviewCandidates는 전체 역추적 조회를 유지한다. 실제 출제는 그 목록을 한꺼번에 문제 세트로 변환하지 않는다.
- 가까운 선수부터 제한된 후보/문항 수로 확인한다. 깊이·세션 문제 수·하루 보충 예산·재검사 유예를 정책에 둔다.
- 충분한 직접 근거가 있는 단원은 건너뛴다. support는 선택적 도움이며 선수 확인을 강제하지 않는다.
- 선수 확인이 통과하면 새 변형 문제로 목표 단원에 복귀한다.
- 계속 실패하거나 근거/문항이 부족하면 이유를 표시하고 교사 확인 또는 목표 단원의 일반 연습으로 연결한다.
- 동일 문항·동일 family의 반복 노출을 제한하고, 난이도와 풀이 유형을 균형 있게 조합한다.
- 문제 공급이 부족해도 정책을 조용히 풀거나 승인되지 않은 문제를 사용하지 않는다.
- 추천 이유에 관찰한 어려움, 선택한 선수, 간선 이유, 자료 한계와 공급 상태를 표시한다.

### 4.4 TypeSafe/Jev 역할

산술, 정답 비교, 그래프 탐색, 숙달 집계, 예산·권한·공급 조건은 코드가 담당한다. Jev는 필요할 때 문항-학습 요소 의미 매핑 또는 학생 풀이 설명의 오류 유형 판정 후보를 좁히는 선택적 계층으로만 쓴다.

- 첫 구현의 결정적 폐회로는 외부 AI 호출 없이 동작해야 한다.
- 선택적 의미 판단은 기존 askJev를 재사용한다. no-match/uncertain 선택지를 포함한다.
- typed output와 confidence를 사실의 보증이나 학생 숙달도로 해석하지 않는다.
- 불확실하거나 실패·시한초과·키가 없는 경우 verified 매핑과 기존 학습 경로를 사용한다.
- 문항 태그 확정과 선수 간선 추가를 AI 응답으로 자동 수행하지 않는다.
- 실제 AI 통합이 필요해지는 단계에서 해당 primitive/API와 domain eval을 추가 검토한다.

참고로 읽은 공식 문서: [빌딩 가이드](https://docs.typesafe.ai/concepts/how-to-build-with-system-one), [confidence](https://docs.typesafe.ai/confidence), [entity alignment cookbook](https://docs.typesafe.ai/cookbooks/entity_alignment), [HTTP API](https://docs.typesafe.ai/api). 이 교육 도메인 적용안은 프로젝트 설계 제안이다.

## 5. 단계, 책임 범위, 검증

| 단계 | 결과 | 실행/수정 범위 | 통과 근거 |
|---|---|---|---|
| P0 | 제외 범위가 반영된 JSON·Markdown, 독립 CLI | math-graph.cjs, math_graph_2022.json, math_graph_2022.md | 중복/잘못된 ID/선수 순환 없음, 제외 과목 간선 없음, --target/--mastered/--out 동작 |
| P1 | 그래프 계약·조회·검증된 ID 매핑 | 계약, src/lib/math-prerequisite의 graph/mapping, 작성 데이터 | 지원/미지원과 ambiguous 구분, topic 간선 자동 생성 0, 그래프 버전 일치 |
| P2 | 학생별 직접 관찰·측정 상태·추천 엔진 | 순수 evidence/mastery/recommendation 로직 | 서로 다른 학생, 결시, 힌트, 재시도, 단일 오답, 부분 단원 커버리지, 신선도, 재채점, dedupe 테스트 |
| P3 | 기존 학습의 채점·저장과 연결 | 기존 route/DTO/state를 최소 확장 | CAS·기존 payload 호환·학생/교사 소유권·정답/다른 학생 기록 비노출 API 테스트 |
| P4 | 교사 그래프 조회와 학생 확인·보충·복귀 화면 | 기존 학습/교사 화면의 제한된 컴포넌트 | 검색/필터/단원 정보, 같은 학생별 실제 문제 흐름, 미지원 표시, 공급 부족 처리 브라우저 검증 |
| P5 | 회귀 검증·병합·정리 | 각 구현 worktree → main | 관련 테스트·type-check·lint·필요한 build, 기존 학습 동작 회귀 없음, 깨끗하고 병합된 Orca 세션 정리 |

P1과 P2는 확정 계약 이후 독립 worktree에서 병렬 진행한다. P3는 결과에 의존한다. UI는 확정 DTO와 공급 정책 이후 연결한다. 실제 단계별 구현 분할은 최종 합의안에서 파일 소유권까지 확정한다. main의 기존 미추적 자료는 변경하거나 함께 커밋하지 않는다.

새 DB 테이블/마이그레이션·대규모 문항 태그 변경은 필요성 확인 전 계획에 넣지 않는다. 운영 배포/기존 실사용 데이터 재작성은 이 계획의 로컬 구현 완료 조건과 별도로 다룬다.

## 6. 3자 합의 절차

1. Codex, Grok, Claude를 실제 Orca 리뷰 세션으로 분리한다. 세션은 계획만 검토하며 제품 코드를 수정하지 않는다.
2. 세 모델은 같은 v0.1을 독립 검토하고 approve / request_changes / reject, 중요도별 결함, 대안, 테스트, 첫 지원 경로를 보고한다.
3. 조정자가 차이를 결정표로 정리하고 계획을 개정한다. 동의하지 않은 쟁점은 합의된 것으로 표시하지 않는다.
4. 동일한 최종 개정안과 해시를 다시 보내 세 모델의 명시적 동의를 받는다.
5. 세 명 모두 동의하고 중대 미해결 사항이 없을 때 합의 기록을 작성하고 구현을 시작한다. 모델 실패·중단·무응답은 동의가 아니다.
6. 실행에 외부 상태/필수 정보가 부족하면 가능한 계획 검증을 마친 뒤 정확한 부족 정보를 사용자에게 요청한다.

## 7. 검토자에게 특히 묻는 것

- 기존 시스템을 재사용할 연결점과 예상 회귀는 무엇인가?
- 전체 단원 숙달과 일부 유형 숙달을 구분할 가장 작은 데이터 구조는?
- 실제 공급 가능한 첫 경로는 무엇이며 근거 파일은?
- 자기채점/힌트/즉시 재시도/채점 수정은 어떤 관찰로 보아야 하는가?
- 조상으로 계속 내려가는 보충 루프를 막고 목표로 돌아오는 규칙은?
- 별도 DB 테이블 없이 기존 학생 JSON 상태에 안전하게 저장할 수 있는가?
- 지원하지 않는 고등 단원까지 지원한다고 표시하지 않으려면 무엇을 검증해야 하는가?
- 계획에서 미확정인 부분 중 구현 전 반드시 결정해야 할 것은?
