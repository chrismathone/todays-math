**1. 우선 확인할 위험**

1) **높음 — 계수 호출부만 복원하면 500행씩 순차 왕복하는 읽기가 남는다.**

`src/lib/problem/questionProjection.ts:61` 이후는 메타데이터를 `skip/take=500`으로 끝까지 읽고, 미판정 본문도 500개씩 읽는다. 기준본의 같은 함수는 메타데이터를 한 번에 읽고 본문은 5,000 ID씩 읽었다. 따라서 `bankSourceQuestions.ts` 또는 전역 요약을 기존 `loadQuestionCandidates` 호출로 돌리는 것만으로는 “1차 전 코드 복원”이 완성되지 않는다.

리드 브리프의 118,166행에 현행 500행 반복을 적용하면 메타데이터 조회만 약 237회다. 이는 코드와 브리프에서 계산한 수이며 독립 실측값이 아니다. 공유 DB 왕복에서는 이 차이가 중요하다. 복원을 택하면 기존 계수용 읽기의 배치 방식까지 확인해야 한다. 그 과정에서 별도의 SQL 후보 ID 페이지 조회를 지우면 안 된다.

2) **높음 — 후보 ID 페이지 조회는 계수 함수가 채우는 형식 캐시에 의존한다.**

`src/lib/unifiedPreview.ts:597` 이후는 요청별 `cache`를 만들고, `loadQuestionCounts(listingWhere, tx, [], format, cache)`로 총수와 미판정 형식을 얻은 뒤 같은 캐시를 `questionPageSql`에 넘긴다. SQL은 `formatEvidenceSql`의 형식 증거와 기존 빠른 판정을 함께 사용한다. 전역 요약 캐시에는 이 요청별 형식 맵이 들어 있지 않다.

계수 경로를 바꾸더라도 좁혀진 후보 범위의 미판정 행을 판정하여 같은 맵을 채우는 과정은 필요하다. 이를 생략하면 실제 SQL에서 형식이 NULL인 문항이 일반 목록이나 형식 필터에서 빠질 수 있다. 반대로 이를 해결하려고 모든 후보 본문을 다시 Node로 가져오면 교체 최적화를 잃는다.

3) **높음 — 두 번째 집계를 없앤 보정은 각 bucket의 문항 합집합을 보존해야 한다.**

최초 열람본은 미판정 행이 하나라도 있으면 첫 SQL의 실제 계수 부분을 비우고 두 번째 전체 집계에 맡겼다. 이 상태에서는 JS의 재집계 호출만 삭제할 수 없었다. 이후 열람한 시안은 첫 집계 결과를 유지하고, 미판정 행이 속한 `question_id`의 알려진 형제까지 `touched`로 반환하여 기존 기여를 빼고 판정 후 기여를 더한다. 이 방향은 중복 보정 위험을 다루고 있다.

예를 들어 한 문항에 이미 사용 가능한 단답 표현과 본문 판정이 필요한 객관식 표현이 있으면, 후자가 사용 가능해져도 전체 `available`은 1이다. 객관식 가용량만 늘 수 있다. 같은 문항의 두 미판정 행이 같은 형식으로 판정돼도 해당 형식 수는 1이다. 이 관계는 전체뿐 아니라 단원·난이도·출처·책·자료 종류·자료·학년의 각 bucket에서 독립적으로 성립해야 한다. 부분 bucket 수를 더해 상위 합집합을 만들면 안 된다.

따라서 보정 입력에는 **동일한 필터 범위 안의 알려진 형제**가 필요하고, 범위 밖 형제를 가져와 수를 넓혀서도 안 된다. `held`, `available`, 가족 수 계산용 `rowCount`를 서로 구분해야 한다. 첫 집계 한 번이 공유 DB에서 여전히 느리면 브리프에 따라 복원하는 판단은 남아 있다.

4) **중간 — mock 시험만으로 형식 캐시 전달과 SQL 보정의 정확성을 확정할 수 없다.**

열람한 `src/mocks/prismaTestDouble.ts:3187`의 page 모드는 전달받은 형식 맵 대신 저장된 본문으로 `classifyFormat(row)`를 다시 호출한다. 실제 SQL과 달리 캐시 전달 누락을 숨길 수 있다. 또 최초 mock의 미판정 응답은 후속 시안에 필요한 `members`를 제공하지 않았다. 시안을 유지하면 대역과 SQL의 새 응답 계약도 함께 맞아야 한다.

`builderSpeedPgliteParity.test.ts`의 실제 SQL 실행 및 기존 전체 응답 비교가 중요하다. 특히 새 보정 계산과 기대값이 같은 helper만 공유하는 경우를 피하고, 보존된 기존 API 읽기 결과와의 비교도 유지해야 한다.

5) **낮음 — 보정 관계 복원의 truthy 검사에는 빈 문자열 경계가 있다.**

후속 시안의 `relations.materials`는 `source_material_id`, `book_id`, `material_kind`가 모두 truthy일 때 관계를 복원한다. `SourceMaterial.kind`는 DB에서 CHECK가 없는 문자열이다(`prisma/schema.prisma:1033`). 빈 kind가 존재한다면 본문 판정 후 책·종류 보정이 누락될 수 있다. `grade`의 truthy 검사도 유사하다. 실제 데이터의 존재 여부는 확인하지 않았다. 기존 결과와 완전 동일성을 요구한다면 빈 문자열을 NULL처럼 버려도 되는지 픽스처 또는 기존 계약으로 확인할 가치가 있다.

| 교과서·자료 | 자료 없는 교과서 문항은 전체 합에는 포함되고 책 목록에는 억지로 붙지 않는다. 책/종류/자료의 교집합, 자료 편수, 책·학년·자료의 기존 순서, 선택한 책의 0건 자료를 보존한다. PGlite 자료 보기의 현재 기본 비교 외에 세 형식별 자료 계수도 확인할 가치가 있다. |
| SQL 우회·외벽 | private 풀은 계수·page 모두 0건이며 형제로 유입되지 않는다. `%`, `_`, 역슬래시 등 미지원 검색과 미지원 정렬/조건은 기존 경로로 돌아간다. 긴 제외 목록, nullable 조건과 NOT의 SQL 의미를 유지한다. 기존 row 정체 API 시험도 함께 회귀 확인한다. |
| 캐시·화면 | 다른 계정의 최근 수 재사용 금지, 적재 후 무효화, 실패 후 재시도, 화면 토글 시 중복 요청 제거, 소비자 abort가 공유 pending 요청을 취소하지 않는 조건을 보존한다. initial 목록은 수량 도착 전 보이되 선택할 수 없어야 한다. |

성능에 관한 단언은 의미 parity와 구분해야 한다. `builderSpeedParity.test.ts:130` 이후의 “답을 전송하지 않음/집계 bucket만 반환” 및 `questionBankProjection.test.ts:307`의 raw 집계 1회 단언은 SQL 계수 구현에 종속된다. 브리프가 허용한 기존 계수 복원을 택하면 해당 조건은 복원 경로와 맞게 조정할 수 있지만, 앞선 결과 스냅샷과 기존 코드 대비 전체 응답 동일성은 약화시키면 안 된다.

반면 후보 ID 페이지 최적화의 성능 경계는 남겨야 한다. 지원되는 후보 조건에서 전체 후보 메타데이터/답을 Node로 읽지 않는지, 대표 ID raw 응답이 pageSize 이내인지, 본문 판정이 ID 범위로 제한되는지 확인한다. 계수 시안을 유지하면 두 번째 전체 집계가 없다는 조건도 필요하다. 작은 mock의 실행시간은 공유 DB 성능의 대체 증거가 아니다.

**4. 실측 스크립트 정적 검토**

대상: `scripts/qa/measure-builder-speed-live.ts` (22:35 KST 열람본)

- **읽기 전용 장치:** `readOnlyClient`가 model read 메서드만 허용하고 `$queryRawUnsafe`, 일반 쓰기 및 실행 메서드를 노출하지 않는다. 실제 외부 트랜잭션에서 `SET TRANSACTION READ ONLY`를 실행하고 `transaction_read_only`를 확인한다. `AsyncLocalStorage`로 조건 해석 중 읽기와 제품 내부 transaction을 같은 읽기 전용 tx에 연결한다. 이 구조는 주석만으로 읽기 전용을 주장하는 수준보다 강하다. 실행 검증은 하지 않았다.
- **비밀값 출력:** `PrismaClient({ log: [] })`, dynamic import 이전 guard 설치, 고정 오류 문구/제한된 code 출력, 행·ID·접속 문자열·SQL 매개변수 미출력 방식을 확인했다. 리드의 임시 스크립트가 출력하던 오류 원문을 그대로 옮기지 않았다.
- **전후 교대 3회:** 단일 측정 자식 프로세스 안에서 기존/현재 독자를 모두 불러오고 `before` 묶음→`after` 묶음을 세 번 실행한다. 초기 bootstrap용 자식 실행이 있다는 사실은 전후를 서로 다른 프로세스에서 측정한다는 뜻이 아니다. 다섯 경로와 기존/현재의 동일 입력 사용을 확인했다.
- **전체 응답 동일성:** 객체 키만 canonical 정렬하고 배열 순서 및 Date를 보존한 전체 직렬화의 SHA-256을 비교한다. 총수·바이트 길이만 비교하는 방식이 아니다. 첫 열람본은 주 측정 응답만 비교했고 warm 응답은 비교하지 않았다. 사용자가 후속으로 warm 전체 응답 비교도 보완했다고 알려 이 항목은 해결 보고된 것으로 기록한다. 보완 최종본의 실행 결과까지 독립 확인한 것은 아니다.

측정표에는 다음 제한을 함께 명시하는 것이 정확하다.

1. 캐시 무효화는 각 독자의 다섯 경로 묶음 시작 때 수행한다. `문항 교체`는 앞선 `문항 추가`가 만든 전역 요약 캐시를 재사용할 수 있다. 따라서 그 수치를 독립적인 최초 교체의 cold 성능이라고 부르면 안 된다. 시나리오 순서를 유지한 리드 측정과의 비교라는 의미는 있다.
2. `recentProblemIds`가 빈 배열이므로 “최근 제외”는 플래그 경로와 공유 캐시 우회 성능이다. 실제 계정의 비어 있지 않은 최근 제외 목록의 비용은 아니다. 비어 있지 않은 이력의 정확성은 로컬 parity가 맡아야 한다.
3. 전후 각각 다른 읽기 전용 RepeatableRead tx이므로 동시에 다른 작업자가 내용을 바꾸면 응답 해시가 다를 수 있다. 읽기 전용만으로 전후 데이터 스냅샷까지 같아지는 것은 아니다. 원인을 분리하지 않고 불일치를 무시해서는 안 된다.
4. 표의 시간은 tx 개시와 read-only 확인을 포함한 읽기 함수 시간이다. 인증·HTTP·브라우저 렌더를 포함한 실제 화면 대기시간으로 확대 해석하지 않는다. 세 회 원값과 중앙값, 캐시 재호출 결과를 함께 남기는 방식이 적절하다.

**주 작업자가 마지막으로 판정할 항목**

- 최신 계수 시안이 기존 전체 응답과 같고, 공유 DB에서 범위 두 경로·문항 추가·출처 고르기가 1차 전보다 느리지 않은지 확인한다. 제공된 PGlite 한 시험 통과만으로 실측 조건을 충족했다고 판정하지 않는다.
- 느리면 계수 호출과 계수용 읽기까지 복원하고, SQL 후보 ID 페이지·형식 캐시 전달·화면 재사용은 보존한다. 복원한 최종 코드에 대해 관련 parity와 필수 검사를 다시 확인한다.
- 실측 결과에는 실제 실행한 최종 코드, 다섯 경로의 3회 수치, 전체 응답 동일성, 남긴 것/되돌린 것 및 캐시 상태를 기록한다. 이 검토에서는 실행 결과나 성능 통과를 별도로 주장하지 않는다.
