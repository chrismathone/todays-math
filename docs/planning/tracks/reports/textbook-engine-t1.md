## 1. 결과와 완료 범위

T1의 **64묶음·544행 중 470행을 대체 원장에 기록했고 74행은 보류했다.** 브리프의 부분 완료 규정에 따라 큰 계산·수 목록 묶음부터 구현했다. 34묶음의 대상 행 508개를 검토했으며, 그중 33묶음에 채택 행이 있다. 검토했지만 맞지 않은 38행과 후속 구현·검토가 필요한 30묶음 36행을 분리했다. T1 전체 완료를 뜻하지 않는다.

**새 등록 키 30개, 기존 재사용 키 15개**다. 기존 계산 골격을 확장하되 난수 순서·소문항·갈래를 기존 키에 더하면 동일 씨앗 결과가 달라지므로 별도 키를 썼다. 소문항 개수나 숫자 표현마다 키를 늘리지 않고 수학적 요구가 같은 가족으로 묶었다. 기존 1,517키의 핸들러는 수정하지 않았고, 고정 씨앗 세 개의 4,551개 공개 생성 결과 해시가 모두 이전과 일치했다.

이 워크트리 안에서 코드·시험·원장을 작성했다. 견본은 브리프가 지정한 저장소 밖 경로에만 만들었다. DB 읽기·쓰기, 적재·잠금, 유료 API, 운영 빌드, 배포, 다른 가지로의 병합, push는 하지 않았다.

## 2. 구현과 난이도

새 키의 접두사는 모두 `textbook-20261125|교과서 수와 연산|`이다. `C`는 정확 유리수 계산, `N`은 약수·배수·소수·거듭제곱, `F`는 소인수 조건, `O`는 분류·범위·순서다. 기존 등록 배열 끝에 추가했다. `gen-cli --list`에서 30개가 검색되고, 전체 등록은 1,547개다. `type-census`는 RPM 색인 밖 등록을 별도로 보여 원래 색인의 분모를 늘리지 않는다.

0단계 난이도는 묶음 단위의 시작값이다. 새 핸들러에서는 `easy=기본`, `mid=응용`으로 고정했으며 `hard=심화`를 새로 두지 않았다. 단순 계산인 C05는 기존 mid 묶음에서 기본으로, 부호·거듭제곱·분배법칙을 복합 적용하는 C03·C04·C08은 easy 묶음에서도 응용으로 정했다. 조건 역산 F04·F05·F06과 경계 결합 O04도 응용이다. O05에 대응한 `J10202-B29-001`은 수의 대소관계에 있던 원문이지만 실제 요구가 직접 절댓값 계산이므로 엔진의 정수와 유리수·기본에 둔다.

## 7. 남은 작업

**74행은 대체 원장 밖에 있다.** 38행은 이번에 읽었지만 원문 조건이나 답 요구를 현재 가족이 충분히 보존하지 못해 제외했다. 36행·30묶음은 작은 묶음의 후속 구현·독립 검산·그림 대응이 남았다. 데이터의 `sourceFigureReadThisStage: false`는 이번 단계에서 그림을 읽지 않았다는 뜻이며, 0단계 관측을 이번 확인으로 바꾸어 적지 않았다.

남은 예는 서로 다른 계산 가족을 섞은 소문항, 곱의 최댓값과 최솟값을 모두 요구하는 카드 문제, 분류에 절댓값 조건 역산이 더해진 문제, 원문 자체의 조건 부족이다. `J10104-A36-001`은 c가 소수라는 제약이 없어 후보 (2,3,5)와 (1,3,10) 등이 남으므로 정답 하나로 대체하지 않았다. `J10102-B43-001`의 이미 소인수분해된 입력을 자연수 입력인 기존 09로 덮지 않았다.

새 사다리·표·피라미드·기계·배치 지면은 **시안 필요**다. 기존 수직선이나 텍스트 골격으로 확장할 수 있는 나머지 항목도 §3에서 새 유형 결정과 확장 결정을 구분했다. 새 지면을 임의로 만들거나, 확인하지 못한 행에 대체 키를 채우지 않았다. 2단계 드라이런·원장님 확인·적재는 이 커밋의 범위 밖이다.

## 8. 리드 검토 반영 — RPM 출처 오등록 수정

**새 30유형을 `textbook-20261125|교과서 수와 연산|…`으로 옮겼다.** 이전 `d2f72276e`에서는 교과서 엔진 유형을 RPM 책 `1-1`의 없는 중단원처럼 등록했다. 1차 관련 시험에서 `middleTypeCoverage.test.ts`를 빠뜨린 것이 검증 누락이었다. 리드가 발견한 «정본과 다른 유형 30개» 실패를 이 가지에서 그대로 재현했다([coverage-before.log](textbook-engine-t1/coverage-before.log)).

[approved-types.json](textbook-engine-t1/approved-types.json)은 새 30키의 승인 목록이다. 기존 자작 `manual-20261018`처럼 별도 출처이며 RPM 색인에 추가하지 않았다. 가드는 다음을 모두 검사한다.

- 승인 목록 길이 30과 C01~C08·N01~N09·F01~F07·O01~O06의 **정확한 키 집합**.
- 해당 출처로 등록한 키 집합과 승인 목록의 일치. 누락·추가·중복을 허용하지 않는다.
- `rpmBook`, `rpmMinor`, `rpmType`, `rpmTitle`, `grade`, `unitSection` 여섯 칸의 문자 그대로 일치.
- `catalog["textbook-20261125"]`가 `undefined`임. 승인 목록 밖의 등록은 기존 RPM 가드를 그대로 거친다.

RPM 정본과 확장 번호 규칙은 수정하지 않았다. 승인 목록은 생성기에서 런타임에 만드는 목록이 아니라 별도 검토 데이터다. 공개 생성 결과도 승인된 메타데이터·선언 난이도·표시 난이도와 대조한다. **학년 중1, 단원 9개, 연산 유형 C01·C02·C05·N05·F01은 그대로**다. `--book 1-1`에 새 유형이 들어가지 않고 `--book textbook-20261125`에서 30개가 나온다. 학년·단원 검색은 유지된다. CLI와 검수 HTML의 `RPM`·`p기준` 표기는 출처·유형 표기로 고쳐 자작 출처에 RPM이라는 이름을 붙이지 않았다.

키 전체가 `keySalt`에 쓰이므로 키만 바꿔 같은 씨앗을 쓰면 생성물도 달라진다. 검토한 문항의 조건·갈래를 보존하기 위해 견본 씨앗을 `기존 씨앗 + 2786810649 (mod 2^32)`로 옮겼다. **런타임 RNG·keySalt·공용 생성 함수는 바꾸지 않았다.** 변경 전 `d2f72276e`에서 동결한 210개 공개 생성 결과와 새 키·보정 씨앗의 결과를 비교해, `rpmBook`만 새 출처로 정규화하면 본문·답·풀이·facts·학년·단원·난이도까지 전체 해시가 같음을 확인했다([provenance-migration.json](textbook-engine-t1/provenance-migration.json)). 이전 키와 씨앗은 이 파일 안에서 변경 이력으로만 보관한다.

검토 JSON의 씨앗 참조 129건과 이 보고서의 새 유형 대표 씨앗 24건을 그 동결 견본에 대조했다. 대체 원장 470행 중 새 출처를 쓰는 426행의 키를 옮겼고 기존 RPM 재사용 44행은 그대로다. 원문 ID·행 해시·출처 순서·채택/보류 판정은 바뀌지 않았다. `calc-review.py`와 `build-ledger.py`의 재현 결과도 일치한다. 이전 파일들의 검증 기록은 `initialValidation` 또는 명시된 `reviewedCommit`으로 구분했다.
