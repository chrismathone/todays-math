m1805는 이전 `v13_upload_results.json`을 읽어 7개 파일을 교체 요청하는 목록을 만들고, ZIP에서는 PDF와 독립 HTML/미리보기 PNG 등을 제외한다. 따라서 **ZIP 하나에 PDF까지 모두 들어 있다고 가정하지 않는다**. m1809/m1811의 응답은 redacted이므로 library version 번호를 v14라는 이름으로부터 계산하지 않는다. `output/..._v11/` 경로를 계속 수정해서 v14를 만드는 기록도 있으므로 폴더 이름의 v11과 문서 판본도 같지 않다.

다음 복구는 coordinator가 확보하는 실제 ZIP/HTML 경로 또는 적법한 파일 다운로드 기능으로 진행해야 한다. 파일을 받으면 읽기 전용 해시·목록·manifest 검사부터 한다. HTML이 있더라도 먼저 데이터와 자산을 정적으로 분리하고, 임의 JS 실행을 해야만 원고를 읽을 수 있다면 별도 검토 대상으로 남긴다. **도구 호출 기록을 다시 실행해서 파일을 재생성하는 것은 이번 조사 결과의 연장선이 아니다.**

| 8. 검증 | 내용 보존 / 권한 / 충돌 / 수식 / 출력 전체 동선 | 예제의 공개 풀이와 연습 정답 비노출 분리. 원본 대비 보존 원장 + 실제 저장 재열기 비교 + 최종 인쇄 PDF 텍스트·시각 검사를 모두 요구. 실물 검수 대기는 `대기`로 표시하며 이번 보고서에서 제품 목록을 바꾸지 않음 |

**QR은 편집 가능한 연결 정보다.** 영상 제작은 별도 작업이며, 현재는 “연결 준비” 상태다. 개념과 영상을 ID로 연결하고 범위·준비/연결됨 상태를 저장한다. 페이지를 재배치해도 영상 대상이 바뀌면 안 된다. 주소가 없으면 작동하는 QR처럼 인쇄하지 않는다.

**전용 탭이 독립되어 있다는 것은 별도 문제은행을 자동 채우라는 뜻이 아니다.** 사용자가 직접 만든 교재 문항을 기존 공용 `Problem`으로 자동 승격하거나, SRS 전용 자료를 가져와 빈 분량을 채우는 것은 이번 요구에서 나오지 않는다. 처음에는 문서의 자체 원고로 보존하고 기존 은행과 연결이 필요하면 명시적 계약으로 다룬다.

## 6. 저장소 실사에서 확인한 구현 관련 경계

직접 읽은 파일은 다음과 같다. 현재 코드의 관측 사실이며 DB에 접속하지 않았다.

- `src/contracts/accountAccess.contract.ts:14`: `WORKSPACE_MENUS`와 별도 `workspaceMenuSchema`에 textbook이 없음. `workspaceMenuProduct`는 product가 없으면 math로 간주한다.
- `prisma/migrations/20261001180000_user_menus_check_all/migration.sql:11`: 메뉴 차단 값 DB CHECK도 제한된 목록이다. “탭 하나 추가”만 하면 메뉴 권한을 저장/회수하는 동선이 실패할 수 있다. 현재 schema 계약 목록과 SQL의 일치 검사가 필요하다.
- `src/contracts/privateWorkspace.contract.ts:12`: kind는 draft/extraction/conceptBlank뿐. 저장 wrapper가 strict여도 payload는 `Record<string, unknown>`이므로 새 교재의 전체 내용 검증을 대신하지 못한다.
- `prisma/migrations/20261001210000_workspace_document_concept_blank/migration.sql:11`: DB kind CHECK도 같은 세 종류만 허용한다.
- `src/lib/privateDocumentActions.ts:30`: `EDITOR_MENU` 및 `problemCountOf`가 kind별 처리. 일반 자료는 problems/crops 목록을 요구하고 최대 2,000개로 제한한다. 새 kind를 더한 뒤 extraction 모양으로 저장하는 우회는 데이터 의미를 훼손한다.
- `src/lib/privateDocumentActions.ts:108` 이후: 저장 JSON 요청은 UTF-8 **3,500,000 bytes** 초과 시 413. 저장 revision 비교 및 조건부 update, 자산 소유/실체 확인, 감사 기록이 있다. **지면 이미지 base64를 통째로 payload에 넣는 설계는 부적합**하다. v14 원고 자체 크기는 아직 모르므로 상한을 통과한다고 단정할 수도 없다.
- `src/lib/privateWorkspace.ts:70,211`: 기본 저장 접근 허용 메뉴와 asset ID 수집 경로가 정해져 있다. textbook만 있는 계정의 접근, private/branch 자산, copy/reopen/print까지 점검 대상이다.
- `prisma/schema.prisma:230`: `WorkspaceDocument`는 `[userId,id]`, JSONB payload, revision, visibility/sharedBranchId, asset 관계를 가진다. `20261002053000_branch_library_visibility`는 private/branch 제약 및 자산 연결을 제공한다. 권한과 자산 저장의 재사용 후보지만, append-only 개정 이력을 이미 제공하는 것은 아니다.

기존 문서 kind 확장은 목록·계정 소유·CAS·asset 관계를 재사용할 수 있는 장점이 있다. 반면 저장/count/copy/rename/list/print 분기와 계약, 모든 손실 저장 방지 경로를 넓혀야 한다. 별도 textbook/edition 모델은 원고 revision snapshot과 대용량 장별 편집을 명확히 할 수 있지만 권한·자산·목록 경로를 다시 설계해야 한다. **둘 중 하나를 이름만으로 결정하지 말고, 완성된 한 권 payload 크기와 복구 요구를 대어 결정한다.** 첫 구현에서 revision history를 제외한다면 저장 충돌 처리와 원고 JSON 백업/복구를 제공하고 “버전 되돌리기”를 약속하지 않는다.
