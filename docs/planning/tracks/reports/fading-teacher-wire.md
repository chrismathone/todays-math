# «오늘의 기억» 교사 학생 현황 — Wire 5안

2026-10-06 · Codex · `srs` · 구조 선택 대기

**B안 «살펴볼 학생 먼저»를 추천한다.** 확인할 학생을 먼저 보여 주되 전체 명단을 같은 화면에 남겨, 사유가 없는 학생도 곧바로 찾을 수 있다. 선택은 원장님께 남겼고 Hi-fi와 제품 배선은 진행하지 않았다.

## 보는 주소

- 전체 5안: `http://localhost:3443/dev/fading-teacher-wire`
- 한 안: `/dev/fading-teacher-wire?variant=A` — `A`를 `B`·`C`·`D`·`E`로 바꾼다.
- 반 표본: 위 주소 뒤에 `&class=0`(0명) · `1`(1명) · `2`(30명) · `3`(네 사유 확인반)을 붙인다. 화면의 «반 선택»으로도 바꿀 수 있다.

리드의 후속 지시에 따라 3443 서버를 유지한다. 현재 PID는 3188이며 `.qa-artifacts/fading-screens/teacher-wire/qa-server.mjs`로 시작했다. 공유 `.next` 충돌을 피하기 위해 자체 빌드 폴더를 쓰며, `MATH_FADING=off`이고 DB 주소는 프로세스 안에서 `127.0.0.1:9`로 지정했다. `.env`는 수정하지 않았다.

## 다섯 구조

| 안 | 무엇을 먼저 보게 하나 | 명단과 학생 상세 | 쓰임과 부담 |
| --- | --- | --- | --- |
| A · 명단 중심 | 학생별 복습일 된 개념·밀림·살펴볼 까닭을 한 표에서 비교 | 왼쪽 전체 명단, 오른쪽 학생 상세 | 익숙한 명단 작업에 맞는다. 확인할 학생을 찾으려면 표를 읽어야 한다 |
| B · 살펴볼 학생 먼저 | 사유가 있는 학생의 명단 | 왼쪽 위 확인 명단, 아래 전체 명단, 오른쪽 학생 상세 | 일상 확인이 짧다. 같은 학생이 위·아래 명단에 함께 보인다 |
| C · 반별 묶음 | 반의 인원과 살펴볼 학생 수 | 빈 반도 포함한 반별 명단, 오른쪽 학생 상세 | 반 단위 업무에 맞는다. 반이 많으면 화면이 길어진다 |
| D · 사유별 분류 | 계정 없음 → 시작 전 → 복습 밀림 → 오래 쉼 | 사유별 명단과 전체 명단, 오른쪽 학생 상세 | 계정 확인 등 같은 사유를 함께 확인하기 쉽다. 여러 사유가 있는 학생은 여러 분류에 보인다 |
| E · 학생 상세 중심 | 학생 한 명의 고른 개념·평가 기록 | 좁은 학생 선택 목록, 넓은 학생 상세 | 상담처럼 한 학생을 깊게 볼 때 맞는다. 여러 학생의 숫자를 비교하기는 어렵다 |

안마다 «오늘의 기억 · SRS / 학생 현황» 머리 오른쪽에 **«미리 보기»**를 두었다. `/dev/fading`으로 이어지는 자리이고 **«저장되지 않음»**을 함께 표시한다. 학생 앱의 미리 보기 알맹이는 다른 Codex의 범위다. 이 보고서는 그 앱의 완성이나 동작을 검증했다고 주장하지 않는다.

첫 학생 상세는 현재 명단의 «복습 밀림» 학생 하나를 예시로 펼치고, 없으면 첫 학생을 펼친다. 이후에는 행 안의 **«보기» 단추**로 학생을 바꾼다. 행·이름·사유 딱지는 클릭하지 않는다. 표는 A·B에서 5건, C의 각 반에서 3건을 먼저 보이고 «더 보기»로 전체를 펼친다. D의 사유 목록과 E의 학생 목록은 모두 펼쳐 보여 준다.

## 표본과 데이터 경계

`fadingCatalog()`의 실제 개념 은행을 받아 저장 기록 표본을 만든 뒤, **`fadingTeacherSummary`와 `fadingTeacherConcepts`가 숫자·사유·개념 상태를 계산한다.** 화면에 전달할 요약 수치나 사유 배열을 직접 적지 않는다. 사유를 발생시키는 날짜와 개념 수는 `teacher.ts`가 공개한 문턱 상수에서 정한다. 저장 표본은 `storedFadingSchema`, 명단과 상세는 `fadingTeacherDashboardSchema`·`fadingTeacherStudentSchema`로 확인한다. 시험에서 실제 응답의 `{ data }` 스키마도 통과시켰다.

| 반 | 등록 학생 | 포함한 상태 |
| --- | ---: | --- |
| 준비반 | 0명 | 빈 명단과 빈 상세 |
| 개별반 | 1명 | 김하윤, 중1 정규반에도 등록 |
| 중1 정규반 | 30명 | 일반·계정 없음·시작 전·복습 밀림·오래 쉼·밀림과 쉼이 함께 있는 학생 |
| 상태 확인반 | 4명 | 살펴볼 네 사유를 하나씩 확인 |

전체는 **학생 34명 / 등록 35건**이다. 명단·선택은 `(classId, studentId)`로 식별하고, 학생 수는 id로 한 번만 센다. 상세 머리에는 그 학생의 등록 반 이름을 함께 표시한다. D안은 사유별 중복을 문장으로 밝힌다.

명단은 교사 명단 GET의 꼴, 상세는 학생 하나 GET의 꼴이다. API와 DB를 호출하지 않으며 학생 개념의 문장·빈칸 답을 클라이언트로 전달하지 않는다. 상세에는 계약의 용어와 상태, 별개의 개수·날짜·평가 건수만 그린다. 최근 기록의 `passed`는 **«‘다시’ 외 평가» 건수**로 표시하고 뜻을 한 줄로 적었다. 뭉친 점수·기억 보존율·정답률·백분율·마스터 표시는 없다.

## 작업실 틀과 측정

`05` §8.9의 작업실 문법과 기존 `--learn-*` 토큰을 사용한다. 남색 옆 메뉴, 밝은 작업 바탕, 흰 면, 구분선, 간결한 한글 문구로 구조를 비교한다. 별도 팔레트·외부 글꼴·아이콘·의존물을 추가하지 않았다. Hi-fi 선택으로 읽히지 않도록 다섯 안에 같은 말씨를 적용했다.

**제품 틀을 기준으로 최종 측정을 다시 했다.** `Workroom.module.css`와 같이 1280에서는 옆 메뉴 240px, 768에서는 212px를 남긴다. A~D는 좁은 내용 폭에서 명단 다음에 상세를 놓으며, E는 학생 목록과 상세의 두 칸을 유지한다. 처음 768에서 옆 메뉴를 접어 측정한 결과는 최종 캡처와 `measurements.json`에서 교체했다.

헤드리스 Chromium과 격리된 agent-browser 세션으로 **5안 × 2폭 × 5상태 = 50개 장면**을 측정했다. 글꼴 적재를 기다린 뒤 계산된 스타일·상자·`elementFromPoint`로 확인했다.

## 검사와 한계

- `npx vitest run src/__tests__/components/fadingTeacherWire.test.tsx --maxWorkers=1`: **7개 통과**. 계약, 다섯 안, 빈 반·한 명 반, 사유 분류, 두 반 등록·전체 펼침·검색, 금지 표시를 확인했다. 구현 전 없는 모듈의 RED를 확인했다.
- 지정 파일 `npx eslint`: **오류 0**.
- 지정 파일 `check-affordance.mjs`: **통과**.
- 전체 `npm run lint:affordance`: 자체 파일 **0건**, 범위 밖 기존 **1건**(`ListeningBankMaterial.module.css:129`의 `.transcriptSeek`). 리드가 해당 파일은 손대지 않고 자체 파일 기준으로 인수하라고 후속 지시했다.
- `NODE_OPTIONS=--max-old-space-size=8192`로 `npx tsc --noEmit --incremental false`: 자체 파일 **0건**, 범위 밖 기존 **1건**(`src/lib/english/listening/runtime/bank.ts:10`, 없어진 `ebs-catalog-20261003.json`). 처음 함께 나온 `fading-traps/calibrate.ts:208`은 리드가 수정했고 재실행에서 사라졌다. 리드가 남은 1건을 별도로 기록하고 자체 파일 기준으로 인수하라고 지시했다.
- 최초 브라우저에서 서버 페이지가 클라이언트 모듈의 상수를 읽어 500이 났다. 상수와 타입을 `wireKey.ts`로 옮긴 뒤 200·실제 렌더를 확인했다. 현재 캡처에는 오류가 없다.

전체 시험·변이 실험·DB 연결·git 쓰기는 하지 않았다. Next가 자체 QA 빌드 경로 때문에 자동으로 더한 `tsconfig.json`과 `next-env.d.ts` 변경은 자신의 추가분만 제거했고 두 파일의 최종 내용 diff는 없다. 다른 Codex·리드의 파일은 수정하지 않았다.

## 원장님이 고르실 것

1. **기본 구조 A~E 중 하나** — 추천 B. 반 단위 확인이 주 업무면 C, 학생 상담이 주 업무면 E도 맞는다.
2. **처음 펼칠 학생 상세** — 시안처럼 밀림 학생 하나를 바로 보여 줄지, 학생을 누르기 전에는 비워 둘지.
3. **처음 볼 반 범위** — 시안의 전체 반을 기본으로 둘지, 마지막에 본 반을 기본으로 둘지.
4. **미리 보기 자리** — 시안처럼 머리 오른쪽 진입점을 유지할지.

고르신 뒤 해당 구조의 Hi-fi 4~5안과 세부 표시 범위를 이어 정한다. `UnifiedWorkspace`, `CourseDashboard`, 접근 관문 및 교사 API 배선은 그다음 단계다.
