The principal causes are:

1. **Contradictory/stale prompt contract.** The shared transform instruction exposes only v2, expressly says graphs/statistical figures outside that schema should be null, and restricts construction to text-only conditions. The grouped caller actually attaches validated PNGs and subsequently asks for new figures, but retains that restrictive block. Several proposals explicitly say the table cannot be represented by the given schema and move its contents into prose/Markdown instead.
2. **Transport schema loophole.** Old receipt schemas allow string-or-null. New receipt schemas require a string with `minLength:2`; the four-character string `"null"` passes. It is not a FigureSpec. Current post-parse checks correctly reject it before rendering. This is a generation/transport schema loophole, **not a demonstrated persistence bypass**.
3. **Incomplete engine instructions and actual analytic-curve gap.** The renderer accepts v2, `elem-1`, and `graph-1`; the transform prompt teaches only v2. Tables and condition boxes can already be rendered. However, `graph-1` supports polynomial/reciprocal curves, and `elem-1/curveGraph` supports quadratic/reciprocal curves: **neither has native exponential/logarithmic curves**. All ten graph sources need those families. Merely naming `graph-1` in the prompt will not add them.
4. **Wrong shared coordinate guidance.** The grouped prompt says all coordinates/radii are roughly `-10..10` scene units, conflicting with the shared v2 instruction's 100–300 screen-unit geometry. v2 uses SVG y-down coordinates and fixed-size labels; `graph-1` maps mathematical y-up coordinates through explicit ranges. The existing four v2 outputs use spans of only 6–12 units, producing tiny strokes among large labels.

## Smallest concrete correction to recommend

**First fix the grouped figure instruction at its own boundary**, keeping shared behavior for callers that truly have no images. Replace the inherited v2-only/null-for-graphs block for this path with a short contract selected from the actual engine catalog. Supply exactly the versions/kinds needed by each source: condition box, `elem-1/table`, and graph contracts. Say that attachments contain question conditions, with a digest-bound transcription of image-only facts; do not invite the model to “solve” missing figures by rewriting the question as text-only. State separate coordinate conventions: v2 SVG y-down with readable screen-unit scale, graph-1 math y-up with explicit ranges, elem-1 kind-defined layout. Do not apply `-10..10` globally.

Minimal required-figure transport tightening while retaining `figureSpecJson` and all source-bound schema branches:

```ts
// Shape filter only; existing JSON.parse + engine remain authoritative.
figureSpecJson: source.requiresFigure
  ? z.string().min(2).regex(/^\s*\{[\s\S]*\}\s*$/)
  : itemSchema.shape.figureSpecJson
```

This rejects encoded null/scalars/arrays at structured output rather than after an apparently successful generation. `{}` still needs the existing engine/version validation; **do not claim this regex validates JSON or math**. Add explicit instruction: “For requiresFigure=true, the string must encode one FigureSpec object; literal null, encoded null, arrays, SVG, URLs, and copied original geometry bytes are not renderable results.” Preserve a fail-closed unresolved/refusal reason outside the successful candidate path when evidence/capability is insufficient. Do not force fabricated output to satisfy the regex. A later tagged `unresolved` result branch may make this clearer, but is not required to diagnose this cohort.

**For the ten graph sources, prompt/schema changes alone do not provide native curve semantics.** The smallest robust engine addition is typed, finite, deterministic exp/log evaluation in the existing graph adapter, for example:

- exponential: `multiplier × base^(slope*x+intercept) + offset`;
