계수 대상 네 경로의 최종 중앙값은 모두 기준 이하이며, 교체 중앙값은 1,921→368ms다.
3회 개별 값에는 네트워크 편차가 있으므로 모든 개별 호출이 빨라졌다고 주장하지 않는다.
첫 호출 15쌍·재호출 15쌍, 총 30쌍의 전체 응답이 모두 일치했다(스크립트 종료 0).

객체 키만 정규화한 전체 응답 SHA-256을 비교한다. 배열 순서·문항 ID·revision·본문·수량·메타데이터를 빼지 않는다.
최종 원출력은 [실측 로그](builder-speed-r2-live-20261018.txt)에 남겼다.

읽기 전용 장치는 설명만 붙인 것이 아니다. 실제 `RepeatableRead` 트랜잭션의 첫 명령이
`SET TRANSACTION READ ONLY`이며, `transaction_read_only=on`을 확인한다. 조건 해석 중 읽기와
제품 함수 안의 트랜잭션도 같은 읽기 전용 범위에 연결한다. 모델 읽기와 매개변수화된 SELECT만
허용하는 프록시도 둔다. 쓰기 검증을 위한 UPDATE조차 실행하지 않았다. Prisma 로그를 끄고
접속 문자열·SQL 매개변수·ID·문항 본문·오류 원문은 출력하지 않았다.

측정 조건과 해석 범위:

- 리드 스크립트처럼 공용 풀에서 문항이 가장 많은 단원을 고른다. 추가는 그 단원 12문항,
  교체는 같은 단원·기본 난이도·기존 ID 하나 제외·10문항이다. 출처는 전역 문항 보기다.
- `recentProblemIds`는 빈 배열이다. 최근 제외 플래그와 캐시 우회 경로를 재며,
  실제 계정의 긴 최근 목록 처리 시간은 아니다. 비어 있지 않은 최근 제외는 parity 시험으로 확인한다.
- 교체는 앞선 추가가 채운 전역 요약 캐시를 재사용한다. 독립적인 최초 교체의 무캐시 시간이라고 해석하지 않는다.
  공용 캐시 TTL은 15초이며, 재호출 때에도 앞선 경로의 소요에 따라 만료될 수 있다.
- 시간에는 읽기 전용 트랜잭션 시작·확인 비용이 들어간다. 인증·HTTP·브라우저 렌더를 포함하는 화면 전체 시간은 아니다.
- 전후는 별도 읽기 트랜잭션이므로 외부 쓰기가 동시에 일어나면 응답이 달라질 수 있다. 불일치는 숨기지 않고 실패로 종료한다.

## 한 번 집계하는 시안을 제거한 근거

첫 SQL이 알려진 문항의 계수를 유지하고, 미판정 문항과 같은 정체의 알려진 형제 표현만 함께 돌려주도록 바꿨다.
본문을 기존 파서로 판정한 뒤 그 정체의 기존 기여를 빼고 새 기여를 더해 **두 번째 전체 집계는 없앴다**.
실제 로컬 PostgreSQL(PGlite) parity 시험은 통과했지만 공유 DB의 실측 중앙값은 다음과 같았다.

| 경로 | 1차 전 → 한 번 집계 시안 (ms) |
|---|---:|
| 범위 수량(최근 제외) | 1,973 → 5,512 |
| 범위 수량(제외 없음) | 2,046 → 5,467 |
| 문항 추가 | 1,930 → 4,067 |
| 문항 교체 | 1,874 → 379 |
| 출처 고르기 | 1,835 → 4,753 |

[시안의 3회 원출력](builder-speed-r2-delta-live-20261018.txt).
계수 회귀를 해소하지 못했으므로 해당 SQL 집계·보정 코드는 최종 제품 코드에서 제거했다.
기존 1차 구현도 직접 재측정해 범위 약 7.3~7.6초를 재현했다([1차 재측정 로그](builder-speed-r2-r1-live-20261018.txt)).

실측의 전체 응답 비교는 1차 구현과 집계 시안에서 목록의 `grades` 순서 차이도 찾아냈다.
계수 숫자를 맞추는 데 그치지 않고 `questionBankMetadata`를 기존의 문항 등장 순서 방식으로 복원했다.
작은 픽스처에서는 드러나지 않았던 차이이며, 최종 실측에서는 이 배열 순서까지 비교한다.

## 남긴 것과 되돌린 것

**남긴 것**

- `unifiedPreview.ts`의 제외 조건을 사용하는 교체 경로는 `questionPageSql`로 대표 문항 ID만 페이지 크기만큼 읽는다.
  실제 문항과 형제 표현 정보는 선택한 페이지에 필요한 것만 읽는다. 정렬, 그룹 후 쪽 자르기, 형식·자격·정확 ID 예외를 보존한다.
- `questionCountSql.ts`에는 닫힌 조건 컴파일러·기존 판정에서 생성한 형식 SQL·후보 ID 페이지 SQL을 남겼다.
  미지원 조건은 기존 Prisma 경로로 돌아가며, 공용 풀 외벽은 유지한다.
- 단원 목록 먼저 표시, 확인 전 선택 금지, 최근 포함/제외 및 문항류 토글에서 받은 수 재사용을 그대로 남겼다.
  R2에서는 제품 JSX·문구·스타일을 수정하지 않았다.
- 공용 계수·전역 요약의 TTL 15초 캐시, 최대 64개, 실패 제거, epoch와 은행 쓰기 무효화를 유지했다.
  계정별 최근·제외·정체 관련 가용량을 공용 캐시에 넣지 않는다.

**되돌린 것**

- `bankSourceQuestions.ts`의 범위·출처·자료 계수와 facet 구성을 보존된 1차 전 코드로 복원했다.
- `questionProjection.ts`는 기준 HEAD와 같은 코드다. 계수 메타데이터는 한 번에 읽고,
  미판정 본문은 기존처럼 5,000개 ID씩 읽는다. 계수 호출만 바꾸고 500행 순차 왕복을 남기지 않았다.
- 일반 문항 추가는 기존의 정렬된 메타데이터 읽기·그룹·쪽 자르기를 사용한다.
  계수 뒤 별도 SQL 페이지 조회까지 붙여 남는 작은 지연도 제거했다.
- 전역 요약은 기존 문항 정체·사용 가능 판정과 메타데이터 순서를 사용한다.
  캐시를 새로 채우는 경우 요약과 후보 계수가 같은 트랜잭션과 형식 판정 맵을 쓴다.
  캐시에 형식 맵을 저장하거나 다른 요청의 판정 맵을 재사용하지 않는다.
- SQL 계수 전용 groupBy·미판정 응답·두 번째 집계와 대역 코드를 제거했다.
  교체 총수용 `loadQuestionCounts`는 기존 읽기와 같은 정체 집합을 세고, 요청별 판정 맵을 ID 페이지 SQL에 전달한다.

계수 복원은 전체 메타데이터 전송 비용까지 1차 전 수준으로 되돌린다. 모든 최초 읽기를 크게 단축했다고 주장하지 않는다.
현재 범위의 목표는 계수 회귀 제거와 교체·재조회 개선이며, DB 형식 열/백필은 적용하지 않았다.

대역도 미판정 본문을 자체 재판정해 캐시 전달 누락을 숨기지 않도록, SQL과 같이 전달받은 판정 맵을 쓰게 맞췄다.
