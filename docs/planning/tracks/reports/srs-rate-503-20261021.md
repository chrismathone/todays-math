# 평가 POST 503 — 기존 백업 로컬 재현과 원인 검토 (2026-10-21)

상태: **리드 원인·범위 승인 후 최소 방어 구현·검증 완료, 로컬 커밋 전달 단계. 운영 조작·배포 없음.**

승인 후 결과: 날짜 역행은 503 대신 `FadingConflict` 409로 거절하며 저장하지 않는다.
성공한 영수증의 멱등 반환은 날짜 검사보다 먼저 유지한다. 제품 변경은
`src/lib/fading/state.ts` 4줄이며, UI·저장 형식·FSRS·연속 일수 정책 변경은 없다.
아래 원인 조사의 수치와 a449 비교는 **수정 전** 결과이고, 수정 후 검증은 마지막 절에 있다.

## 결론과 증명의 범위

기존 저장 입력은 유효하다. 관찰된 `good` 평가를 합성 요청으로 적용하면,
**날짜가 10/25에서 10/21로 역행할 때 평가 전이가 연속 일수의 마지막 날을
10/21로 덮는 반면, 날짜순 집계의 마지막 날은 10/25로 남는다.** 그 결과
`storedFadingSchema`의 최신 날짜 일치 제약을 깨고, `changeFadingState`의
쓰기 전 `parseSrsState`에서 `SrsUnavailable`로 거절되어 503이 된다.

운영 기준 eeabac와 이전 a449에 동일 백업·동일 합성 요청·동일 시계를 실행한
결과가 완전히 같다. **M03/M05/M06 이후의 신규 백엔드 회귀로 재현되지 않았다.**
같은 백업의 평가 날짜만 10/25 또는 10/26으로 둔 대조군은 모두 200이며,
학생 데이터가 전혀 없는 두 개념의 순수 전이 fixture도 같은 역행 조건에서 실패한다.
정상 날짜 순서의 일반 평가 실패라는 근거는 이번 조사에서 얻지 못했다.

원본 HTTP 요청 본문·응답 본문 및 앱 `requestId`는 미확보다. 네트워크
`requestId=8458.956`는 앱의 멱등성 UUID가 아니다. UI의 «알맞음» 관찰을
합성 요청으로 옮겼으며, 원본 wire 요청의 복원이나 바이트 동일 재전송으로 주장하지 않는다.

## 원인 보고 당시의 최소 수정안

이번 결과만으로 최근 화면 변경의 긴급 제품 수정·새 배포가 필요하다고 판단하지 않는다.
정상 순서 대조는 통과하며, 운영 백업을 고치거나 시계를 옮겨 이 결과를
«운영 정상화»로 바꾸지 않는다. 신규 배포 보류를 유지한다.

수정한다면 **기존 영수증의 멱등 반환 뒤, 실제 rate 전이 전에 날짜 역행을
명시적으로 거절하는 최소 방어안**을 우선 권고한다.

- 위치: `rateFadingSession`의 `applyFadingRating` 이전.
- 조건: 유효한 입력의 최신 평가 날짜(`state.streak.lastOn` 또는 마지막 집계 날짜)가 `today`보다 뒤.
- 결과: 기존 `FadingConflict`로 409, 날짜 충돌을 설명하는 문구. 열린 회차,
  원기록·FSRS·집계·재학습·영수증·진도·보상은 전혀 갱신하지 않는다.
- 영수증 확인을 먼저 유지하므로 이미 성공한 requestId는 시계가 역행해도 안전하게 재응답한다.
- 저장 형식·reader 변경이 없어 새 reader-first 배포는 필요하지 않다.
- 제한: 503의 잘못된 «저장 기록 손상» 분류를 없애는 방어이며, 미래 이력이 남아 있는
  시험 계정에서 과거 날짜 평가를 저장할 수 있게 만드는 기능은 아니다. 그 허용 여부는 별도 결정이다.

**역행 평가도 저장해야 한다는 결정을 내린 경우의 별도 최소 후보**는 과거 날짜를
집계에 추가하면서 `streak` 전체를 기존 요약으로 유지하는 것이다. 이 백업에서는
평가 후 상태의 streak만 기존 값으로 둔 메모리 반증 실험이 전체 parse를 통과했다.
그러나 이것은 진단용 counterfactual이며 구현·운영 복구가 아니다. 단순히
`lastOn`만 max로 바꾸면 current=1로 잘못 줄어든 값이 남고, helper만 바꾸면
`state.ts`의 `lastOn: today`가 다시 역행시킨다. 또한 과거 빈 날짜를 새로 채웠을 때
연속 길이를 소급해서 늘릴지, 400일 밖 요약은 어떻게 할지 정책이 필요하다.
따라서 이 후보를 원인 검토 전에 조용히 제품에 넣지 않는다.

계약 제약 완화, 최신 날짜를 요청 날짜로 강제 이동, 기존 미래 집계 삭제,
FSRS 평가일을 최신 날짜로 올리기, 백업/기대값 변경은 수정안에서 제외한다.
리드의 원인 검토·범위 확인 뒤에만 선택된 안의 RED→GREEN과 로컬 커밋을 진행한다.

## 리드 승인 후 최소 방어와 검증

리드가 보고서·두 버전 결과·provenance를 검토한 뒤 날짜 역행을 명시적으로
거절하는 안을 승인했다. 저장 형식·FSRS·streak 소급 정책·기존 기록은 그대로 두고,
기존 영수증 반환 → 기존 세션/평가 검증 → 날짜 검사 → `applyFadingRating`
순서를 유지했다.

제품 변경은 `state.ts`의 다음 검사뿐이다.

```ts
if (state.streak.lastOn !== null && state.streak.lastOn > today)
  throw conflict(
    "마지막 학습 날짜보다 이전 날짜에는 평가를 저장할 수 없습니다. 선생님께 확인해 주세요.",
  );
```

이 문구는 날짜 비교의 사실과 선생님 확인을 안내한다. 기록 손상이나 기기 시계 변경을
단정하지 않는다. 기존 `FadingConflict` 409 경로를 사용하며 저장 형식 추가가 없으므로
새 reader floor가 필요하지 않다. 미래 학습 이력이 있는 상태에서 과거 날짜의 새 평가를
저장할 수 있게 하는 변경은 아니다.

저장소 회귀 시험은 다음 세 파일에 추가했다.

- `src/__tests__/unit/fadingState.test.ts`: 학생 자료 없는 기존 합성 개념 둘로
  10/25→10/21을 재현한다. 역행 거절, 원 상태·평가 대기 보존,
  기존 세션/평가 검증 우선, 성공한 영수증의 최우선 반환을 확인한다.
- `src/__tests__/api/fadingRoutes.test.ts`: 메모리 표와 합성 학생으로
  역행 409·쓰기 0·원 payload/revision/열린 session 보존, 같은 날/다음 날
  200·정확히 1회 쓰기, 다른 기록 영역 보존을 확인한다. 성공한 requestId를
  다시 10/21 시계에서 보내도 200·같은 영수증·추가 쓰기 0이다.
- `src/__tests__/components/fadingCardSession.test.tsx`: 실제 `createApiFadingSource`
  → `useFadingSessionActions` → `FadingApp`을 연결하고 fetch만 메모리 응답으로
  치환했다. 평가 POST 1회가 409를 받으면 GET 1회로 같은 평가 대기를 복원하고
  정확한 안내 문구를 표시한다. 다시 그리기·대조 화면 이동이 POST를 반복하지 않고,
  «저장 다시 시도»도 나타나지 않는다. 기존 hook의 pending 제거/완료 콜백 억제
  회귀도 함께 통과했다. 제품 UI 변경은 필요하지 않았다.

RED는 제품 수정 전에 실행했다: 위 새 시험 6개 중 2개 실패·4개 통과.
실패는 직접 rate가 예외를 내지 않는 것과 라우트가 409 대신 503을 내는 것이었다.
문구를 전달하고 평가 대기를 복원하는 UI 시험은 변경 전부터 통과했다.
로그: 외부 `guard-red.log`.

수정 후 관련 8파일 **188개 전부 통과**했다(`guard-green.log`). 대상은 위 세 파일과
`fadingApiSource`, `fadingCardActions`, `fadingSource`, `fadingContentGuard`,
`fadingRelearnSource`이며 모두 `--maxWorkers=3`으로 실행했다.

기존 실백업도 별도 `fixed-backup.test.ts`로 재확인했다. 수정 전 증거/하네스는 보존했다.

| 10/21 | 409, 승인 문구 | 0회 / 166, 원 payload 동일·평가 대기 유지 | 409, 추가 쓰기 0 |

실패 후 로컬 GET은 200이고 같은 public session token·`phase=rating`을 복원한다.
정상 저장 후에도 fading 밖 기록은 깊은 값 비교로 동일하다. 초기 백업 검증 하네스는
정상 parse가 JSON 객체의 키 순서를 바꾸는 것까지 문자열 해시 차이로 잡았다.
원본을 출력하지 않고 `isDeepStrictEqual`로 값이 같음을 확인했으며, 정상 저장의
