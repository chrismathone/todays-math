이 검토는 제품 코드·DB·환경 변수를 바꾸지 않았고 DB 에 접속하지 않았다. 원본 스냅샷은 비공개 경로에서 행 단위로 읽었고 은행 원문을 이 파일에 옮기지 않았다.

## 1. 결론

계획을 승인한다. 정체 증명은 내 스크립트로 따로 돌려 같은 수를 얻었다. 트리거와 이력 호환 설계는 기존 DB 장치와 부딪히지 않는다. 출제 형식 선택은 현재 결함(`assignFormats` 가 같은 문항류의 다른 숫자를 형식 형제로 씀)을 정확히 짚었다. 보강 상한 96내용/174행은 감사 원장에서 다시 셌다.

계획을 막을 결함은 없다. 다만 아래 구속 조건 1(정삼각형 오답)은 17행 수정 내용 검토에서 반드시 확인해야 한다. 계획 문장으로는 덮이지만 «원인» 칸에 빠져 있어 놓치기 쉽다.

## 2. 독립 검산

### 2.1 정체 증명과 수량 — 재현함

설계 보고서의 스크립트를 쓰지 않고 따로 짠 검산기로 스냅샷(`daf90c9a…cbac3`, 직접 SHA 일치)을 읽었다. 조건은 계획 §2 의 1~4 그대로다. 세 외부 키 문법을 쓰고, 정확히 단답 1·객관 1이어야 하며, 저장 형식이 일치해야 한다. 메타 7필드가 같아야 하고, 단답 본문의 끝 공백을 뺀 앞부분에 ①~⑤ 다섯 줄이 붙어야 한다. 정답 보기의 값은 단답 정답과 trim 후 같아야 하고, 단답 정답은 보기 번호가 아니어야 한다. 해설과 그림 6필드도 같아야 한다.

### 2.2 스키마·트리거 — 기존 장치와 부딪히지 않음 (조건 2)

- 현재 `problem` 의 BEFORE UPDATE 트리거는 `problem_code_freeze` 와 `registered_problem_outer_wall` 이다. 새 무효화 트리거가 다루는 열은 이 둘이 다루는 열과 겹치지 않는다. 그래서 트리거 이름에 따른 발동 순서와 상관없이 결과가 같다.
- `updated_at` 을 자동으로 고치는 DB 트리거는 마이그레이션에 없다. 키만 SQL 로 SET 하면 revision 을 흔들지 않는다는 계획의 전제가 맞다(Prisma `@updatedAt` 은 앱 경로에서만 쓴다).
- **주의:** `registered_problem_outer_wall` 은 등록된 행에 **어떤 UPDATE 든** 들어오면 `pool=private`·`direct_use_allowed=false`·`review_status=rejected` 로 바꾼다. 키만 바꾸는 backfill 도 여기에 걸린다. 스냅샷의 대상 행은 모두 `pool=shared` 라서 등록 행이 섞였을 가능성은 낮다. 그래도 Gate 2 manifest 는 대상 95,492행과 `problem_outer_wall_quarantine` 의 겹침이 **0** 임을 사실 줄로 적어야 한다. 계획의 «자격 전후 동일 readback»이 사후에 잡기는 하지만, 사전 거부로 막는 것이 맞다.
- 트리거가 «키만 바꾸는 UPDATE»를 막지 않는 것은 설계상 의도다. 다른 키로 바꾸는 갱신은 backfill 도구가 거부해야 하고, 증명 없는 키 부여는 도구와 적재기의 증명으로만 일어나야 한다. 시험 행렬에 «증명 없이 키를 SET 하는 직접 SQL»이 그대로 통과한다는 사실을 문서화해 둔다. 그 경로로 생긴 키는 projection 이 그대로 믿으므로 운영 규칙으로 막는다.
- 로컬 검증에 PGlite 를 쓴다고 coordinator 가 알려 왔다. plpgsql 트리거, `IS DISTINCT FROM`, 트랜잭션 롤백은 PGlite 로 충분하다. 하지만 PGlite 는 단일 사용자라서 `SECURITY INVOKER`·`REVOKE EXECUTE … FROM PUBLIC`·Supabase 역할(`anon`·`authenticated`)의 권한은 거기서 증명되지 않는다. Gate 2 에서 공유 DB 카탈로그(`pg_proc.prosecdef`·`proconfig`·`proacl`)를 읽기로 확인한다.

### 2.3 형식 선택 — 현재 결함 확인

`src/lib/unifiedBankSelection.ts` 의 `assignFormats`(393행)는 형제를 `family|unitId|difficulty` 로 묶는다. 그래서 같은 문항류에 속한 **다른 seed·variant 의 행**이 «형식만 바꾼 후보»로 들어간다. 계획의 세 층 분리는 이것을 바로잡는다. 세 층은 문항류 제한, 문항(questionId) 선택, 그 문항 안의 실제 표현 선택이다. 부족 판정을 «선추첨 뒤 배정 실패»에서 «전체 후보에 대한 계획기»로 옮기는 것도 맞다. 계획 §7 의 필수 반례 «선추첨으로 실패»가 이 회귀를 지킨다.

### 2.4 이력 호환 — 문제없음

TestProblem·ProblemAnswer·BasketItem·TextbookProblemSnapshot 은 실제 `problem_id` 를 그대로 가진다. 계획은 행 삭제·코드 재발급·FK 치환·옛 시험 재구성을 모두 금지한다. 옛 저장본의 형제 중복도 자동으로 줄이지 않고, 30일 사용 수는 시험 ID 의 합집합으로 센다. 저장 조건 v1 이 «형식 미저장»이라는 사실을 화면에 밝히는 것도 들어 있다. preflight 의 참조 열 11곳(`problem_outer_wall_quarantine` 포함)이 17행에 대해 모두 0 인 것을 JSON 에서 확인했다.

### 2.6 53유형 · 96내용 · 174행 — 다시 셈 (조건 3)

`docs/reports/math-type-audit-20261018/engine-comparison.json` 의 `thinStoredFamilyReview.rechecks` 에서 «저장 서로 다른 내용 < 5 이고 생성 관측 ≥ 5»인 것을 골랐다.

- 중등·새 서술형은 **36유형, 부족 62** 이다. 그중 native 서술 6유형은 유형당 저장 2, 부족 3씩이라 **18** 이다.
- 초등은 감사 README 기준 17유형·부족 34 다. 합하면 **53유형·96내용** 으로 계획과 같다.
- 174 = 18(서술 단독) + 78 × 2(단답+객관)이다. 계획대로 **상한** 으로만 맞다.
- **주의:** 36 가운데 `mid:manual-20261018|…` 8유형(부족 16)은 지금 **객관식 단독**이다(`formats={"multiple_choice":3}`). 이 유형에 단답 형제를 만들려면 그 생성 계약에 검증된 단답 파생이 있어야 한다. 없으면 새 내용 하나가 1행이다. 그 경우 실제 행 수는 174 보다 작다. 174 를 채워야 할 목표로 읽거나, 보기 삭제로 단답을 만들면 안 된다.
- 감사에는 «53»이 두 번 나온다. 생성기가 5개 이상을 내는 53유형과, 초등의 고정 성질·작은 유한 영역 53유형이다. 계획은 앞쪽 집합을 명시했고 f33/f39·고정 정의형을 빼므로 맞다. 최종 allowlist 에는 유형 키를 적어 두 집합이 섞이지 않게 한다.

## 3. 구속 조건 (구현 · Gate 에서 지킨다)

1. **tri221PickIso 의 eqTri** — 17행 수정 후보에서 이 유형의 두 오답(현 eqTri·rightTri 자리)이 모두 이등변이 아님을 좌표로 증명한다. tri222Pick 도 같다. 기존 `rightTri`·`wideTri`·`eqTri` 의 전역 의미는 바꾸지 않는다(다른 문항류가 쓴다).
2. **바깥벽 겹침 0** — Gate 2 backfill manifest 는 대상 행과 `problem_outer_wall_quarantine` 의 겹침이 0 임을 실행 직전에 다시 확인해 적는다. 하나라도 겹치면 그 쌍을 빼거나 중단한다.
3. **174 는 상한** — 보강 allowlist 는 내용마다 예상 행 수(1 또는 2)와 그 근거 계약을 적는다. 객관 단독 유형과 native 서술은 단독 행이다.
4. **권한은 실제 DB 에서** — PGlite 로 트리거의 의미를 증명하고, `SECURITY INVOKER`·고정 `search_path`·`REVOKE` 는 Gate 2 에서 공유 DB 카탈로그로 읽어 확인한다.
5. **증명 없는 키 SET 금지** — 키를 쓰는 길은 backfill 도구와 «실제 쌍 증명 뒤의 적재기» 둘뿐이다. 기존 키를 다른 키로 바꾸는 갱신은 도구가 거부한다. 이것을 시험으로 고정한다.
6. **인쇄 검수 항목** — 17행 수정으로 그림·보기가 바뀌는 문항류와 새 형식 선택 UI 가 지면에 주는 변화(교사용 답 노출 포함)는 `/dev/print-check` 의 `items.ts` 에 «대기»로 올린다. 물리 출력이 끝났다고 말하지 않는다(CLAUDE.md 절대 규칙 6, 계획 §7 의 과장 금지와 같다).

## 4. 권고 (막지 않음)

- 형식 선택 창은 DESIGN.md 의 대화창·라디오 기준을 따른다. 그것으로 모자라면 화면별로 새로 짓지 말고 공용 부품을 넓힌다(절대 규칙 11).
- 목록 projection 의 성능 기준(EXPLAIN, p95, 전송 바이트)은 설계 보고서 `futureTests` 에 있다. 운영 전환 전 그 수치를 Gate 2 묶음에 같이 둔다.
- 보류한 두 쌍(그림 SVG 차이, `π`/`1π` 표기)은 이번 범위에서 단독으로 둔다. 원인을 확인하지 않고 합치지 않는다.
