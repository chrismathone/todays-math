## 원인과 기존 의미

**M-05.** `FadingCardSessionScreen`은 단계 전체가 filling이면 입력 폼을
그렸다. 현재 문장의 `pending`이 null이어도 다른 문장에 빈칸이 남아 있으면
입력창은 활성이고 «입력»만 비활성이었다. 현재 문장에 남은 빈칸이 있을 때만
폼을 그리게 했다. 기존 문장 이동·오답 재입력·포기·단계 마치기·대조는 유지한다.
legacy chips의 빈 문장 입력란은 기존 시험이 Tab 이동 통로로 명시하므로
이번 M-05에서 변경하지 않았다.

**M-06.** 상단의 «n / m 완료»는 현재 단계에서 처리한 **빈칸 수**다.
정답 수·문장 수·오늘 분량·네 단계의 수가 아니다. 실제 `finishStep`은 결과의
`blanks`·`missed`를 남긴 뒤 `filled`·`skipped`를 비운다. cards는 평가 직후
`compare`까지 비워 입력 배열의 0을 다시 표시했고, chips는 대조·평가·완료에서도
비워진 입력 배열을 읽었다.

완료한 단계의 표시에는 그 단계의 실제 `FadingStepResult.blanks`를 쓴다.
진행 중에는 계속 현재 입력·넘김만 세므로 처음부터 완료로 채우지 않는다.
칩 경로의 대조 머리도 그 결과의 단계·분모와 일치시켰다. «다시»를 선택해
다음 학습의 저장 단계가 낮아져도 방금 끝낸 STEP 04의 완료 수는 유지된다.
전부 포기한 경우에도 «처리 완료»이며 정답·숙달을 뜻하지 않는다.

## 화면 확인과 실행 경계

리드의 명시 허용 후 단일 Chromium과 메모리 fixture로 실행했다.
기본 Playwright 실행 파일 1248이 없어 첫 launch는 실패했고 서버는 종료됐다.
공유 의존성을 변경하지 않고 이미 설치된 headless shell 1234를
`QA_CHROMIUM_EXECUTABLE`로 지정했다. 첫 화면 검증은 exit 0으로 끝났고
브라우저·서버의 종료를 기다린 뒤 문서·커밋 정리에 앞서 사용권을 반환했다.

첫 캡처 묶음의 대표 PNG 열람에서 fixture에만 앱 layout의 KaTeX CSS가 빠져 숫자 하나가
중복 표시되는 문제가 보였다. 제품 변경 없이 fixture에 동일 CSS를 추가했고,
그 누락을 잡는 검사와 초기 0/n·첫 답 뒤 1/n 캡처를 추가했다. 1차 PNG·JSON은
`first-run-without-katex-css/`에 별도로 보존하며 최종 수식 외관 증거로 쓰지 않는다.
리드의 재허용 뒤 chips 초기 화면의 두 header를 하나로 읽던 QA 선택자 오류를
만났다. 그 실행은 exit 1, 양쪽 종료 확인 후 `second-run-header-locator/`에
17장·로그·JSON을 보존하고 반환했다. 리드가 같은 사용권 안의 fixture 오류 수정과
순차 재시도까지 허용한 뒤 첫 상태 header로 선택자를 좁혔다.

그다음 실행은 새로 캡처한 legacy chips 초기 화면의 가로 넘침 때문에 멈췄다.
양쪽 종료를 확인했고 `third-run-legacy-overflow/`에 실패 로그·17장·JSON을 보존했다.
제품이나 CSS를 고치지 않고 레이아웃 관찰을 `layoutIssues`에 따로 기록하도록
QA를 정리했다. M-05/M-06 상태·수식·진도 막대 단정은 유지했다.

최종 실행은 Chromium `151.0.7922.34` 단일 엔진, 390×844·1440×900에서
16경로·56장을 남기고 exit 0으로 끝났다. 페이지 오류·외부/API 요청은 0이다.
`finally`가 브라우저와 서버 종료를 모두 기다린 뒤 `browserClosed: true`,
`serverClosed: true`를 기록했다. 문서·커밋 정리에 앞서 리드에게 반환했고
리드의 반환 수신도 확인했다. 이후 서버·브라우저를 실행하지 않았다.

두 폭의 모든 경로 대표 PNG를 직접 열었다. 캡처 파일명은 다음과 같다.
