## 검토 범위와 증거의 한계

브리프, `docs/planning/25-english-studio.md`의 확정·화면·제작·다음 판·§12.8~§12.13, `docs/planning/10-handoff.md`의 §0-ZC를 읽었다. 아래 현재 기능 판정은 세 뷰, 계약, 생성·저장 라우트, 스키마, 편집·인쇄 및 공용 함수를 직접 읽은 결과다. 경로 뒤 숫자는 이번 검토 시점의 행 번호다.

제품 코드·스키마·기획 SSOT는 수정하지 않았다. 개발 서버, DB 접속, 유료 API, 한컴 COM, 커밋·푸시를 실행하지 않았다. 관련 테스트 소스는 일부 대조했으나 테스트를 실행하지 않았으며, 아래 실패 경로는 정적 코드 추적 결과이지 운영 재현 결과가 아니다. 검토 시작 때 있던 `package-lock.json` 변경은 건드리지 않았다. 외부 홍보의 진위나 경쟁 제품 품질은 이번 코드 감사로 판정하지 않는다.

## 실제 구현된 범위

**학교별 내신 대비.** `src/components/english/EnglishPrepView.tsx:101`의 단계 완료는 자료 수·세트 수·검토 완료 세트 수가 각각 0보다 큰지로 계산한다. 범위 전체를 출제했는지 계산하는 기능은 아니다. 학교·시험 선택, 자료 등록·삭제, 생성 유형 설정, 최근 세트 네 개 표시와 편집 진입이 있다. 설정 창은 유형 이름 배열만 저장한다(`EnglishPrepView.tsx:616`).

**자료 저장.** `src/app/api/english/exams/[id]/materials/route.ts:83`은 파일 원본을 `english_material.bytes`에 저장한다. PDF·DOCX·PNG·JPG/JPEG·TXT를 받고 상한은 4MB다. TXT만 UTF-8로 읽어 앞 30,000자까지 `content`에 넣고, 다른 파일의 `content`는 null이다. 직접 입력은 이름과 글을 저장하며 원본 bytes는 없다. `prisma/schema.prisma:1499`에도 파일·텍스트 외에 추출 상태, 지문 분할, 출처 쪽수, 자료 수정 이력은 없다. 자료 개별 API는 내려받기·삭제만 제공한다(`src/app/api/english/materials/[id]/route.ts:24`). 텍스트 자료도 API로 내려받을 수 있지만 Prep의 다운로드 링크는 `hasFile`인 자료에만 붙는다(`EnglishPrepView.tsx:239`).

**문제 만들기.** `src/components/english/EnglishMakerView.tsx:188`에 ChatGPT·원문 복원·API 세 길이 있으며, `content`가 있는 자료만 불러온다(238행). 생성 계약은 주제·내용 일치·어법·빈칸 추론·문장 삽입·서술형 여섯이고, 원문 복원은 별도 규칙 경로다(`src/contracts/english.contract.ts:52`). 원문 복원은 긴 단어를 고르는 규칙이며, 어휘 난도나 교과서 암기 대상을 고르는 기능은 아니다(`src/lib/english/cloze.ts:23`). API 계약은 1~8문항, 화면 선택지는 3·5·8문항이다. 한 요청에 지문 하나와 유형 목록을 보내며 유형별 문항 수나 여러 지문 작업 목록은 없다.

**API 생성.** `src/lib/english/generate.ts:72`는 `ENGLISH_AI_VENDOR` 지정값을 우선하고, 미지정이면 OpenAI 키 유무로 공급자를 고른다. 모델 상수는 `gpt-6-luna`와 `deepseek-v4-pro`다. OpenAI 호출 실패 시 DeepSeek로 자동 전환하는 기능은 아니다. JSON 파싱 재시도와 검증 거절 후 한 번 고쳐 쓰기는 이미 있으며, 후자는 첫 시도 경과가 150초를 넘으면 생략한다(102·128·133행). 검증 통과 초안은 즉시 반환하므로 품질 검사 지적만으로 모든 초안을 다시 쓰는 구조도 아니다. 생성 API는 저장하지 않고, 화면이 별도 세트 POST를 호출한다(`src/app/api/english/generate/route.ts:67`, `EnglishMakerView.tsx:425`).

**세트와 보관함.** `src/components/english/EnglishLibraryView.tsx:40`은 이 시험의 세트 제목·상태만 클라이언트에서 거른다. 시험을 바꿔 보는 것은 가능하지만 시험 전체 통합 검색, 본문 검색, 복제는 없다. 목록 API도 `where: { examId: id }`다(`src/app/api/english/exams/[id]/sets/route.ts:43`). 세트는 단일 지문·문항 배열·검토 상태·제작 조건·revision을 저장하고, 새 세트는 항상 초안이다. 수정은 revision 충돌을 막지만 이전 판을 보관하지 않는다(`prisma/schema.prisma:1518`, `src/app/api/english/sets/[id]/route.ts:73`).

**이미 끝난 품질·지면 기능.** 제작 조건 저장·표시는 `src/lib/english/meta.ts:35`와 `EnglishEditor.tsx:431`, 검사 안내·브라우저별 확인함은 `src/lib/english/notes.ts:175`와 `EnglishEditor.tsx:62`, 거절 당시 결과에 대한 수정 요청문은 `EnglishMakerView.tsx:314`에 있다. `validate.ts:39`는 보기·정답 번호·근거 연속 인용 등을 막는 검증이고 `quality.ts` 전체를 저장 차단기로 쓰지 않는다. `bundle.ts:131`과 `EnglishPrintClient.tsx:141`은 누출 검사에 따른 학생용 묶음·배부 순서와 교사용을 이미 제공한다. 읽기 모양 편집, 밑줄, 보기 줄 처리도 기존 기능이다. 이들을 신규 후보로 세지 않는다.

## 고도화 후보 8개

### 1. 생성 성공 뒤 저장만 다시 시도하기

걷어낼 손작업은 저장 오류 뒤 같은 지문·조건으로 다시 생성하고 새 결과를 다시 검토하는 일이다. 현재 `EnglishMakerView.tsx:425`는 생성 응답을 함수 안의 지역값으로 받은 뒤 곧바로 `saveDraft`를 부른다. 저장에 실패하면 오류만 상태에 남으며, 다음 생성 버튼은 생성 API부터 다시 호출한다. 서버 생성 API도 결과를 보관하지 않는다. ChatGPT 길은 붙여넣은 글이 남으므로 이 공백은 특히 API 길에서 크다.

빈칸은 생성된 초안·제작 조건을 저장 완료까지 붙잡고 저장만 재시도하는 경로다. POST가 서버에서는 성공하고 응답만 끊긴 경우도 있어 중복 생성 방지 기준까지 필요하다. 노력은 **중간**이다. 복구 범위 결정은 필요하고, 재시도 단추·안내가 생기면 **시안 필요**다. 하지 말아야 할 방식은 모든 실패를 자동 재생성하거나 세트 POST를 무조건 반복하는 것이다. 현재 세트 POST는 요청 식별자 없이 매번 새 행을 만들므로 중복 저장을 늘릴 수 있다(`exams/[id]/sets/route.ts:75`).

### 2. 자료를 출제 가능한 지문으로 정리하기

걷어낼 손작업은 PDF·DOCX에서 영어를 복사하고 줄바꿈을 고친 뒤 긴 자료를 출제할 지문 단위로 나누는 일이다. 현재는 파일 보관과 직접 입력·TXT 읽기까지만 있다. Maker는 글 전체를 원문 칸에 넣는다(`EnglishMakerView.tsx:494`, 551행). 저장 자료는 30,000자까지지만 AI 생성 입력은 18,000자, 원문 복원·세트 지문은 24,000자까지다(`english.contract.ts:100`, 308행). TXT의 30,000자 뒤는 원본 파일에 남지만 출제용 글에는 빠진다.

빈칸은 쓸 구간 선택·분할·교정·원본 위치 확인이다. 먼저 기존 TXT·직접 입력의 길이 안내와 분할 필요를 확인하고, 자동 읽기는 DOCX·텍스트 PDF·이미지 OCR을 나누어 결정할 수 있다. 자동 추출과 교사 확인까지 포함한 노력은 **큼**이다. PDF·DOCX·이미지 자동 읽기는 이미 §10.2의 다음 판 후보이므로 원장님 범위 결정과 **시안 필요**이며 새 발견으로 포장하지 않는다. 하지 말아야 할 방식은 업로드 즉시 추출문으로 자동 출제하는 것이다. 잘린 글·섞인 단·인식 오류를 확인하지 않으면 다시 검토할 양이 늘어난다. 실제 입력이 짧은 텍스트뿐이면 자동 읽기의 우선순위는 낮다.

### 3. 저장된 제작 조건을 다음 제작에 다시 쓰기

걷어낼 손작업은 같은 난이도·유형·문항 수를 매번 다시 고르고, 탭을 나갔다 돌아와 원문을 다시 붙이는 일이다. `englishSetMetaSchema`는 조건을 이미 저장한다(`english.contract.ts:227`). 그러나 `meta.ts`는 저장용 값과 표시 문자열을 만들 뿐이고, Maker는 기본값으로 시작한다(`EnglishMakerView.tsx:189`). 현재 불러오기 단추는 시험의 유형 배열만 가져온다(253행). 상위 탭 이동으로 Maker가 언마운트되면 입력 상태도 유지되지 않는다(`EnglishStudio.tsx:404`, 457·478행).

빈칸은 기존 세트의 조건을 새 제작 초깃값으로 옮기는 기능과 시험별 미완료 입력의 보존 범위다. 노력은 **중간**이다. 조건 재사용과 임시 보존을 어디까지 할지 원장님 결정 및 **시안 필요**다. 하지 말아야 할 이유는 저장된 meta를 완전한 재현 기록으로 오해할 수 있다는 점이다. 옛 세트는 meta가 없고, 원문 유지의 최초 원문은 별도로 저장하지 않으므로 세트 지문을 수정한 뒤에는 최초 원문을 정확히 복원할 수 없다(`meta.ts:31`, 세트 PUT 계약). 모델·프롬프트 판도 기록이지 과거 모델 실행을 보장하는 기능이 아니다. 시험을 바꿀 때 다른 시험의 미완료 글을 조용히 이어 쓰게 해서는 안 된다.

### 4. 지난 시험 자료·세트 찾기와 복사

걷어낼 손작업은 작년·다른 반 시험을 하나씩 열고, 같은 자료를 다시 올리거나 검토한 문제를 다시 옮기는 일이다. 현재 보관함은 선택한 시험 안에서 제목·상태만 검색하고, 자료·세트 모두 시험에 종속된다(`EnglishLibraryView.tsx:40`, `prisma/schema.prisma:1499`, 1518행). 별도 복사 API나 원본 세트 연결 필드는 없다. 이름만 바꾼 검색 기능은 이미 있는 기능이므로 후보의 핵심이 아니다.

빈칸은 허용된 소유 범위 안에서 시험을 가로질러 찾고, 원본을 보존한 채 대상 시험에 복사하는 흐름이다. 노력은 **중간**이다. 복사 시 검토 상태를 초안으로 돌릴지, 출처·원본 연결을 무엇으로 남길지 결정과 **시안 필요**다. 하지 말아야 할 방식은 학교 이름이 같다는 이유로 전 사용자 자료를 공유하거나, 새 시험 편집을 원본에도 반영하는 것이다. 권한은 계속 부모 시험의 소유 범위로 판단해야 한다. 실제로 이전 시험을 재사용하지 않는다면 통합 검색보다 현재 시험 정리의 가치가 크다.

### 5. 시험 범위별 제작 현황과 유형별 문항 수

걷어낼 손작업은 외부지문 목록 옆에 출제 여부를 적고, 세트마다 어법·삽입이 몇 개 있는지 세어 빠진 범위를 찾는 일이다. Prep의 세 단계는 자료·세트·검토 수만 센다(`EnglishPrepView.tsx:101`). 출제 설정은 유형 선택뿐이며 생성 요청은 총 문항 수와 유형 목록만 받는다. 검증도 고른 유형이 각각 하나 이상 있는지 확인할 뿐 유형별 할당량은 없다(`english.contract.ts:302`, `src/lib/english/validate.ts:105`). meta의 자료 출처는 이름뿐이고 자료 id 관계가 없다.

빈칸은 자료·지문과 세트의 명시적 연결, 목표 유형별 개수, 실제 완료 현황이다. 노력은 **중간**이며, 여러 지문 일괄 작업까지 포함하면 **큼**이다. 범위 단위를 자료·지문·단원 중 무엇으로 잡을지 결정과 **시안 필요**다. 하지 말아야 할 방식은 세트 개수만으로 범위를 다뤘다고 표시하거나 자료 이름을 식별자로 쓰는 것이다. 이름 중복·원문 수정·새 지문 생성이 있기 때문이다. 이 현황을 학생 성취 점수로 합치거나 배점 기능을 끼워 넣지 않는다. 대량 생성은 검토량까지 줄어드는지 확인한 뒤 별도로 판단한다.

### 6. 필요한 문항만 남기고 순서를 고치기

걷어낼 손작업은 세트 중 쓰지 않을 문항을 외부 편집기에서 지우고 번호·정답지를 다시 맞추는 일이다. `EnglishEditor.tsx:227`은 기존 문항의 발문·보기·정답·해설·근거를 바꾸지만, 문항 삭제·순서 변경·추가 단추는 없다. 삭제는 세트 전체 삭제다(304행). 인쇄의 묶음 선택·합치기는 이미 있으며, 이는 임의의 문항 선택과 다르다(`bundle.ts:131`, `EnglishPrintClient.tsx:235`).

빈칸은 같은 지문 세트 안에서 문항을 빼거나 재배열하는 제한된 편집이다. 노력은 **중간**이다. 원본을 바꿀지 사본으로 만들지, 인쇄 번호를 어떻게 이어갈지 결정과 **시안 필요**다. 하지 말아야 할 방식은 서로 다른 지문의 문항을 현재 단일 passage 세트에 그대로 섞는 것이다. 근거 검증과 묶음 누출 판단의 전제가 깨진다. 문항 순서를 바꾸면 배열 위치를 쓰는 검사 확인함·누출 설명·인쇄 번호도 함께 다시 계산해야 한다. 통과한 문항의 AI 부분 재작성은 별도 문제이며, 거절 시 수정 요청문과 사람 감사가 이미 진행 중인 결정을 대체하지 않는다.

### 7. 학교에서 손으로 만드는 부족 유형 한 종류부터

걷어낼 손작업은 실제 학교 시험에서 반복되는데 현재 여섯 생성 유형으로 만들 수 없는 유형을 별도로 작성하는 일이다. 현 계약에는 글의 순서·어휘·요약 등의 별도 유형이 없다(`english.contract.ts:52`). 다만 서술형 안내 안에는 조건 영작·요약·어법 고쳐 쓰기가 이미 있으므로 이를 별도 유형과 혼동해서 결손 수를 늘리면 안 된다(`src/lib/ai/prompts/englishExam.ts:63`).

빈칸은 최근 실제 시험에서 자주 쓰고 손작업이 오래 걸리는 한 유형의 출력 계약·검증·지면·검토 기준이다. 예를 들어 글의 순서는 후보일 수 있으나 채택 근거는 홍보 사이트의 유형 수가 아니라 원장님이 만드는 시험이어야 한다. 노력은 **큼**이다. 유형 선택, 대표 문항, 정답 유일성을 판단할 표본과 **시안 필요**다. 하지 말아야 할 이유는 유형 상수만 추가하면 현재 묶음 분류에서 새 유형이 독해형으로 처리되어 원 지문을 함께 보여 줄 수 있다는 점이다(`bundle.ts:135`). 계약·검증·누출·인쇄를 함께 검토해야 한다. 오답 레시피 v4 재개나 수능 유형 전부 채우기는 이 후보가 아니다.

### 8. 편집 가능한 영어 문서 파일 내려받기

걷어낼 손작업은 이미 검토한 세트를 한글 문서에 다시 붙이고 보기·밑줄·정답지를 재배치하는 일이다. 현재 영어 출력 경로는 저장된 세트를 읽는 인쇄 페이지와 `window.print()`다(`src/app/(main)/english/sets/[id]/print/page.tsx:56`, `EnglishPrintClient.tsx:273`). 저장소에 별도의 HWPX 생성 경로는 있다(`src/app/api/exports/hwpx/route.ts:12`). 그러나 영어 세트·학생용 묶음·교사용 자료를 그 입력으로 변환해 내려받는 연결은 영어 코드에 없다.

빈칸은 영어용 문서 변환, 학생용 정답 제외, 묶음 구분, 밑줄·보기·쪽 나눔의 파일 검수다. 노력은 **큼**이다. 실제 편집에 필요한 형식이 HWPX인지 DOCX인지와 종이 모양을 정하고 **시안 필요**다. 하지 말아야 할 이유는 파일 형식 하나를 추가하면 브라우저 지면과 다른 조판 검수 비용이 생기기 때문이다. 출력 뒤 외부 편집을 거의 하지 않으면 기존 인쇄의 가치가 더 크다. 검토 가능한 방향은 서버에서 파일을 만들어 내려받는 것이며, 한컴 COM으로 원본을 열어 조작하는 자동화는 제외한다. 수학 문제은행·엔진을 영어용 중간 저장소로 쓰지 않는다.

## 별도로 드러난 작은 경계 문제

**자료 이름과 제작 조건의 길이가 다르다.** 자료 이름은 255자까지인데 `meta.materialName`은 200자까지다(`english.contract.ts:168`, 240행). Maker의 `sameText`와 `englishMetaFromConditions`는 자료 이름을 줄이지 않고 전달한다(`EnglishMakerView.tsx:209`, `meta.ts:52`). 따라서 201~255자 이름의 자료를 그대로 불러와 세트를 만들면 초안 내용이 유효해도 저장 계약에서 거절될 수 있다. 코드 경계의 불일치이며 발생 빈도는 확인하지 않았다. 생성 실패 복구와 함께 우선 확인할 작은 항목이다.

**편집 화면의 미저장 수정은 인쇄에 전달되지 않는다.** 편집기는 저장과 인쇄가 별도이고 인쇄 링크에는 세트 id만 실린다(`EnglishEditor.tsx:256`, 600행). 인쇄 페이지는 DB에서 다시 읽는다. 따라서 현재 화면에서 고친 뒤 저장하지 않고 인쇄하면 이전 저장본을 보게 된다. 코드에서 이 구분을 알리는 미저장 변경 비교나 인쇄 전 저장 경로는 확인하지 못했다. 저장 여부를 명확히 하는 방식은 시안에서 정하되, 인쇄 기능 자체가 없다는 식으로 제안하지 않는다.

## 순서 제안

### 지금 가치 있는 것

첫째, 생성 후 저장 실패 경로와 위 두 경계 문제를 우선 확인한다. 실패한 생성 전체를 다시 돌리는 대신 결과를 살리는 것은 이미 허용된 제작 작업의 신뢰성을 높이는 범위다. 다만 새 단추나 인쇄 안내 형태는 D-07을 따른다.

둘째, 하루 작업 몇 건에서 자료 확보·조건 재입력·과거 세트 찾기·문항 편집·외부 문서 조판에 든 시간을 구분한다. 이 코드는 하루 30~60분 중 어느 단계가 큰지 보여 주지 않는다. 제작 조건 재사용(3)과 지난 시험 복사(4)의 수요를 먼저 확인하면 새 AI 기능 없이 줄일 수 있는 작업을 가를 수 있다.

셋째, 이미 준비된 사람 감사를 진행해 기존 검사의 정확성과 검토 부담을 확인한다. 새 감사 화면을 만들자는 뜻이 아니다. 감사 결과 전에는 프롬프트·모델·검사 표시가 문항 품질을 높였다고 결론 내리지 않는다.

### 시안·결정 뒤

후보 1의 복구 안내와 3·4·6의 반복 작업 단축을 먼저 시안으로 비교한다. 자료 복사·정리에 시간이 많이 든다는 확인이 나오면 2를 앞당기되, 자동 읽기는 기존 다음 판 결정의 연장으로 다룬다. 범위 누락과 개수 맞추기가 주된 일이면 5를 검토한다. 7은 실제 학교 문항의 결손, 8은 실제 한글 재편집 수요가 확인됐을 때 후순위로 진행한다. 이 순서는 구현 승인이 아니다.

### 하지 말 것

- 세 탭·메타데이터·품질 안내·수정 요청문·학생용 묶음을 새 기능처럼 다시 제안하지 않는다. 코드에 이미 있다.
- 경쟁사의 유형 수·변형 단계 수를 그대로 목표로 잡지 않는다. 현재 `new/original/variation`과 `기본/표준/심화`는 서로 다른 축이며 학교의 작업량 근거도 없다.
- 사람 감사 전에 오답 레시피 v4나 품질 차단 규칙을 강화하지 않는다. §12.9의 천장 결과와 §12.13의 표시 범위를 다시 여는 일이 된다.
- 학생 풀이 앱·정답지 사진 채점을 이번 출제 작업 개선의 1순위로 잡지 않는다. 영어 세트에는 학생·제출·결과 관계, 안정적 문항 id, 과거 판 보관이 없다. 사진 채점은 이미 §12.10에 배관과 선행 조건이 정리돼 있으므로 새 기능 발굴로 중복 제안하지 않는다.
- 교육과정 자료를 넣었다는 이유만으로 학년별 어법 출제가 검증됐다고 하지 않는다. 코드의 어법 안내는 고정 범주이고 학년은 문자열 입력이다. 2015/2022 처리·학교급과 학년 매핑·과목 칸·지면 표시는 §12.12의 결정 대기다.
- 수학 `Problem`·채점·엔진을 영어 세트의 저장·편집 우회로로 쓰지 않는다. 기존 영어 울타리와 소유 범위를 유지해야 한다. 단일 성취 지수·배점 확대·한컴 COM 자동화도 제외한다.

## 브리프의 외부 사실을 제품에 대입할 때 생기는 과장

**파일 지원을 자동 읽기로 바꿔 읽을 수 없다.** 경쟁사의 PDF·이미지·HWP 홍보를 우리 업로드 확장자 목록과 맞춰 기능이 같다고 하면 틀린다. 우리 PDF·DOCX·이미지는 보관이고 출제용 글은 null이다. 화면 안내도 PDF·이미지를 보관용이라고 적지만 DOCX는 명시하지 않아, DOCX만 읽힌다고 오해할 여지가 있다(`EnglishPrepView.tsx:590`).

**학교별 화면과 학교별 출제 분석은 다르다.** API 생성은 시험에서 학년만 가져와 요청 조건과 함께 프롬프트로 보낸다(`src/app/api/english/generate/route.ts:65`, `src/lib/ai/prompts/englishExam.ts:144`). ChatGPT 요청문에는 학교·시험 이름도 들어가지만(`src/lib/english/chatgpt.ts:52`), 기출 분석 결과·학교별 출제 특징을 구조화해 넣는 기능은 없다. 시험별 자료 보관을 이미 학교 경향 학습이라고 설명할 수 없다.

**여섯 생성 유형과 원문 복원을 혼동하면 안 된다.** `ENGLISH_QUESTION_TYPES`는 일곱 값이지만 생성 요청은 여섯 값이다. 원문 복원은 가장 긴 단어를 지우는 규칙이다. 수능 읽기 유형 전부나 경쟁사의 워크북·5단계 변형·대량 제작에 대응한다고 설명할 근거가 없다. 반대로 서술형 안에 이미 들어간 조건 영작·요약까지 모두 없는 기능으로 세는 것도 과장이다.

**검증·묶음 분리는 문항 타당성의 증명이 아니다.** 근거가 지문에 포함되는지 확인하는 코드는 지문 없이는 못 푸는지, 정답이 유일한지 판단하지 않는다. 누출 검사와 별도 묶음은 이미 있으나 바꿔 쓴 단서나 학생 기억까지 차단하지 않는다. 브리프의 지문 의존·지역 의존 연구 취지에 비추어도 코드 존재만으로 품질 향상을 주장할 수 없다. AI 가림 풀이의 천장 문제와 사람 감사 미실시는 그대로 남는다.

**온라인 시험·자동 채점·영어 HWPX는 현재 완료 기능이 아니다.** 세트 스키마의 answer·explanation은 출제자가 작성하는 정답·기준이지 학생의 제출 결과가 아니다. 기존 HWPX 서버가 있다는 사실도 영어 전용 내보내기의 완료를 뜻하지 않는다. 경쟁사가 내신 또는 수능에 집중한다는 홍보만으로 우리 학생 앱·수능 확장 우선순위를 정할 근거는 없다.

**브리프 자체의 모델 설명은 조건을 덧붙여야 한다.** 키가 있으면 luna라는 요약은 공급자 지정이 없을 때만 맞는다. `ENGLISH_AI_VENDOR`로 명시하면 그 설정이 우선한다. `source: "deepseek"`는 luna 생성에도 쓰이는 기존 저장 분류이므로 실제 모델은 `meta.model`을 봐야 한다. 또한 계약 머리 주석의 10MB와 프롬프트 파일 머리의 v2 표기는 낡았고 실제 상수는 4MB·v3다. 이번 보고서는 주석보다 실행값을 기준으로 삼았다.

## 가정의 구멍 하나

이 검토는 원장님의 하루 출제 시간이 자료 정리와 반복 설정·재사용에서 상당 부분 발생한다고 가정한다. 코드만으로 그 비중은 알 수 없다. 실제로는 짧은 텍스트를 이미 갖고 있고 시간 대부분이 정답·오답을 읽고 고치는 데 쓰인다면, 자동 읽기·통합 보관함보다 기존 사람 감사와 후보 6의 문항 편집이 먼저다. 동일한 실제 제작 몇 건의 작업 시간을 단계별로 기록하면 이 우선순위가 틀렸는지 확인할 수 있다.
