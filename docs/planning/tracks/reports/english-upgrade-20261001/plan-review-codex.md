# 저장·어휘 조각 코드 대조 (2026-10-01)

초안은 고칠 곳이 있다. 저장 재시도의 실패 단계·동시 요청 보장, 어휘 누출의 대상 목록·시험 기준, 붙여넣기 허용과 유형 선택 제한의 충돌을 보완하면 1·2조각의 방향은 유지할 수 있다.

검토 대상은 브리프가 지정한 세션의 `plan.md`와 합본의 이번 범위이며, 아래 행 번호는 검토 당시 초안 기준이다. 제품 코드와 기획 문서는 수정하지 않았다. 파일과 기존 테스트 내용을 읽어 대조했으며, 테스트 실행·개발 서버·유료 API·커밋은 하지 않았다.

## 수정 제안

### 1. 저장 실패와 생성 실패를 나누고, 재시도할 본문을 고정한다

- **초안 문장:** 19행 «세 길은 초안을 지역값으로만 갖고 저장에 실패하면 버린다. 다시 누르면 생성을 처음부터 한다», 21~24행 초안·조건 보관과 재시도 시험.
- **코드 사실:** `src/components/english/EnglishMakerView.tsx:277`의 `saveDraft`는 전달받은 초안과 meta를 POST한다. `importPaste`는 성공한 뒤에만 `pasteText`를 비우므로 실패해도 붙여넣은 원문은 남는다(314~361행). 원문 복원 입력도 남아 다음 클릭에서 로컬 `makeCloze`를 다시 실행한다(383~423행). 서버 생성 호출을 다시 하는 경로는 API 탭이다. API 생성과 저장은 같은 `try/catch`여서 세트 POST의 503도 `aiLink = waiting`으로 처리된다(425~473행). 현재 폼의 소재·자료 선택 등은 비동기 작업 동안에도 변경할 수 있다.
- **최종본에 넣을 문장:** «API 탭은 생성 응답의 초안을 잃고, 붙여넣기·원문 복원은 입력은 남지만 검증·복원을 다시 실행한다. 세 경로 모두 검증된 초안, 그때의 meta와 clientKey를 세트 POST 전에 한 묶음으로 보관한다. 다시 저장은 이 본문만 재전송하고 현재 폼에서 조건을 다시 만들지 않는다. API 생성 실패와 저장 실패를 구분하여 저장 503은 AI 연결 상태를 바꾸지 않는다. 저장 성공 때만 보관 상태를 지우고 검토 화면으로 이동한다. 시험은 API의 생성 요청 1회·세트 POST 2회, 붙여넣기·원문 복원의 동일 본문 재전송, 재시도 전 폼을 바꿔도 본문·키 유지, 생성 실패 때 저장 재시도 미노출을 각각 확인한다.»

### 2. clientKey 조회와 생성 사이의 동시 요청을 닫는다

- **초안 문장:** 26~31행 «같은 저장을 두 번 눌러도 행이 하나», «같은 시험에 같은 clientKey가 이미 있으면 기존 행 200», 5행 «데이터베이스 마이그레이션은 없다».
- **코드 사실:** `src/app/api/english/exams/[id]/sets/route.ts:55`는 세션·시험 소유권·입력 검증 뒤 매번 `create`하며, 기존 키 조회나 트랜잭션이 없다. `prisma/schema.prisma:1518`의 세트 모델은 `meta` JSONB와 `(examId, updatedAt)` 색인만 있고 clientKey 유일성 제약은 없다. 조회 뒤 생성만 추가하면 두 요청이 동시에 조회를 통과할 수 있다. `src/__tests__/api/englishSets.test.ts:28`은 DB 대역을 쓰고, `src/mocks/englishTestDouble.ts:7`도 영어 라우트에 트랜잭션이 없다는 전제로 작성되어 있다.
- **최종본에 넣을 문장:** «clientKey는 시험 범위의 재시도 식별자다. 소유권 확인과 입력 검증을 유지하고, 같은 시험·키의 조회와 생성은 DB에서 직렬화한다. 마이그레이션 없이 구현한다면 부모 시험 행을 트랜잭션 안에서 잠근 뒤 같은 트랜잭션에서 키를 조회·생성하는 방식으로 동시 요청을 막는다. 두 번째 요청은 첫 저장 결과와 같으면 200, 다르면 409이며 덮어쓰지 않는다. 순차 재시도뿐 아니라 같은 키의 동시 요청에도 행 하나인지 검증한다. DB 대역이 사용하는 조회·트랜잭션을 지원하도록 시험 범위를 함께 적고, 메모리 대역 시험만으로 실제 DB 동시성을 입증했다고 하지 않는다.»

### 3. 같은 본문의 비교 범위와 meta 보존 회귀를 적는다

- **초안 문장:** 29행 «제목·지문·문항이 다르면 409», 30행 «세트를 고쳐도 키는 유지», 31행 키 없음 201.
- **코드 사실:** 생성 계약은 `title`, `source`, `passage`, `questions`, 선택적 `meta`를 받는다(`src/contracts/english.contract.ts:274`). 문자열 trim을 거친 검증 결과가 저장된다. `source`는 생성 POST에서 저장되고 편집 PUT에서는 기존 값이 유지된다(`src/app/api/english/sets/[id]/route.ts:62`). PUT 계약과 업데이트 데이터에는 meta가 없어서 meta 보존 방침은 맞다. 응답 직렬화도 meta 전체를 `englishSetMetaSchema`로 다시 읽는다(`src/lib/english/serialize.ts:129`).
- **최종본에 넣을 문장:** «동일 여부는 계약 검증 후 저장할 title·source·passage·questions의 값으로 비교한다. questions에는 순서와 모든 문항 필드를 포함하고 JSON 객체의 키 나열 순서는 비교 근거로 쓰지 않는다. 기존 행을 반환할 때 status·revision·meta를 초기화하지 않는다. 시험에는 source 또는 문항 내용만 다른 같은 키의 409, 다른 시험의 같은 키 독립성, 키 없는 기존 클라이언트의 201, 세트 PUT 뒤 clientKey 보존과 응답 직렬화를 포함한다.»

`materialName`을 200에서 255로 올리는 33~36행은 그대로 유지한다. 실제 자료 이름 상한은 255이고 meta만 200이다(`src/contracts/english.contract.ts:165`, `:227`). clientKey를 선택적 uuid로 계약에 추가한다는 설명도 맞다.

### 4. 문항 수와 어법·어휘 선택 제한을 모든 설정 유입 경로에 적용한다

- **초안 문장:** 16~17행 유형 수에 맞춘 문항 수 상승, 60행 «둘을 같이 고르면 나중 것을 푼다».
- **코드 사실:** `EnglishMakerView`는 초기 `exam.types` 복사(189~197행), 체크박스 `toggleType`(243~251행), «출제 설정 불러오기»(253~259행)의 세 경로로 유형을 받는다. 학교 설정은 두 유형을 함께 저장할 수 있으며, 목록을 상수 순서로 재구성하므로 클릭한 시간 순서는 저장하지 않는다(`src/components/english/EnglishPrepView.tsx:628`). 체크박스 클릭만 막으면 처음 열기와 설정 다시 불러오기로 우회된다.
- **최종본에 넣을 문장:** «문항 수 선택지는 3·5·6·8로 한다. 유형 초기화·개별 토글·출제 설정 불러오기 모두에서 허용 유형을 확정한 뒤, 현재 문항 수가 유형 수보다 작으면 가능한 가장 작은 선택값으로 올린다. 어법·어휘 중 하나가 선택된 상태에서 다른 것을 클릭하면 그 새 선택을 받지 않고 기존 알림 줄에 이유를 보인다. 두 유형이 함께 든 학교 설정을 불러올 때는 저장 배열에서 먼저 나온 하나를 유지하고 같은 알림을 보인다. 저장 배열 순서를 과거 클릭 시각이라고 설명하지 않는다. 처음 열기와 설정 불러오기 둘 다 회귀 시험에 넣는다.»

### 5. 붙여넣기 허용은 세트 POST만 고쳐서는 성립하지 않는다

- **초안 문장:** 60행 «저장은 막지 않는다(붙여넣기 세트를 거절하지 않음)»와 만들기 화면의 동시 선택 해제.
- **코드 사실:** `EnglishMakerView.tsx:314`의 붙여넣기는 `validatedConditions`와 `parseChatgptResult(..., { types: request.types })`를 거친다. `src/lib/english/chatgpt.ts:211`은 이 조건을 검증기에 넘기고, `src/lib/english/validate.ts:111`은 선택하지 않은 유형을 거절한다. 따라서 한쪽 선택을 해제하면서 두 유형이 든 붙여넣기 결과를 그대로 허용한다는 두 문장은 현재 경로에서 양립하지 않는다. 저장 POST에 새 금지 규칙을 추가하지 않는 것만으로는 부족하다.
- **최종본에 넣을 문장:** «어법·어휘 동시 선택 제한은 새 생성 조건에 적용한다. 이미 두 유형이 들어 있는 붙여넣기 결과는 거절하지 않도록 importPaste의 요청 유형 대조도 함께 조정한다. 이 예외는 선택된 어법 또는 어휘에 대응하는 나머지 한 유형의 동반 수록에만 적용하고, 다른 미선택 유형·요청 문항 수·요청 유형 누락·원문 유지·보기·정답·근거 검증은 유지한다. 수정 요청문을 만드는 경로도 같은 허용 범위를 사용한다. 회귀 시험은 세트 POST뿐 아니라 실제 붙여넣기 버튼에서 두 유형이 든 세트가 저장되는지 확인한다.»

### 6. 기존 어법 검사의 실제 보장 범위를 구분한다

- **초안 문장:** 7행 기존 기계 공유, 46~53행 «밑줄 다섯·다른 밑줄 하나·그 번호가 정답·나머지 넷 원문 그대로».
- **코드 사실:** `src/lib/english/quality.ts:598`의 진입 조건에 어휘를 추가해야 `variantChecks`에 도달한다. 내부는 소문자 영어 토큰 대조이고 꺾쇠 표기를 먼저 제거한다(71~102행). 번호 존재 검사는 중복 횟수나 실제 `<u>` 구간 수를 검사하지 않는다. 나머지 네 표현 검사는 보기 문자열이 원문 **어딘가에** 있는지를 보고(530~540행), 해당 번호의 실제 밑줄과 보기의 동일성을 확인하지 않는다. 정답 위치는 보기 토큰 길이와 편집 구간의 접촉으로 계산한다(549~562행). 기존 테스트에도 `<u>`가 전혀 없는 어법 문항이 구조 검사에 통과하는 표본이 있다(`src/__tests__/unit/englishQuality.test.ts:96`).
- **최종본에 넣을 문장:** «어휘를 quality의 유형 진입 조건에 추가하고 어법의 토큰 정렬을 재사용하되, 기존 검사 통과가 실제 밑줄 다섯과 보기 대응까지 보장한다고 쓰지 않는다. 어휘의 네 조건을 완료 기준으로 삼으므로 번호와 실제 밑줄 구간의 대응, 각 보기와 해당 밑줄의 일치, 정답 외 네 구간의 원문 위치 대조를 어휘 고정물로 확인한다. 번호 누락·중복, 보기와 밑줄 불일치, 두 곳 변경, 잘못된 정답 번호를 실패 표본에 둔다. 이 검사는 품질 관측값으로 남기고 저장 거절에 연결하지 않는다. 문맥상 어휘 선택의 적절성까지 기계로 검증했다고 쓰지 않는다.»

### 7. 누출은 대상 목록과 답 위치를 함께 열고 방향별로 센다

- **초안 문장:** 55~58행 answerSpan 확장, «어휘 정답 낱말이 빈칸 문항 지문에 20자 이상 연속으로 있으면 누출 1건».
- **코드 사실:** `src/lib/english/leak.ts:33`에 `bundle.ts`와 별개인 `VARIANT_TYPES`가 있다. `findVariantLeaks`는 이 목록으로 먼저 거르므로(155~158행) answerSpan만 수정하면 어휘는 검사되지 않는다. 어법 answerSpan은 틀리게 제시한 낱말이 아니라 **원 지문에서 그 낱말이 차지했던 위치**를 찾는다(80~99행). `withContext`는 앞뒤 두 토큰을 붙이고 필요하면 20자 이상까지 넓힌다(65~76행). 비교는 소문자 영어 토큰의 연속 일치다. 누출은 방향이 있는 source→target 쌍이므로 서로 노출하면 두 건이다. 기존 시험도 전체 개수보다 해당 방향의 쌍과 원래 표현을 확인한다(`src/__tests__/unit/englishLeak.test.ts:79`).
- **최종본에 넣을 문장:** «leak.ts의 VARIANT_TYPES와 answerSpan의 밑줄 분기 모두에 어휘를 포함한다. 어휘가 바꾼 위치의 원래 표현을 원 지문에서 찾고, 앞뒤 문맥을 붙인 20자 이상 토큰 창이 다른 변형 문항 발문에 남아 있는지 비교한다. 어휘→빈칸의 source·target·kind와 원래 표현이 담긴 snippet을 확인하는 고정물을 둔다. 전체 1건을 주장하려면 역방향 누출이 없는 표본을 쓰고, 양방향 표본은 2건으로 확인한다. 원래 낱말만 같고 문맥은 다른 음성 표본도 둔다.»

### 8. 변형 분류와 서로 다른 묶음 보장을 구분한다

- **초안 문장:** 60행 «bundle의 VARIANT_TYPES에 어휘를 넣는다», 완료 표 107행 묶음 분리.
- **코드 사실:** `src/lib/english/bundle.ts:59`의 목록 추가는 원 지문 상자가 없는 변형으로 분류하는 역할이다. `groupVariants`는 누출이 없으면 여러 변형을 같은 묶음에 놓고, 누출 그래프가 순환하면 하나씩 떼어 남는 쌍을 `open`에 기록한다(89~170행). 어법과 어휘라는 이름만으로 항상 다른 묶음이 되는 구조가 아니다. 원 지문은 독해 문항이 있는 마지막 묶음에만 실린다.
- **최종본에 넣을 문장:** «어휘를 변형으로 분류하여 독해의 원 지문 상자와 분리한다. 어법·어휘가 함께 든 붙여넣기 세트는 실제 findVariantLeaks 결과를 이용한 통합 고정물로 묶음을 확인한다. 서로 원래 표현을 보여 주는 표본은 다른 묶음으로 나뉘고 남는 순환 누출은 open과 기존 안내에 표시되어야 한다. 유형 분류만으로 누출이 해결되었다고 하지 않는다.»

### 9. options.ts의 존재하지 않는 유형 분기는 수정 대상으로 적지 않는다

- **초안 문장:** 62행 «options.ts의 어법 자리 판정도 어휘를 포함한다», 같은 행 밑줄 그리기·학생용 인쇄 잠금 확장.
- **코드 사실:** `src/lib/english/options.ts:49`의 `englishOptionLayout`은 `type`을 입력받지 않고 `prompt`와 `options`만 사용한다. `①<u>` 또는 `(①)` 위치와 번호뿐인 보기인지로 판단하므로 같은 표기인 어휘에 이미 적용된다. 유형 분기가 실제로 있는 곳은 `src/components/english/EnglishPromptText.tsx:48`과 `src/lib/english/underline.ts:79`다. `englishUnderlineNotices`의 안내 문구는 «어법 문항»으로 고정되어 있다(123~134행). 밑줄 잠금은 짝 불일치 또는 밑줄형 발문에 유효 구간이 하나도 없는 경우이며 다섯 구간의 정확성 검사와는 다르다.
- **최종본에 넣을 문장:** «EnglishPromptText와 findEnglishUnderlineProblems의 어법 전용 분기에 어휘를 포함하고, 안내가 어휘 문항을 어법이라고 부르지 않게 한다. options.ts는 유형 분기를 신설하지 않는다. 같은 발문·보기 표기의 어휘에서도 번호 중복 없이 보기 줄을 생략하는 회귀 시험을 추가한다. 기존 비밑줄형 어법의 인쇄 허용과 다른 유형의 꺾쇠 표시 규칙은 유지한다.»

### 10. 읽기 계약과 생성 프롬프트의 결합을 구현 순서에 반영한다

- **초안 문장:** 44행 «읽는 쪽을 먼저», 64행 «검사 뒤 englishExam.ts와 ChatGPT 요청문에 어휘 줄», «상수 한 줄이 세 길에 같이 간다».
- **코드 사실:** `src/contracts/english.contract.ts:52`의 목록에서 생성 유형이 바로 파생된다. `src/lib/ai/prompts/englishExam.ts:63`의 안내는 모든 생성 유형을 요구하는 `Record`이고, 시스템 프롬프트는 그 전부를 순회한다(136행). enum만 추가하고 안내를 빈 채로 둔 단계를 타입 검사 통과 상태로 볼 수 없다. ChatGPT 제작 요청은 같은 안내를 읽지만(`src/lib/english/chatgpt.ts:87`), 수정 요청문은 허용 유형 이름만 읽는다(279행). 원문 복원은 `makeCloze` 경로이므로 어휘 생성에 참여하지 않는다. 어법의 기존 안내는 밑줄 표현을 보기 5개로 그대로 내도록 명시한다(englishExam.ts 67행).
- **최종본에 넣을 문장:** «2조각은 내부 순서만 읽기·검사·표시 준비와 생성 활성화로 나눈다. 저장 enum 추가가 생성 목록에도 즉시 반영되는 현재 구조를 고려하여 미완성 중간 상태를 배포하지 않는다. quality·leak·bundle·underline 시험을 먼저 통과시킨 뒤 공유 ENGLISH_TYPE_GUIDE에 어휘 안내를 완성하고 전체 타입 검사·요청문 회귀를 통과시켜 조각을 마친다. 어휘 안내에는 문제용 지문을 prompt에 넣는 자리, ①<u>표현</u> 표기, 다섯 보기와 밑줄의 대응, 정답 번호를 명시한다. API와 ChatGPT 제작 요청은 안내 한 벌을 공유하고 수정 요청문은 허용 유형 이름에 반영된다. 원문 복원과 기존 어법 안내는 바꾸지 않는다. 프롬프트 판과 변경 이유 기록은 해당 파일 규칙을 따른다.»

## 빼거나 뒤로 밀 문장

- 19행의 «세 길 모두 다시 생성»은 경로별 설명으로 바꾼다. 붙여넣기 원문과 복원 입력은 남는다.
- 44행의 «문자열로 그리므로 거절만 안 되면 된다»는 뺀다. 새 유형은 밑줄 표시·인쇄 잠금·변형 분류까지 열려야 학생용 지면이 맞다.
- 58행의 «정답 낱말 20자·누출 전체 1건»은 원래 표현의 문맥 창과 방향별 누출 시험으로 바꾼다.
- 62행의 options.ts 유형 추가는 뺀다. 해당 함수에는 유형 분기가 없고 동일 표기 회귀만 필요하다.
- 64행의 «상수 한 줄이 세 길에 같이 간다»는 공유 프롬프트 소비 경로 설명으로 바꾼다. 원문 복원에는 해당하지 않는다. 브리프의 글자 `c` 주석에 별도 의미를 부여하지 않는다.
- 3·4조각의 순서·무관 문장 검사 함수와 테스트도 이번 실행 목록에서는 뒤로 둔다. D7 가에 따라 계획에만 남기며, 이번에 계약·검사·인쇄 코드를 쓰지 않는다.

## 최종본 순서

이번 실행은 **1 저장 → 2 어휘**로 유지한다. 1조각에서 세 경로의 저장 본문 보존·원자적 재시도·6문항·이름 255자를 닫고, 2조각에서 읽기와 검사·표시 준비 뒤 생성 안내를 마지막에 완성한다. 2조각의 내부 단계를 나누되 enum만 먼저 배포하지 않는다.

초안의 3 글의 순서 → 4 무관한 문장은 후속 순서로만 남긴다. 이번 완료표에서는 해당 검사 구현을 요구하지 않는다. 어휘의 print-check는 같은 지면의 항목을 추가하고 실물 확인 전까지 대기로 남긴다.
