# 수학 문항 형식 통합·오류 수정·재고 보강 계획

작성 Codex · 2026-10-18 · R1. Claude의 명시적 승인과 이 파일 SHA-256을 연결한다.
사용자 지시: “보강 계획세우고 클로드한테 승인 후 진행”, “같은 문제임에도 2개로 되는거지”.
이 계획의 제품 코드·생성기·공유 DB 변경은 계획 승인 뒤 시작한다. 수정 요청은 승인이 아니다.

## 1. 결과와 기준

같은 수치·조건·그림·물음인 객관/단답 표현은 **한 문항·한 카드·한 재고**로 센다.
교사는 담기·구성·문항 검토에서 실제로 사용할 형식을 선택한다. 숫자가 다른 같은 유형은
별개 문항이며, 풀이·반례·증명 등 다른 학습 행동을 요구하는 본래 서술형도 별개 과제다.
지원하지 않는 형식을 끝말 변경이나 보기 삭제로 즉석 생성하지 않는다.

기준은 main `1d84a0a933e439acba941498472a420b184e9095`와
[기존 감사](../../reports/math-type-audit-20261018/README.md)다. 감사의 읽기 전용 스냅샷은
2026-10-18 13:58 KST, SHA-256 `daf90c9a97e0630bb8be372e873187603f1fdbf5a201de18c009e266f7cfbac3`다.

## 2. 문항 연결과 DB 호환

`Problem.questionGroupKey` nullable text와 직접 형제/단원 조회 인덱스를 추가한다.
`questionId = questionGroupKey ?? row:<기존 UUID>`이며 새 키는 `q:v1:<SHA-256>` 이름공간이다.
기존 ID·문항 코드·externalId·familyKey·모든 FK를 보존한다. 행 삭제/코드 재발급/학생 기록
변경/과거 시험의 재구성은 하지 않는다. NULL과 알려지지 않은 자료는 각각 독립 문항이다.

첫 backfill은 다음 조건을 **모두** 만족한 정확한 두 행만 연결한다.

1. 알려진 `engine-elem`, `engine-mid`, `engine-mid-combo` 전체 외부 키 문법에서 형식만 다른
   정확한 단답 1개/객관 1개이고 저장 형식도 일치한다. 단원·원천·유형·seed·variant를 보존한다.
2. unitId/source/familyKey/difficulty/problemType/originProblemId/sourceMaterialId가 같다.
3. 객관 본문은 단답 본문 뒤에 기존 생성 계약의 정확한 다섯 보기 ①~⑤를 붙인 것이다.
   객관 정답이 가리킨 보기 값과 단답 정답이 trim 후 정확히 같고 단답 정답은 보기 번호가 아니다.
4. 해설 및 figureSvg/figureUrls/figureDims/figureSourceMm/choiceFigureIndex/figureSource가 같다.
   대수적 추정·숫자 마스킹·문장 유사도는 증거로 사용하지 않는다.

정체 관련 필드(위 비교 필드와 externalId/questionType)가 실제로 바뀌면 `BEFORE UPDATE`
트리거가 **그 행의** 키를 NULL로 지운다. 같은 UPDATE에서 키를 덮어써도 무효화한다.
키만 설정하거나 검수/잠금/pool/updatedAt만 바꾸는 경우에는 유지하고 요청마다 현재 자격을
다시 판정한다. 트리거는 SECURITY INVOKER, 고정 search_path, 공개 실행 권한 회수로 만든다.
기존 코드 동결/등록 바깥벽/관계 보호 트리거와 함께 검증한다. RLS나 브라우저 권한은 넓히지 않는다.

DDL은 추가만 한다. 적용 전 실제 스키마/트리거/인덱스·잠금 시간을 확인하고 로컬 PostgreSQL에서
기존/새 코드 쓰기·무효화·롤백을 검증한다. backfill은 현재 데이터를 다시 proof한 manifest를
생성하고 충돌/부분 쌍/기존 키 변경을 거부한다. 원본 revision을 흔들지 않게 키만 SQL SET하며
updatedAt/내용/자격/코드는 readback으로 전후 동일함을 확인한다. 배치별 짧은 트랜잭션·두 행
잠금·현재 payload CAS·멱등 재실행을 사용한다. 중간 배치는 미연결 행이 단독으로 보이는
보수적인 상태이며 잘못 합쳐지지 않는다. 생성/검증 적재기는 실제 pair proof 뒤 키를 부여한다.

**Gate 2:** 실제 DDL, 트리거, backfill 판정 manifest의 SHA·현재 건수·전후 불변 검사를
별도 Claude 실행 검토로 승인받기 전 공유 DB에 쓰지 않는다. 역작업은 이 실행이 넣은 키만
CAS로 NULL로 돌리는 명시적 도구이며 다른 작업의 새 키/내용을 지우지 않는다.

## 3. 공통 읽기 계약과 수량

서버 공통 projection이 현재 visibility/eligibility와 모든 필터를 통과한 **같은 실제 행**을
문항 키로 묶는다. 그룹화 → 정렬 → 페이지 처리를 한다. 한 페이지를 받은 UI에서만 접지 않는다.
큰 SVG를 모든 조회에 전송하지 않고 후보의 작은 메타데이터와 최종 선택 행의 본문을 읽는다.
본문이 필요한 형식 판정은 기존 정확한 classifyFormat/formatQuery를 재사용한다.
raw SQL 사용 시에도 기존 권한/공개/자격 gate를 동일하게 적용한다.

- `held`는 현재 조건에 맞는 공개 행의 distinct questionId, `available`은 그중 적격 행의
  distinct questionId다. available ≤ held. 목록 total과 같은 조건의 가용량은 일치한다.
- 형식별 수는 그 형식을 낼 수 있는 문항 수다. 객관/단답 양쪽에 속할 수 있어 합산하지 않는다.
- 기본 유형 제한을 켠 한 장 구성 상한은 문항류 제한도 적용한다. 단순 문항 총수를 출제 보장으로 표시하지 않는다.
- 글로벌 출처 수/자료 수/차시 수/facet는 각 기존 범위를 유지하며 단위만 문항으로 맞춘다.
  확인하지 못한 수·로딩·실패는 null/확인 중이고 0으로 바꾸지 않는다.
- 코드 검색과 명시적 `ids` 복원/검토는 정확한 실제 ID를 유지한다. 저장본은 형제 대표로 바꾸지 않는다.
- 편집 중 선택한 questionId/실제 problemId/형식/개정을 서버가 발급하고 출력·새 저장 전에
  실제 행의 현재 자격·연결·형식·개정을 재검증한다. 변경되었으면 409/재조회로 입력을 보존한다.

전환은 `identity=question`의 명시적 읽기 요청과 응답 `countUnit:question`으로 한다.
기존 행 조회/정확 ID 상세/검수 계약은 유지한다. **현행 사용자 은행 UI와 초기 bootstrap,
목록, 출처, 가용량, 담기, 랜덤 구성은 한 번에 새 보기를 사용**한다. 새 보기 실패 시 행 수를
문항 수로 대신 표시하지 않는다. 운영/dev GET·긴 조건 POST가 같은 함수를 사용한다.

통합 계약 파일 `src/contracts/questionFormats.contract.ts`를 데이터 담당이 먼저 고정한다.
BankProblem/StudioProblem에는 optional `questionId`, `questionFormats`를 더하되 `id`는 실제
Problem.id다. 표현 항목은 problemId/format/revision/state(available|blocked|unverified)/reasonCode다.
실제 표현 상세를 읽은 선택은 questionId/problemId/format/revision을 가진다. unknown은
서술형으로 간주하지 않는다. 구 저장 payload/영어/로컬 잘라낸 문항은 이 메타 없이 읽힌다.

## 4. 선택·담기·최근 제외·출제 형식

가능 형식은 기존 카드에 표시하고 다중 형식일 때 담기/검토의 native radio 대화창에서
실제 본문·보기 미리보기를 선택한다. 같은 문항이 이미 담겼으면 형식 변경은 같은 자리의
실제 행 전체를 교체한다. 담긴 수·순서는 늘어나지 않는다. 선택된 형식의 잠금은 별도 검사한다.

Studio 배열 바구니와 `/api/basket` 계정 바구니 양쪽을 바꾼다. 동시 담기는 사용자별
직렬화/트랜잭션으로 같은 questionId 중복을 막는다. 같은 실제 ID는 멱등, 다른 형제가 있으면
명시적 형식 변경 요청을 받는다. 형식 교체는 한 트랜잭션에서 순서를 보존한다. 기존 바구니에
형제가 둘 이상이면 GET에서 정리하지 않고 충돌로 보여 교사가 선택해 해소한다.
새 시험 생성은 형제 중복을 거부하고 실패 시 바구니를 보존한다.

현재 제작기의 객관식/단답형/서술형 3칸 할당을 재사용한다. `0`은 금지, 누락은 미지정이며
모두 지정하면 총합이 맞아야 한다. 같은 문항 안의 실제 표현에서 배정한다. 먼저 몇 문항을
뽑고 다른 유형 변형으로 형식만 맞추는 현재 동작을 고친다. 전체 후보의 범위·난이도·형식·
유형 제한을 함께 고려하고 가능한 다른 선택이 있는데 임의 선추첨 탓에 부족으로 보고하지 않는다.
탐색 한도에 도달한 경우는 증명된 재고 부족과 구분한다.

`distinctFamilies=false`여도 questionId는 한 장에 한 번이다. “새 문항 교체”는 현재 문항의
모든 형식을 제외한다. `recent`가 켜진 경로는 기존 소유 계정·14일 경계를 유지하면서 최근
실제 ID를 모든 형제 ID로 확장한다. 같은 유형의 다른 숫자까지 제외하지 않는다.
수동 바구니의 recent 생략 기본은 기존대로 두고 새 UI가 선택한 설정을 명시한다.

일일/확인 출제 GenerateSetup와 DailyReviewSection에 기존 설정 끝의 접힌 3칸 형식 할당을
추가하고 `/api/tests/generate`의 optional `formats`에 전달한다. 생략한 호출/아침 자동 초안은
기존 미지정 정책을 유지하되 문항 중복은 막는다. 부족 시 다른 형식으로 몰래 채우지 않는다.
서로 다른 학생의 필요 문항 수에 한 절대 할당을 무조건 복사하지 않는다.
이번에 새 반 기본 설정/일정 화면은 만들지 않는다. 초안 교체는 요청 형식을 보존한다.

과거 시험/배포본/교과서 snapshot/개인 저장 payload의 실제 ID·내용·답·형식·순서는 유지한다.
과거 중복 저장본도 열기/출력 시 자동 축약하지 않는다. 새 규칙으로 편집할 때 사본에서
유지할 표현을 선택한다. 이 변경이 모든 옛 시험을 불변 snapshot으로 만들었다고 주장하지 않는다.
30일 “내 출제”를 문항으로 집계하는 새 보기에서는 형제의 서로 다른 시험 ID를 합집합으로 센다.
저장 조건 v1은 형식/배치 미저장 의미를 유지하고 그 사실을 화면에 명시한다.

## 5. 확정 오류 17행과 유형 정리

[읽기 전용 preflight](reports/math-question-formats-20261018/repair-preflight.json)는
5개 문항류의 17행을 확인했다. 최초 감사 14행에 `tri222Pick` 3행이 추가됐다.
현재 연결 참조는 0이지만 실행 직전 다시 검사하며 새 참조가 생기면 수정을 중단한다.

| 원인/대상 | 현재 행 | 수정 |
| --- | ---: | --- |
| tri221PickIso/tri222Pick: rightTri와 wideTri도 이등변 | 3+3 | 두 선택 문제에만 정확히 비이등변인 부등변/직각부등변 도형 사용. 기존 rightTri/wideTri 전역 의미는 보존 |
| quad242PerpCount: 4/5쌍인데 그림은 3쌍으로 잘림 | 4 | 실제 개수 그대로 FigureSpec에 전달, 렌더된 수직 관계도 검산 |
| quad244Pick: 직사각형도 포함 정의상 사다리꼴 | 3 | 평행쌍이 없는 오답 도형으로 교체, 유효 정답 정확히 1개 |
| poly263Name: 모든 변만 같은데 정다각형 답 | 4 | 모든 각도 같다는 조건을 명시하고 정답 유일성 검토 |

소스/저장된 실제 SVG/본문/정답/해설의 대응을 확인한다. 새로운 원시 도형이 필요하면
좌표로 변 길이/각/평행을 독립 검산한다. 원래 씨앗/라벨/정답 위치를 가능한 한 보존한다.
참조 테이블 runtime catalog 재검사·쓰기 잠금·원본 payload CAS·전후 원장을 사용한다.
수정 후보 17개와 source/renderer SHA를 Claude가 내용 승인하기 전 DB 수정을 하지 않는다.
변경 후 두 형식이 있다면 다시 proof해 그룹 키를 회복한다. 학생/과거 시험을 소급 수정하지 않는다.

유형 통합은 기존 감사의 whole-family source proof가 있는 것만 한다. 결합형 위임 3개를
대응 중등 기본 유형으로, 계수 위치 19A/21A/23A/25A와 20A/22A/24A/26A를 각각
무수히 많은 해/해 없음 두 부모로 묶는다. 두 해 조건은 합치지 않는다. 순수 canonical-family
resolver로 raw 키·코드·검색 소속을 보존하고 모든 family count/선정/제외 경로를 맞춘다.
부분 중복 후보 전체를 자동 병합하지 않는다. 이 유형 묶음이 다른 숫자 문항까지 하나로 세는 근거는 아니다.

이후 기존 감사에서 생성기가 5개 이상을 만들 수 있는 것으로 확인한 **53유형에 한해서**
다른 내용 5문항에 못 미치는 만큼만 보강한다. 최초 비교의 부족은 96내용(초등34·중등/본래서술62)이며
이번 상한은 **새 내용 96개, 저장 표현 174행**이다. 18개 native 서술은 단독 표현, 나머지만
검증된 객관 파생을 허용한다. 통합/재집계로 줄면 줄인 정확 allowlist를 최종 고정한다.
상한을 넘는 신규 유형·전 교과서 9,647쌍 생성·고등 확장은 이번에 하지 않는다.

가짜 서술형·객관 오답이 성립하지 않는 f33/f39·고정 유한 정의형을 숫자만 바꿔 채우지 않는다.
실제 본문/보기 조건/그림을 포함해 기존 문항 및 새 후보 간 중복을 제거한다. 독립 풀이·정답 유일성·
도형 조건·학년 범위·풀이/부분점수 기준·실제 학생용/교사용 인쇄를 검토한다.
최종 exact 후보 manifest/UUID prewrite 원장/재생성 일치/읽기 검산을 별도 Claude가 승인한 뒤
기존 verified-batch와 동등한 보호 도구로 root만 적재한다. 재실행 0개 추가/전량 readback을 확인한다.

## 7. 역할·실행 순서·완료 증거

1. 계획과 설계 보고서를 고정해 Claude의 SHA 연결 승인을 받는다.
2. Codex 병렬: A 정체/DB/공통 조회·선택·서버 API·family alias와 타입을 먼저 고정,
   B 그 계약을 사용한 카드/형식 선택/바구니/일일 UI, C 오류 17행 소스·독립 검산·보호 수정 도구.
   root는 통합 경계와 후속 보강 후보를 맡는다. 동일 파일 중복 편집을 피한다.
3. 필요한 Next 설치 문서·DESIGN·메뉴 규칙·Supabase 최신 문서에 맞춰 구현한다.
   학생 SRS/선택 메뉴/인증/교과서 원문·슬롯/인쇄 예외를 보존한다. AI 의미 판단 통합은 하지 않는다.
4. Claude의 최종 DDL/backfill/오류/추가 후보 승인 후 root가 보호된 쓰기를 순서대로 실행하고 재집계한다.
5. 관련 검증·타입 검사·lint·로컬 PostgreSQL 통합 검사, 실제 UI→API→DB→선택/인쇄 흐름을 확인한다.
   390/320px·키보드/radio·초점 복귀·잠금/충돌/부족·저장본/영어 호환을 확인한다.
6. main에 로컬 병합하고 실제 행/문항/유형 전후 수와 미해결 사항을 남긴다. push 직전에는
   원격을 fetch/비교/통합/재검증한다. 사용자 추가 지시 없는 배포는 하지 않는다.
   완료·병합·clean·비활성인 Orca 자식만 제거하고 모든 작업 브랜치는 보존한다.

필수 반례: 같은 형제의 페이지 경계/최근 사용/동시 담기, family 제한 off, 같은 family의
다른 숫자, 보기 자체가 조건인 객관식, native 서술, 잠긴 형제, 선택 후 수정/형식 변경,
전체 후보에서는 형식 할당 가능한데 선추첨으로 실패하는 경우, 이전 저장본의 중복 그대로 출력.
DB 연결만 바뀌었음을 기존 내용·ID·코드·FK/학생 기록 불변 검사로 증명한다.
전체 은행 독립 풀이/공식 성취기준 전수 인증/실제 학습 효과/종이 물리 출력 완료로 과장하지 않는다.
